# 外部技能引进（open agent-skills 生态）

技能库的**第三条录入路径**。原有两条是「手写」和「合并」；这条是**从外部公共目录直接装**。
和另两条一样，装完要过 INDEX 重建与体检——外部来的技能不享受豁免。

## 生态是什么

- **`skills.sh`** — Anthropic「Agent Skills」开放标准的公共目录（技能 = 含 `SKILL.md` 的目录），
  按安装量排行，与 Claude Code / Codex 等 agent 生态互通。
- **`npx skills`** — 该生态的包管理器 CLI：`find` / `use` / `add` / `update` / `ls`。

## Hermes 是它的一等目标（不是靠兼容层）

CLI 源码里显式定义了 Hermes 目标，靠**目录是否存在**来决定要不要接：

```ts
'hermes-agent': {
  skillsDir: '.hermes/skills',
  globalSkillsDir: join(hermesHome, 'skills'),
  detectInstalled: () => existsSync(hermesHome),
}
```

落点由 `HERMES_HOME` 决定（默认 `~/.hermes`）。全局装是**两段式**：

```
~/.agents/skills/<name>/          ← 真实文件（所有 agent 共享的唯一副本）
~/.hermes/skills/<name> -> ../../.agents/skills/<name>   ← 软链
```

**软链技能是技能库的成员，但「扫得到」必须按工具分别验**：
`register.sh` 会跟进软链（索引里正常出现，总数 +1）；**基于 `os.walk` 的扫描器默认不跟进**
（`followlinks=False`），会**整条漏掉**软链技能——症状是 `skill_ref_lint.py --skill <名>`
报 `no skill matched: <名>`，而全库扫描把它当不存在，**且不报任何错**。
`skill_ref_lint.py` 已补丁修正（`iter_skill_dirs` 在 `os.walk` 之后补扫 `root.iterdir()` 里的软链目录）。
**装完不能只看 register.sh 的数字，必须再用 `--skill <名>` 单查一次。**
⚠️ **落盘形态不一定是软链** —— 实测同一批安装里，有的落成软链（真身在 `~/.agents/skills/`），
有的直接落成**实体目录**。所以「共几个真身、怎么删、备份在哪」**每个技能都要单独确认**，
不能从一次观察推全体。卸载流程见下文「卸载一个已装的外部技能」。

## 命令

```bash
npx skills find <关键词>                     # 搜
npx skills use <owner>/<repo>@<skill>        # 不安装，先把内容打印出来
npx skills add <owner>/<repo>@<skill> -g -y  # 装：-g 全局，-y 免确认
npx skills update -g                         # 更新已装的全部
npx skills ls -g                             # 列出全局已装
```

`--agent <name>` 可定点指定目标，**但它只出现在 `--help` 的示例区，不在选项列表里** ——
只读选项区会以为没有这个参数。

**`use` 的仓库级用法，清单走 stderr**：`npx skills use <owner>/<repo>`（**不带** `@skill`）
会列出该仓库的全部技能名——**这份清单输出到 stderr，不在 stdout**。
只管道 stdout 会拿到 0 行，很容易误判成「这个仓库是空的」。要抓就 `2>&1` 或直接读 stderr。

## 引进前必做三件事

1. **先用 `use` 验证，再决定推不推荐。** `find` 会列出 `use`/`add` 解析不了的条目
   （实测见过一个二十万安装量的搜索结果，在该仓库里根本不存在）。
   **搜索结果不是可用性证明。**
   ⚠️ **判「留还是删」必须读完整的 `SKILL.md`，不能只看开头几行。**
   实测：一份技能读前 25 行时判为「可装可不装」，读完全部 180 行才发现它
   **整篇是另一个 agent 产品的专有协议**（消息类型、团队配置文件路径、专有工具名），
   在 Hermes 里**一条都用不上** —— 结论从「可留」翻成「必删」。
   长文技能的前言通常是通用套话，**领域标签和专有名词都在中后段**。
   这是往模型上下文里灌的活，别拿行数省成本。
2. **看安全评级。** 安装时会自动跑三家扫描（Gen / Socket / Snyk）并打印结果。
   技能**以完整 agent 权限运行**，CLI 自己也这么提示：`Review skills before use`。
   来源不明或安装量三位数以下的，不装。
3. **判相关性，别因为分高就装。** 排行榜前列压倒性是**前端开发**
   （React / Next.js / Expo / 设计系统）。跟本机实际负载（运维、cron、文档处理、笔记）
   对得上的很少；值得看的集中在**文档转换、表格处理、笔记与知识库**这几类。
4. **先翻官方包，再翻排行榜。** `nousresearch/hermes-agent` 是发布在 skills.sh 上的
   **官方技能包**（50+ 个技能：文档四件套 `xlsx`/`docx`/`pdf`/`powerpoint`、`humanizer`、
   `product-price-monitor`、`arxiv`、`llm-wiki`、`grounded-citations` 等）。
   来源确定、与 Hermes 自身设计一致，**优先级高于任何第三方仓库**。
   查某个能力域时，官方包和通用搜索一起看。
5. **装量高 ≠ 对你有用。** 高装量技能常**绑死某个框架**——实测 LangChain 的 `deep-agents-*`
   三件套合计 4 万+ 装，但内容是 `create_deep_agent()` / `StateBackend` 这类**框架专有 API**，
   装进 Hermes 用不上；同类的还有 AWS Bedrock、Rivet 等。**判据是「跨框架是否成立」，不是装量。**
   另外 `find` 是松匹配：实测一个有五十多万装量的结果出现在 "multi agent" 搜索里却完全不相关。
   **`find` 命中 ≠ 相关，也不是可用性证明，必须 `use` 看过再定。**
6. **优先方法论类，回避框架专有类。** 值得引进的是「怎么做」——上下文工程、独立评估者/
   Generator-Evaluator 分离、agent 评估方法。它们跨框架成立、不随框架版本腐烂。
7. **装完用本机确定性扫描器终检，别只信安装时那三家在线评级。**

   ```bash
   python3 ~/.hermes/skills/skill-security/scripts/scan.py <安装路径>
   ```

   离线、零 API key、带 YARA 规则与 source→sink 污点追踪，输出 0–100 风险分。

   | 分数 | 动作 |
   |---|---|
   | 0–20（LOW） | 直接用 |
   | 21–50（MEDIUM） | 读扫描器逐条 finding 再判 |
   | 51+（HIGH/CRITICAL） | 不装，除非能逐条解释清楚 |

   ⚠️ **扫描器会假阳性，两个必知：**
   - **它扫自己（或任何带检测规则库/威胁分类文档的技能）会报一堆 HIGH** —— 把 YARA 规则里的
     模式字符串、分析器里的检测正则、taxonomy 里的说明文字，当成了「实施攻击」。
     `skill-security` 自扫报 6 个 HIGH，**全是假阳性**。判法：问「这是它自己的规则库吗」。
   - **不能拿没验证过的扫描器输出直接汇报或执行删除。** 最低验证成本：造一个**已知恶意样本**
     （如伪装成「菜谱助手」实则读环境变量 POST 到外部域名的脚本），确认它能把
     `Credential/env flows to network sink` 这类链条报出来，**它的输出才可采信**。

   扫描器的两阶段分工值得学：Stage 1 确定性扫描出候选；**Stage 2 由 agent 读原文做契约检查**
   ——「声称做的事」vs「代码/指令实际做的事」对不对得上。**扫描器判不了意图，人能。**
   详见 skill `skill-security`。

## 克隆下来 ≠ 拿到实现：先确认核心逻辑在哪个仓库/包里

评估一个候选项目能不能满足需求时，**读论文/读 README 会让你以为核心逻辑就在眼前**。
真实情况常见两种：核心算法 `import` 自一个**独立发布的包**，或只存在于**服务端**。

实测：一个声称做「格式合规评分 + 技能组一致性检查」的工具，`src/` 下 59 个文件里
`validator.ts` / `skillset-coherence.ts` 全部把自己的规则 `import` 自 `@skilldex/validator`——
**那个包不在这个仓库里**，clone 下来只有「找目录、读文件、列文件」这层 I/O。
其作者注释自承曾有两套实现漂移了四处才统一。**评分规则要 `npm pack`/`pip download` 那个包才拿得到。**

**判据: 判断「它能不能做 X」之前, 先 `grep -rE "from '@|require\\(|import .* from ['\\\"][^./]" <src>` 找出所有外部依赖**, 再逐个确认:
- 依赖是否开源可取（私有/需登录 ⇒ 拿不到, 结论只能基于论文描述, 不能基于代码）
- 依赖是否需要服务端/数据库（需要 ⇒ 本地跑不通, 只能读设计）

**推论: 论文级贡献 ≠ 可用代码。** 读到好的设计**就把设计抄进自己的实现**,
不要停在「有个现成项目」——按 skill `tool-trial-keep-drop` 的纪律, 新工具的判据是**实测功能**,
4 star 的学术原型与 35k star 的成熟工具要分开对待。

⚠️ **“搜一下有没有现成的” 是独立的一道工序, 不是自建前的可选动作。**
用户提新能力需求时, **先搜再设计**——但搜完必须**如实报出空白**,
不能因为“搜不到”就静默转自建, 也不能因为“搜到了”就跳过验证。
本机实例: 需求是「技能剖析 + 拼接 + 自动推荐」, 搜出三个候选, 逐个查完发现
**只有一个命中三项需求, 而它的核心逻辑在另一个 npm 包里**; 另外两个分别只管安装/发布、
只管目录清单。**结论是“市面上没有第二个做功能重叠检测的”——这个空白本身就是交付物的一部分**,
它决定了下一步是移植还是自建、以及自建时该抄哪些设计。
**动作: 搜完在回复里明确写一行“搜到了什么 / 什么仍是空白”, 用户据此决定方向。**

### 论文/README 的贡献清单要按「我能不能用」重排

论文的 novelty 排序是给同行看的, 不是按你的需求排的。把每条贡献过一遍:
**它的输入是什么、我的输入是什么、两者一致吗?** 输入不一致的贡献再漂亮也用不上。

实测: 某工具的「智能推荐技能」被列为三大贡献之一, 但它读的是**项目上下文**(依赖清单、工具链)
去查**远端注册表**推荐「装哪个新的」; 而实际需求是「**已经装了的这些里哪个更适合当前任务**」——
**输入源不同(本地库 vs 远端注册表)、目标不同(选已有 vs 装新的)**, 那条贡献完全用不上。
另外它依赖某个本机没配的厂商 SDK, 连跑都跑不起来。

**动作**: 拿候选工具的贡献清单, 逐条标注「输入是否同源 / 输出是否同目标 / 依赖是否具备」,
三栏里有一栏是「否」, 这条贡献就出局。**只把通过的贡献当参考。**

## 验证一个候选项目（克隆之后）

⚠️ **star 数、README 的宣称、最近的提交日期, 都不是「它能干什么」的证据。**
克隆后至少验三样, 每样一条独立命令:

```bash
# 1) 它到底做什么——看命令面与依赖, 不看简介
cat package.json | head -40
# 2) 有没有偷传数据 / 读凭据
grep -rEl 'child_process|fetch\(|axios|\.ssh|\.aws|credentials' <src>
# 3) 最近提交是真代码还是只刷热度
gh api repos/owner/repo/commits?per_page=5 --jq '.[].commit.message' | head -5
```

**第 2 条命中不等于有后门——要看清那处调用在干什么。** 实测一个 TS 项目全文只命中
一处 `child_process`, 读下来是 `build-info.ts` 里用 `execFileSync` 读版本号, 无害。
**反过来, 一条「0 命中」也不能直接信**——扫的是 `src/`, 配置与构建脚本不在其中。
**验证的终点是「真跑一次」, 不是「读懂了源码」**：低星项目尤其,
论文级的设计往往配着未验证的实现, 两者要分开判。

## 装完的三种结局（「装好了」不等于交付）

装完当场就要能回答「**它命中我哪条铁律 / 往后替代哪段重复劳动**」。答不上来的，结局只有三种：

| 结局 | 判据 | 动作 |
|---|---|---|
| **会被触发** | 领域与实际负载重合（运维 / cron / 文档 / 笔记 / 写作风格） | 留，写清触发场景 |
| **读一遍就够** | 概念有价值，但其实现绑死在别的环境（某个 CLI / 框架 / 平台） | **吸收概念后删掉** |
| **永远不触发** | 领域与负载完全不重合 | 删 |

**关键认识：安装技能 ≠ 获得能力。** SKILL.md 只是**指令**，不是可执行能力 ——
它的价值完全取决于「你的 agent 实际任务会不会走到那块指令上」。
领域不重合的技能装进库，会**永远停在 `use_count=0`**，而「以为装着就有用」正是要防的错觉。

**判据（用于事后核对，不是装前依据）**：`.usage.json` 里的 `use_count` / `view_count`
与 `agent.log` 里的出现次数。
⚠️ 但它只记 agent 载入，**不记脚本直跑、不记 cron**，而且刚装完必然为 0 ——
**不能用它当「没用」的证据**（同 `long-tail-inventory-audit.md` 的三信号交叉判据）。

**一个可迁移的收尾原则**（来自 harness 设计）：
> 每个组件都编码了一个关于「模型/环境做不到什么」的假设。**假设不成立时，组件就该拆。**

拿它审自己刚装的技能：逐个问「它假定我不会什么？」——若那条你早已有别的机制覆盖
（如输出纪律已有 SOUL.md、模型路由已有插件），**这个技能就是重复组件，该删**。
这条原则可以来自一个你判断该删的技能本身：**它的内容有价值，但价值在你读它的那一遍。**

## 先有判断力, 再装能力包

用户问过「有了铁律再装技能, 有啥好处」。结论是**顺序本身是筛选器**：

**先问「我有哪条铁律 / 偏好 / 踩过的坑」, 再看候选技能命中哪条。** 命中哪条 → 用途当场清楚,
也**自然排出安装次序**(最对口的第一条装)。一条都对不上的 → 不装, 无论装量多少。

具体收益有三层：

1. **技能变成铁律的工程化实现, 而不是新东西往脑子里堆。** 例: 已有「生产者不得自审」这条铁律,
   看到某技能自称「把生成与评估分离」——用途当场成立, 不需要额外解释它能干嘛。
2. **铁律兼作筛选网。** 技能**以完整 agent 权限运行**(CLI 自己就这么提示),
   装错了不是「不好用」而是「有权限做别的事」。拿铁律当筛子, 比看装量、看名字可靠得多。
3. **铁律定义验收标准。** 「用了才知道有没有用」——但若事先知道「要拿它验什么」,
   装完就知道该造什么测试, 而不是装完就搁置。

**推论: 汇报一个技能「装好了」不等于交付。** 装完要回答的是
「它命中你哪条铁律 / 往后替代哪段重复劳动」, 答不上来就说明这技能不该装。
同理, **技能库体检通过 ≠ 技能有用** —— 引用干净只证明文件完整, 不证明它在解决真实问题。

## 一批候选的快速分流（收到多个仓库/链接时）

用户常一次扔来 3–10 个仓库问「有没有用」。**先分流再逐个读**——不然会把大量时间花在明显不匹配的项上。

**第一步：元数据分流（不读正文就能剔掉大半）。** 用 `gh api` 一次拿全，输出 ≤10 行/项：

```bash
for r in owner/repo1 owner/repo2; do
  gh api repos/$r --jq '"\\(.full_name) | \\(.language) | ⭐\\(.stargazers_count) | \\(.license.spdx_id) | created \\(.created_at[0:10]) | pushed \\(.pushed_at[0:10]) | archived=\\(.archived)"'
done
# 有 SKILL.md 的才进第二步
gh api repos/owner/repo/git/trees/main?recursive=1 --jq '.tree[].path | select(endswith("SKILL.md"))'
```

**第二步：活跃度查最近提交（区分「真在维护」与「只刷 star 图」）。**

```bash
gh api repos/owner/repo/commits?per_page=5 --jq '.[].commit.message' | head -5
```

实测判据：最近数次提交**全是 `chore: refresh star history chart` / 更新徽章 / 改 README 之类无代码变更的提交**
= 项目实质停滞，**README 里的性能宣称不再可信**。这类要在结论里点明，
否则用户会以为它能用一个已经两年没修的机制。

**第三步：体积与可裁剪性决定「入库 vs 只做摘要」。**
大仓库（尤其带大量多语言翻译/图片/权重）先 `du -sh` 看构成再决定：
**只保留真正会被查的那部分实体，翻译目录与 `.git` 往往占 80% 以上**，
入库前剔掉（把 2G 降到几十 M），并把剔除口径写进索引，否则下次会重新拉一遍。
判据是「会被使用的方式」：当参考手册查的入库，当通读教材的只留索引与要点。

## 汇报纪律：逐项给**差异化**结论，不要模塑两可

一批候选里大部分无价值是常态。**每一项都要有独立判据和独立动作**（装 / 只读 / 收藏不装 / 删），
并把「为什么对**你**没用」写具体——理由应当指向用户的实际负载（做什么工作、有什么设备、跑什么模型），
而不是复述项目简介。模塑两可的「都行」等于没做判断。

⚠️ **交付物要跟动作匹配**：判「只做参考手册」就该真的把精简件入库并给索引 + 使用方法，
判「不装」就不动手。**汇报说入库了却只有一段总结 = 没交付。**

## 卸载一个已装的外部技能（三处都要动）

⚠️ **先确认「要留的内容已落到别的技能里」，再删目录。** 「读一遍就够」的技能删之前，
把可迁移的规则提进**已有的、往后真会被触发的技能**（不是新建一个容器技能），
并当场验提取到位（搜关键词命中数 + 目标文件字节数变了）——
**先删后提 = 源内容没了，还得从回收站搬回来。**
注意：落到已有的技能里才算提取完成；把规则留在要删的技能里、删前自己念一遍，不算。

**删目录不等于卸载。** 按顺序三处，少一处就删不干净：

1. **先辨形态再删**：外部技能的落盘有**两种**，同一台机器上会共存 ——
   软链（`~/.hermes/skills/<name> -> ../../.agents/skills/<name>`，真身在 `~/.agents/`）
   和**实体目录**（直接写在 `~/.hermes/skills/<name>/`）。
   `[ -L "$d" ] && readlink "$d" || du -sh "$d"` 先看清是哪种，删除与备份动作不一样。
2. **删用回收站，不用 `rm`**：`gio trash <目录>` —— 可恢复，
   恢复命令 `gio trash --restore ~/.local/share/Trash/files/<name>`。
   用户明确要求「送进回收站」，删技能一律走这条。
3. **⚠️ 清锁文件，否则会被装回来**：`~/.agents/.skill-lock.json` 的 `skills` 字典里
   仍留着已删技能的名字，`npx skills update -g` 会**照单重装**。
   删完目录必须同时：删锁文件里对应键（先备份锁文件）→ `grep` 复查 → 再跑一次
   `register.sh` 让 INDEX 掉一条。

对账口径：技能总数应**正好减去删掉的个数**，且被删技能名从 INDEX 里消失。
只看到「目录不在了」不算删干净。

## 装完必做

```bash
bash ~/.hermes/skills/knowledge-management/skill-library-curation/scripts/register.sh
python3 ~/.hermes/scripts/skill_ref_lint.py --skill <新技能名>   # 软链专查：必须扫到
python3 ~/.hermes/scripts/skill_ref_lint.py                      # 全库复扫
```

对账：**技能总数必须 +1**（读 INDEX 头部那行），并确认新技能名出现在 INDEX 里。
**再用 `--skill <名>` 单查一次**——软链技能在全库扫描里可能整条不可见（见上文「软链」段），
单查输出里出现 `skills_scanned=1` 才算真被认到。
体检判据看「致命未降级」，**不是** `BROKEN` 总数（那是各类问题之和）。

## 坑

- **API 要鉴权。** `skills.sh/api/v1/...` 直接调用返回 **401**，排行榜与详情都拉不到。
  改用 CLI 的 `find`。**这不是「服务挂了」**，别据此下结论。
- **一个目标失败不影响其他。** 全局装时常见
  `PromptScript does not support global skill installation` —— 那是某个不支持全局安装的
  目标自己报的错，**不是本次安装失败**。判成功看 Hermes 那条链建没建起来。
- **别在测试时 `export HERMES_HOME`。** 它直接决定安装落点, 而终端变量**跨调用持久** ——
  忘了清会让后续每一次“真实”安装都写进临时目录, 表现成「CLI 不认 Hermes」,
  很容易误判成“CLI 不支持 Hermes”。**在同一个调用里 `unset`**, 下结论前 `echo` 确认。

## 装不上时：先分辨是谁的锅, 再动手

`add` 失败**绝大多数不是技能本身的问题**, 而是传输层。按这个顺序判, 别一上来就调工具配置：

```bash
# 1) 先看完整报错(默认输出会截断, 失败原因常在被截掉的那段)
npx -y skills@latest add <owner>/<repo>@<skill> -g -y --agent hermes-agent 2>&1 | head -50

# 2) 关键区分: 报的是「技能找不到」还是「拉不下来」
#    拉不下来 → 看第 3 步; 技能找不到 → 换技能, 不是环境问题
```

**`gnutls_handshake() failed` / `HTTP 000` / 任何传输层报错 → 先测直连, 别动 TLS 配置。**

```bash
curl -s -o /dev/null -w "proxy %{http_code}\n" -x http://127.0.0.1:7890 https://github.com
curl -s -o /dev/null -w "direct %{http_code}\n" --noproxy '*'               https://github.com
```

**代理 000 + 直连 200 → 代理链路死了, 技能是好的。** 绕过代理重跑同一条命令即可:

```bash
unset https_proxy http_proxy; export no_proxy="*" NO_PROXY="*"
```

⚠️ **不要改 `git config http.version` / `postBuffer` / `sslVerify`** —— `npx skills` 底下是
`git clone`, 代理在握手**中途**掐断连接, git 把它报成自己的 gnutls 错误。
**错误消息命名的是最表层那一环, 不是根因。** 先做走代理 vs 直连的 A/B, 再决定往哪一层查。

> 本机实测反面教材: 先改 git 全局 TLS 参数 → 症状不变 → 才测出直连 200。**顺序反了就是白改一轮配置。**

### 传输层故障与「技能本身坏」要分开记

传输层失败**不产生任何关于技能质量的证据**。修好链路后**必须重跑安装并验证落点**,
不要因为「反正失败了」就把这个技能从推荐列表里划掉 —— 它可能完全可用。
