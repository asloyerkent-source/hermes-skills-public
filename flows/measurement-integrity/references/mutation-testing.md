# 变异测试：证明你的测试和检查器**能失败**

全绿和全错在输出上长得一模一样。铁律 4 用「已知正确答案」验读数通道；
这里是对称的另一半：**用「已知错误的答案」验它有没有分辨力**。

---

## 1. 变异测试的基本动作

把被测代码按一个具体的方式改坏，跑测试，**必须变红**。

```bash
cp <f> /var/tmp/orig.bak          # 每个变异单独恢复，别叠
# 改坏 → 跑 → 期望非 0 → 恢复 → 确认恢复后仍全绿
```

有效变异的选择原则：**挑那个「如果它不在，测试应该抓不到」的东西。**

| 变异类型 | 例子 | 能证明什么 |
|---|---|---|
| 判据改回旧错误形式 | 后缀匹配 `("3","2")` 改回 `("-3","-2")` | 这条测试真的在测排序，不是碰巧过 |
| 删掉一行关键分支 | 删掉「切换后复验」 | 该分支有被覆盖 |
| 删一个 import | 删 `import re` | 潜伏分支真被走到过 |
| 判据退化成空操作 | 剥离 tracking 参数的 `re.sub` 换成常量 | 该测试在测去重逻辑 |

三条硬规矩：

1. **每个变异单独恢复**。叠着变异时红屏说明不了是哪个测试起的作用。
2. **恢复后必须复跑确认全绿** —— 否则你把变异体留在库里了。
3. **变异没生效比测试失败更危险**。替换字符串没匹配上（缩进/转义不对）时脚本会
   打印「模式没匹配」然后跳过，看起来像通过了。**跳过 ≠ 通过**，必须显式报出来。

## 2. mock 的陷阱：让所有分支走同一条路 ⇒ 零分辨力

最常见的「测试是绿的但没用」。

写「切换后必须复验」的测试时，把探针设成**恒定失败**：

```python
monkeypatch.setattr(m, "_probe_once", lambda *a, **kw: True)   # 切前：通
monkeypatch.setattr(m, "proxy_works", lambda *a, **kw: False)  # 切后：不通
node, _ = m.try_nodes(["A", "B", "C"])
assert node is None          # ✅ 通过
```

它通过了 —— 但**把「切后复验」那一行整个删掉，它照样通过**。
因为两条路径（验了 / 没验）在这个 mock 下表现完全一样，测试分辨不出来。

**正确做法：让探针能区分两条路径。** 用状态化mock 而不是常量：

```python
calls = {"n": 0}
def flaky(*a, **kw):
    calls["n"] += 1
    return calls["n"] == 1        # 只有第一次通
# → 删掉复验那行，node 会变成 "A"，测试变红
```

**判据: 断言的对象要落在「两条路径结果不同」的那个变量上。**
断言一个在两种情况下都相同的值，等于没断言。

反向配套：也要有一条**正向**测试（复验通过就该立刻采用，别一直试到没节点），
否则你会把「永远返回 None」也测成绿的。

## 3. 静默路径也要验：检查器 exit 0 是个读数

一个 watchdog「无输出 / exit 0」有两种可能：**真的干净**，和**它根本没在看**。
输出上完全一样。所以上线前必须验一次哑巴状态：

```
① 正常态           → exit 0、无输出        （确认不会骚扰）
② 注入已知坏状态    → exit 非 0、有输出     （确认不是哑巴）
③ 撤掉注入          → exit 0               （确认没留残留）
```

第②步的注入要**先独立确认注入物确实不利**（自己测一下它真的坏），
否则「注入成功」和「注入了个无害状态」长得一样（同铁律 6 推论 2b）。

三样东西各测一遍：临时文件放对位置（否则被保护目录规则挡掉、压根没触发）、
检查器自己认得这个坏态、撤掉后库恢复干净。

## 4. 规则集选型：先在自己代码库上量每条的命中数

启用一批现成规则前，先按条统计并**逐条看过**，不要整批开或整批关：

```bash
ruff check --select S105 --statistics <root>   # 这条命中几条
```

判据很具体：

- 命中几十条而**绝大多数是本库的设计如此**（脚本调 `subprocess`、绑 `0.0.0.0` 供手机访问、
  用参数化查询）⇒ 这批规则对你是噪音。
- 少数几条即使全是误报，也值得留 —— 真情况出现时它会红。
  **误报用 `# noqa: <code> — 为什么这里安全` 逐处标注，不要删规则。**
  删规则等于放弃未来的信号，标注则保留了「我看过，这里为什么安全」这条知识。
- 规则集本身可能有覆盖洞：实测某条「硬编码密码」规则只认 `password`/`token`/`secret`，
  **不认 `API_KEY`** —— 而后者才是最常泄露的一类。这类洞只能靠拿真样本逐个试出来，
  补一条针对本库命名习惯的正则。

---

## 5. 什么时候做这一步

- 写完一组测试、准备提交前（比事后补省事）。
- 把检查器挂进 cron / CI 之前 —— **自动化一个哑巴检查器，危害大于不自动化**：
  它会一直显示绿灯，让人以为有闸门。
- 检查器报错但你怀疑判据本身错了 —— 变异测试能快速区分
  「代码有 bug」和「判据写错了」。
