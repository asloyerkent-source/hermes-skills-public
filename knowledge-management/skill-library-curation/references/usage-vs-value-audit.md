# 「技能太多/太多没用」的数据支撑审计

用户问「感觉技能很多但真在用的不多」时，**不要凭印象答，要拿数据**；但也别把「数据」直接等同于「该删的」。
本文件给判据和命令。

## 1. 频次分布（先量，不猜）

`use_count` 在 `~/.hermes/skills/.usage.json`，由 `skill_view` 等调用自动更新。**先看分布形状，再谈删除**：

```python
import json, glob, os, time
B = "$HOME/.hermes/skills"
u = json.load(open(f"{B}/.usage.json"))
rows = []
for p in glob.glob(f"{B}/**/SKILL.md", recursive=True):
    d = os.path.dirname(p); n = os.path.basename(d)
    s = u.get(n, {})
    files = [f for f in glob.glob(f"{d}/**/*", recursive=True) if os.path.isfile(f)]
    rows.append(dict(
        name=n, used=s.get("use_count", 0) or 0,
        age=(time.time() - s["last_used_at"])/86400 if s.get("last_used_at") else 999,
        state=s.get("state") or "unset", pinned=bool(s.get("pinned")),
        ns=sum(f.endswith((".py", ".sh", ".js")) for f in files),
        nr=sum(("/references/" in f or "/templates/" in f or "/assets/" in f) for f in files),
        nf=len(files)))
```

分档：`0` / `1-2`（尝鲜）/ `3-10`（偶用）/ `11+`（常用）。

⚠️ **`use_count=0` 不是长尾判据**，见铁律 24 与 `long-tail-inventory-audit.md`。本文件只负责**量出形状**，
「哪些能删」仍由三信号交叉 + 铁律 24/25 的 pinned 过滤决定。

## 2. 「有没有产物」要和「调用多不多」交叉看

单看任一维度都会得出错误结论。交叉表：

| | 有脚本/references | 纯文本 |
|---|---|---|
| **调用多（≥10）** | 正常 | **纪律型技能**，正常——判据类产物天生是文本（铁律 27） |
| **调用少（≤2）** | 待查是不是真需要 | 大概率长尾 |

**纪律型 vs 工具型的判别式**：这个技能的产出是「我读完之后怎么判断」，还是「一个能跑的东西」？
前者零脚本是**正确设计**；后者零脚本是**缺陷**。

## 3. 挖「有产物但没人用」的假工具

分母取**脚本总数**，分子取「`SKILL.md` 正文里从未出现其文件名」的那些：

```python
for f in glob.glob(f"{d}/**/*", recursive=True):
    if f.endswith((".py", ".sh", ".js")):
        mentioned = os.path.basename(f) in open(f"{d}/SKILL.md", encoding="utf-8", errors="replace").read()
```

⚠️ **别把「正文没提」直接等同于死代码**——两种常见误判：

- **`tests/` 目录**：测的是技能内部实现的正确性。技能是**被 agent 当文本读的，不是被执行的**，
  测试目录的体积不换来任何运行时能力。全库唯一带 `tests/` 的技能往往就是体积虚高的大头（实测 54 个测试文件占该技能 37%、22 天零变动）。
- **回退/备用实现**：代码存在、确实会被走到、只是文档没列（铁律 16）。

## 6. 「这些纪律型技能能不能合并」——先并列读内容，再判重叠

问「这么多纪律型技能有必要留吗 / 能合吗」时，**不要用词频或体量当答案**：
按关键词统计跨技能重合度，会把英文停用词（list / name / file / use）排到最前，
**量出来的高频概念全是噪音，对「是否重复」零信息**。

**判据：把每条纪律的「判据对象」列出来，看有没有两条管同一件事。**
实测一次真实判定：13 个中文纪律型技能（探针假阳性 / 机器体检 / 工具退役 / 隧道 / 编排 / 搜索 / MCP / CUDA / 固件…）
看似同质，逐条读后**无一重复**——它们是 13 个不同领域的判据，**合并没有对象**；
真正的重复只有 1 句（用户档案里一句「不信自报完成」vs 循环里 A8 同义），
而另外三条（校准日志有 CLI 统计、验收技能有 `wc -l`/`stat` 命令、测量诚信是元层）**有工具/命令/元层，不重复**。

**结论形态：「N 条里真重复只有 1 句」比「N 条都不重复」更有用**——前者指出了确切的那一处
（去重时只删弱副本，留 `[硬·优先]` 那侧），后者听起来像「什么也不用做」。
**纪律型技能的价值在于触发词各不相同**：合并会让「探针坏了」「工具该退役」这类具体场景失去入口，
而这类入口正是当初拆开的原因。

⚠️ 这类「有没有必要」的问题，同一轮里我连下错三次结论（先说某目录有 15 个副本、再说一个都没有、
再说纪律型该合并），三次都源于凭印象或口径不对，**只有最后一次读了实际内容**。
**所以答案必须来自逐条读正文，不是来自统计口径。**

## 4. 「这个技能其实是个软件包」的识别

第三方引进的技能常带着完整 Python 项目指纹：`pyproject.toml` / `uv.lock` / `tests/` / `eval_history.jsonl` / 自带 `.git`。
识别出来后**先算构成比**：`SKILL.md` 通常只占个位数百分比。

**真正要紧的不是体积，是它还活着没有**——三项一起查：

```python
# ① 依赖装了吗（pyproject 的 optional-dependencies 逐个 import 试）
# ② 有没有定时任务在跑它
# ③ 产出记录最后一条的时间
tail -1 <skill>/eval_history.jsonl
```

**依赖缺失 + 无定时任务 + 产出记录停在过去某天 = 半瘫痪**。这个状态比「体量大」严重得多，
因为 `use_count` 和产出记录都停在过去，**在列表里看上去像还在用**。

处置选项按代价排序：把纯开发期资产（`tests/`、`uv.lock`、给别的 host 看的文档）移到 `skill-backups/`
（技能功能不变，`SKILL.md` + `scripts/` 原地不动）→ 补依赖让它真跑 → 整个归档。**先问用户它还要不要用**，不要替他决定。
⚠️ **归档时清引用必须分类：活指针删，历史记录标注。** 用「行内含该名字就删行」清引用会连带抹掉决策记录——
实测一次归档误删 7 处，其中包含用户自己上次的明确判断（「修，不弃」）与整节重叠分析，
这些是**为何当初这么决定**的唯一记录。**正确做法：① 目标是指针（路径 / 表格行 / `related_skills:` / cron prompt）→ 删或改指向；
② 目标是对它的评价或决策（决策记录 / 重叠分析 / 体检结论）→ 绝不删，在下方加一行
「`<日期>` 已归档：<一句话理由>。备份在 `<路径>`」。删完必须 `git diff` 复核删掉的是什么，
拿不准就 `git checkout` 回滚。**

## 5. 报告纪律

- **报分布，不报结论**：频次分档 + 产物交叉表摆出来，删除建议单独一节并给证据。
- **用户记忆里的旧数字要先验**：像「59 个技能只有 10 个真用」这类外部数字，量完发现与实测差一个量级时，
  **主动说明差异**（例：实测 84 个里 26 个 11+ 次在用、30 个 3-10 次，不是 10 个而是 56 个）。
- **别把「数据不支持」说成「你错了」**：用户的感觉和实测不一致时，先排除**测量口径**问题
  （口径本身已内置字段覆盖，见铁律 25），再给实测。
