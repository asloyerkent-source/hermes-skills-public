# 功能重叠判定 · 外部流程技能取舍

两件事连着：①「这两个技能是不是同一件事」②「外面那个更流行的要不要装」。判据都是**先查本机已有哪一步**。

## 1. 关键词扫重叠 = 得到候选，不是得到结论

对全库按概念关键词（`spec`/`验收标准`/`拆任务`/`依赖图`）扫一遍，能快速缩小范围，但**命中率高得不能用**。

实测一轮：扫 84 个技能，4 个命中「spec 四阶段」，逐个读内容后 **3 个是假阳性**——
假阳性的两种固定形态：
- **词被借用了**：`hermes-cron-ops` 含「验收标准」，但内容是定时任务自愈，跟规格无关；
- **同名不同层**：`agent-communication-discipline` 含「拆任务」，但它讲的是**回复里多条议题怎么分条**，不是把工程拆成任务。

**判据：命中后必须读到那一段的正文，只看 description 不算。** 命中行数 ≥2 才有资格进人工分诊。

## 1.5 估「能砍多少」必须先量，职责名不算证据

给用户的删除/瘦身估算**不能从职责名推**。「手机访问 → 归手机技能管」「备份 → 归备份技能管」
听起来天经地义，**实测往往是错的**：把每条行规范化（去空白与 markdown 符号、滤掉短行）后求
`A & B` 交集，专用技能通常只覆盖伞形的个位数百分比。

实测反例：伞形技能 2136 行去重行，6 个专用技能合计只吃掉 **115 行 = 5%**；
按职责名该砍的「手机访问」195 行实际只被覆盖 3 行 —— 砍掉等于销毁 192 行独家知识，
而且**不可逆**（那些内容只存在于伞形里）。

**动作顺序**：先跑交集测量（几行 Python），拿到百分比再报价；报价里写明「独占 X 行」。
**逐 ref 展开**才知道该动哪个文件——整体 5% 可能全部集中在单个 ref 上（实测 40 个 ref 里
只有 1 个被覆盖 90%，其余全 0~7%），**按整体比例做决策会错杀 39 个**。

判据：**职责名相似度是待验证假设，逐行交集才是证据**；测量结果与估算冲突时，
先撤回估算再动手，并明说「我上一条估错了」。见 §6。

## 2. 该不该合并：先跑「交接测试」

不要用「体量接近 / 目录相邻 / 都提到验证」当合并理由。看**有没有一方明文把某类活交出去**：

- 交了 → **分层，不合**。实测：`execution-discipline` 正文写「多文件、代码生成、>50 LOC → 见 `coding-delegation`」，
  说明它自己把写代码这一步交出去了；而 `coding-delegation` 的「步0 何时可以自己做」表里全是代码类判据，
  对「改配置/部署/连设备」这类活零覆盖。两者是**生命周期 vs 其中一步**，合起来会得到一个没人能用得上的巨型技能。
- 没交、且同一批场景同一套判据 → 才进合并簇（走 `references/root-cause-consolidation-pass.md`）。

**反向信号**：「都讲验证」「都讲先查证」是**主题相邻**，不是职责重叠——每条纪律各自还挂着具体命令
（`wc -l` 对账、`stat mtime`、`--guess`/`stats` 统计、`pi_probe.sh` 探活）时，合并会丢命令。

## 3. 互引检查：单向引用是缺陷

若 A 的正文指向 B（"见 `coding-delegation`"），**必须确认 B 的正文也知道 A 存在**。
单向的情形会让「只在 B 被想起」的场景跳过 A 那一段——A 的入口藏在 A 里，而加载的是 B。

**判据：`grep -c <另一个技能名> <B>/SKILL.md` 为 0 就是单向。** 补法是在 B 的**第一步**加一句前置指针
（「动手前先过 A 的第 N 步」），不要加在末尾的「相关技能」区——放末尾不影响执行顺序。

## 4. 外部流程技能要不要装：先查本机执行链缺哪一步

外部生态里做同一件事的框架（spec-kit / BMAD / superpowers / planning-and-task-breakdown …）体量差两个数量级，
但对本机的价值只取决于**一件事：本机执行链哪一步是空的**。

动作顺序：
1. 列出本机执行链的阶段（本机是 BRIEF→方案→执行→验证→抽查→沉淀）；
2. 逐阶段标覆盖：谁有模板/工具/命令；
3. **只针对空的那一步**去外部框架找对应规则；
4. 把那几条规则**抄进已有执行链的对应阶段**，不装整套框架。

实测结论：四阶段里 SPECIFY 和 IMPLEMENT 本机已有，**只有 TASKS（拆任务+依赖顺序+垂直切片）是空的**，
而填这个空只需要 4 条规则，不需要一个 7 命令的流程框架。

**判据：补一个空阶段，规则条数 ≤10 就抄，>10 且要求用户改变交互方式才考虑装。**

## 4b. 一批外部仓库：先分流，再下载

从榜单/推荐里拿到一批仓库，**先按四条剔掉大半再下载**——下载只看 README 和目录，不跑不装：

| 剔除判据 | 信号 |
|---|---|
| **已有同类能力** | 与库里某技能职责重叠 ⇒ 先量交集（§1.5）再报价，不重复装 |
| **跑不起来的环境** | 需要显示器/GUI 而本机是无头服务器；需付费/授权 |
| **自认不稳定** | README 首行就写 API unstable / early preview / 文档在建 |
| **根本不是技能** | 榜单里的代码库、应用、游戏，不带 `SKILL.md` |

**但先看一眼它是不是「书 + 自带技能」——那会改变分流结论。**
有些项目本体是书/教程，**却在仓库里自带 `skills/` 目录**（每个子目录一份 `SKILL.md`）。
它看起来不像「技能包」，于是被「根本不是技能」那条直接剔掉 —— 而实际上里面的技能是逐份读过、
可逐份挑选搬进库的粒度。实测一个 5 万星的中文 agent 书仓，顶层 40 个目录里混着
`skills/`（21 份）+ 14 个语言译本 + 每章的配套代码目录。

**动作**：分流时先列顶层目录找 `skills/`，找到就走「逐份读、逐份判定搬不搬」，而不是整批剔。
**判据：仓库里有什么东西该被单独评估，看目录结构，不看项目自我描述。**

**⚠️ 对着外部技能库做覆盖度比对时，关键词交集只是候选清单。** 实测一轮用关键词把 21 份技能
判成「11 份已有对应 / 10 份无对应」，而人工读正文发现匹配大量错位（把一个工具名当成一个技能、
把变量名当成能力）。**判据：任何「覆盖率 N/M」的匹配结果，先随机抽 3 对读正文确认匹配是真的再报那个数。**
没对上通常不是「缺能力」而是「词选错了」——两库谈同一件事时用词可以完全不同。

**落点纪律：克隆到 `~/.hermes/cache/scratch/<批名>/` 看，不直接放进技能库。** 放进去就进索引、进 git、被审计器扫；
看完能删。scratch 空闲 24h 自动清理。读完只报「增量/重复/不可用」三档结论，不当场装。

**判据：星数不是采用理由。** 一整页推荐里通常只有一两个是技能，其余是代码库——先数「几个真的带 SKILL.md」。
**一条有用的判据**：同一个话题连着出现多张同系列图（如编号 02/08~06/08 的系列海报），
那是**内容系列不是项目清单**，整批同质，一次读一张就能判定归属，别逐张OCR/逐张实读。

### 4b-1. 分流已经说了「只看 README 和目录」——那就别做全量克隆

只读 README/目录却下整个仓库，是把「不装」和「不下载」混为一谈。实测一批 5 个仓库浅克隆
`--depth 1` 仍是 **267MB**，拆开看：**82MB 是 `.git`（30%），189MB 是内容**，
其中绝大部分与判断无关——`website-docs/` 44M、`docs/` 23M+18M、`internal/` 28M、前端源码 15M。
真正被读到的只有各仓库的 README 和 `docs/routing_algorithms/*.md`（几百 KB）。

机制：`--depth 1` 只裁历史，不裁工作区；体积大头是**当前那一个 commit 里的文档站与前端产物**，浅克隆一点没裁掉。

**动作顺序**：
1. 先用 **GitHub API** 读元数据与目录（命令见下），**零字节下载**就能跑完四条剔除判据里的三条。
   ⚠️ **不要用 `web_extract` 打 `github.com/<repo>`** —— 它返回的是登录提示 + JS 壳，正文为空；
   `raw.githubusercontent.com` 也可能返回空而文件其实有内容。**两者都不是可靠读数通道。**

   ```bash
   # 元数据：星数 / license / pushed_at / 是否归档 —— 权威
   curl -sS -H 'Accept: application/vnd.github+json' \
     https://api.github.com/repos/<owner>/<repo>

   # 目录清单（含 type/name/size，子目录要一层层取）
   curl -sS https://api.github.com/repos/<owner>/<repo>/contents/<path>

   # 读文件：contents 返回 base64 的 content 字段
   #   raw 为空而 API 说 size=9KB ⇒ 走这条，别断定「文件是空的」
   curl -sS https://api.github.com/repos/<owner>/<repo>/contents/<path>/SKILL.md \
     | python3 -c "import json,base64,sys;print(base64.b64decode(json.load(sys.stdin)['content']).decode())"
   ```

   ⚠️ **搜索结果里的仓库名一律未经验证。** 实测一轮批量选型中，搜索给出的
   `mutmut/mutmut`、`David-OConnor/skill-validator` 在 API 下全是 `Not Found`
   —— 而它们与真实仓库**并列出现、看起来完全正常**。
   判据：**「这个仓库存在吗」是本机一条 API 调用的事，搜索给的是存在性未验证的候选。**
   把名字当已确认事实往下走（去比较、去算差），整段结论就建在流沙上。

2. 剩下确实要看代码/文档的，`git clone --depth 1 --filter=blob:none --sparse` + `git sparse-checkout set <具体目录>`，
   或直接用上面的 contents API 取那几份文件。
3. 只有确认要长期引用（要跑、要抄代码）才留完整克隆。

**判据：下载量应当与「预计要读的字数」成同量级。** 读 3000 字而下了 267MB，说明分流没真做。
事后回收要一次性做完（5 个仓库 + 267MB 一次清完，别留半个），但**抄走的东西要先落地再删源**。

## 4c. 用互斥描述“消撞车”会把该合并的问题变成两条路由

报告说「两个技能疑似同一产物」时，**先验是否已经合并过**：一方 `references/` 里的文件
开头写着「合并来源：<另一方名>」就是**已并入的孤儿**，该做的是查独有内容 → 搬 → 归档，
而不是给它俩各加一句「非 X」当边界。

**加互斥描述当消撞车手段，只有在两者职责确实不同、无法合并时才对。** 用在「其实已合并」上，
后果是：① 两份内容继续各自漂移 ② 索引里多一条永久重叠的路由信号 ③ 审计器下一轮开始
「解释你上轮为什么那么写」——**这是修法掩盖根因的指纹**。

**动手前一步**：`grep -rn '合并来源\|来源：\|由.*合并' <候选>/references/`。

## 5. 抄回来的规则（垂直切片类）

来源化的四条，落在「BRIEF 之后、执行之前」，且注明单文件小改动跳过：

```
依赖图：实施顺序 = 依赖图自底向上，先地基后上层。
垂直切片：每个任务自身可运行、可测试、可独立交付。
  ❌ 横：写完整个 schema → 写完全部 API → 写完全部 UI → 联调
  ✅ 竖：能注册（schema+API+UI 全通）→ 能登录 → …
任务四要素：做什么 / 依赖谁 / 完成判据（可跑命令）/ 产出文件。
```
## 6. 删一个被别的技能覆盖的 ref：先验「独有内容」真的在那边

源技能自带的「已知遗留」常写着「ref 里还有 N 行独有规则，两边都要看」。
**那是当年写的，不是当下的事实** —— 目标技能此后又长过内容，那几行很可能已被吸收。
不验就删，等于用一段过期注记决定删 100+ 行。

删前必做两步：
1. **验文件在位**：注记点名的每个 `references/*.md` / `scripts/*` 用 `os.path.exists` 查，
   并核大小（文件被清空成 0B 也算不在位）。
2. **验那几条规则逐字在目标技能里**：按关键词（规则名 + 关键实体）搜，要看到**规则本身那行**，
   不是只有文件名引用。

实测：注记说「独有两条规则只有 ref 里有」，实测两条**逐字都在活动技能的 SKILL.md 里**，
ref 确为纯子集才敢删。若独有内容**仍在**，正确动作是把那几行**补进目标技能**再删 ref，
而不是保留两份副本。

⚠️ 删除标记本身要避开 lint：写「已删除」时**别把失效路径包在反引号里**
（`` `references/xxx.md` ``），引用扫描器只认反引号格式，会被判成断链。
用 `~~references/xxx.md~~（已删除）` 这种不带反引号的写法。

## 7. 「横着拆」的前三个任务**无法验收**——没法说做完了，只能等全做完才知道对不对。这是不对称的真实代价，不是风格偏好。

## 8. 审稿报告先验真伪与危害量级，再动手

报告里混着三种子类，**「报了 high」不等于「改对了方向」**：

- **真缺陷但危害被夸大**：报「元数据被吞进嵌套节点导致功能失效」——实测前后解析出的键完全相同
  （那本来就是该字段该待的位置）。**缩进确实该修，危害不是它说的那样**；照它的定性下手，
  会顺手重构一堆根本没坏的东西。
- **真缺陷但修法是错的**：报「某触发词正文搜不到」——是自己检索词写错了，它其实在正文里。**先自己 grep 一遍。**
- **修法本身制造了下一轮的问题**：见 §4c。
- **修法没错，但交付话术夸大**：机制正确落地了，标题写「已用起来」而插件根本不读那段配置。
  独立审稿人抓的是这条。**处置**见下方§8d。

**动作**：每条 → ① 自己 grep / 读源码复核 → ② 分清「真缺陷 / 危害夸大 / 修法错误」→ ③ 只改真缺陷，
改完用**独立于本轮工具**的方式回验。**三个审计器同源时尤其危险**：它们共享同一套前提错误，会一起全绿
（实测 yaml 校验器一路绿灯，而实际加载器解析失败——见铁律 14a）。

### 8b. 「多派几个审稿人」不等于换模型——先确认它们真的是不同模型

同源审稿轮次增多**不会**提高独立性，只会让同一个错误前提被重复确认 N遍（本机skill 审计实测：
三轮同模型共报 63 条、全部低价值；第四轮换模型第一件事就挖出前三轮都漏的真缺陷）。

**派之前必须验身份，不能靠任务描述里的措辞**：

| 想表达 | 实际发生 |
|---|---|
| 「你是第二个模型，换个视角审」 | 子代理固定走 `config.yaml` 的 `delegation.model/provider` |
| 派两个「不同模型」的审稿人 | 返回的是**同一个模型**两份输出 |

**动作**：`delegate_task` 无 per-task 模型参数 ⇒ 真要换模型走 CLI：
`hermes chat -q <完整输入> -Q --provider <p> -m <model> > out.txt`。输入写成文件再读入 prompt（几万字的审稿材料不要硬拼进命令行）。
**换之前先探活**每个候选（`hermes chat -q "只回复两个字：可用" -Q --provider X -m Y`）——
「某模型欠费/不可用」是快照不是事实，本机一条欠费旧账早已作废。

**收口判据**：审稿模型报出的新缺陷若**都能被前几轮报告解释掉**，说明它在自己给自己圆场，不是独立审查。
见到这种收敛就换模型，别加轮次。

### 8c. 从外部仓库「抄一条规则」之前，先验它在本机是不是真缺口

外部项目的机制文档写得比本机技能完整得多，容易把「写得细」误读成「我们缺」。

**动作**：`grep -c '<机制关键词>' <本机相关技能目录>` —— 实测三道闸门（回退/作用域/流量）
在两个最该有的技能里命中数**均为 0**，那才是缺口。
抄之前先把「谁负责、现有没有」查实，比读三页外部文档快。

⚠️ **「查了 0 次」只在你查的那一个组件上成立—— 先枚举同域兄弟组件再下缺口结论。**
本机同一个问题常有两套实现并存，而**各自的覆盖面不同**。实测：抄「跑得好不好→调档」这条机制前，
只 grep 了名字里带 router 的那一个插件（`streak=0 · 连续=0 · 降档=0`），写成「本机没有反馈闭环」；
而同目录另有一个插件**早就实现了同类闭环**（连续 N 次工具错误升一档、每回合只升一次防乒乓、
回合末自动降回base tier、用户手动 pin 时不升）。**缺口结论错了，方向也跟着错。**
**动作**：`ls <该类目录>/` 把同域组件全列出来再 grep，且**结论必须写限定语**——
「`<A>` 没有 `<X>`」成立；「本机没有 `<X>`」要先把兄弟组件都查过。
⚠️ 同一节也要防反向：**说「某能力覆盖为 0」时，先核自己选的检索词**。实测声称
「回退闸覆盖为 0」，实际另一个技能的正文里就有现成的 Rollback 段落 —— 真问题不是「没人写过」，
而是「造环时没人主动想起来用」，**这两种诊断的修法完全不同**。

⚠️ **抄的是规则不是外壳**：外部机制带一整套为它的场景设计的周边（代码库控制环、评测数据集、中文分词）。
只取能在本机落地的那几条，用本机既有的技能/配置当落点，**别新建技能也别新装包**。
配好之后还要跑一次真实加载验证（本机实测：往插件配置里加一段它不认的键，先 `importlib` 加载一遍确认不崩）。

### 8e. 扫外部仓库前先分流：多张同系列图不是项目清单

同一话题连着出现多张同系列图（如编号 02/08~06/08 的系列海报），那是**内容系列不是项目清单**，
整批同质 —— 一次读一张就能判定归属，别逐张实读/逐张 OCR。
**这属于 `safe-file-organization` §Pitfalls 的「凭据类 vs 缓存类」同一判断**：
先判「这一堆东西是什么类别」，再决定逐个处理还是整批判定。清单里有几条是项目、有几条是系列，
是同一类错误的两面。

### 8f. 借鉴落地后交付：「文件在」≠「机制生效」

一轮外部借鉴抄三处，提交前自查全绿：三个 ref 文件都在磁盘、三个父技能正文都引用了、配置也写了。
**独立审稿人第一句就指出：配置那段插件从不读（grep 命中 0），而汇报标题写的是「已用起来」**——
文件层面成立、机制层零生效，两件事被合并成了一句。

**三层交付面，各自验、各自说**：
1. **文件层**：文件存在 + 父 SKILL.md 真引用（非只在「相关技能」区）—— `os.path.exists` + `grep -c`。
2. **机制层**：**改到配置/代码里的东西有没有消费方**——`grep -c '<新键名>' <消费者实现>`。读到 0 就是惰性数据。
3. **行为层**：真跑一次（`importlib` 加载插件/脚本执行），而不只是配置能解析。

**汇报纪律**：任何一层没到，就写「文件已落地，机制未生效，改动路径是X」，
**不用「已用起来/已生效」这种跨层断言**。⚠️ 讽刺的是这类夸大往往紧跟在一句诚实的
「⚠️ 如实说：插件不读它」之后 —— **caveat 写了就等于说过，别让标题把它抵消掉**。

**惰性配置段比不写更糟——删掉它，不要只加「未启用」注释。** 未知顶层键被`_deep_merge`
原样并入且无消费者，但它**与真正生效的字段并排呈现**，读者会以为已开启。正确处置是
**移除该段+ 在注释里指向真正负责的那个组件**，并让配置与文档对当前状态说同一句话。

**抄上游时要连「等级」和「数目」一起抄**，二者本身就是信息：
- **等级**：上游写 "offer it; not every loop needs one"，落进本机正文变成「必须有三道闸」——
而自己抄的 ref 里还留着「不是每个循环都要」的口子，**正文与自己的 ref 互相矛盾**。
- **数目**：标题写「四个防抖参数」而表里只有三个（上游原文是 "three base settings"，
  且只有其中一个被称作 cost dial）。**抄完对一遍数目与措辞**，否则文档内部就已经不自洽。
