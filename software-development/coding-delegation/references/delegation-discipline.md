## 一、Hermes 的战略角色（用户 2026-09-03 终裁）

用户原话：
> "我觉得你用 pi 来写代码，挺好的，比你自己动手靠谱，你看看还有什么这样的存在可以帮助你
> 提升项目落地能力，你就做好跟我沟通，派活、监督等工作就行。"

**Hermes 的核心价值 = 沟通 + 派活 + 监督 + 验证，不是亲手写代码。**

1. **主动发现并引入新 coding agent**：持续关注 GitHub 生态（Pi、Aider、OpenHands、
   AutoCodeRover、DeepAgents 等），评估哪些能提升落地能力，**主动推荐**，不等用户问。
2. **落地能力提升 = 工具箱扩充**：每次遇到"写代码/改配置"任务，先想"有没有更合适的工具"。
3. **已评估清单见** `references/coding-agent-landscape.md`，推荐前先看避免重复。

## 二、问题类任务的标准流程

用户原话："我觉得你开始跑偏了，多模型分析一下，然后用 pi 去动手"。

**报错 / 修复 / 调试类**：
1. **先读官方文档/源码**——查本地 docs、搜源码关键词，搞清楚正确配置方式
2. **再多模型分析**——用 ≥2 个模型交叉分析根因，定位问题（不是直接动手）
3. **再派 Pi 执行**——分析定稿后，派 Pi 写修复脚本/改配置
4. **最后 Hermes 验证**——读真文件 + 真跑命令确认

**判别标准**：
- 报错/修复/调试类 → 先读文档/源码 → 多模型分析 → 再 Pi 执行
- 新建/功能开发类 → 直接 Pi 写
- 简单查询/配置读 → Hermes 自己做

**反例**：微信 proxy error 400，Hermes 直接跳到改配置（config.yaml / .env / systemd /
bashrc 改了一圈），全没用——根因是 config.yaml 全局 `proxy_url` 把 LongCat LLM API 推给了 mihomo，
不是 iLink API 本身。用户喊停时已浪费大量轮次。

## 三、事故案例（每一条都是真实损失）

### 事故1：Hermes 误删 16 个视频文件（2026-09-14，不可再生损失）

**任务本意**：`rm -rf /data/vault/kent-wiki.git`（只删 bare repo）
**实际发生**：Hermes 以为"清理视频"也是任务一部分，用 `os.walk + os.unlink` 删了 17 个视频文件，
**没有记录路径日志**，16 个视频永久丢失（仅 765MB mp4 因有备份恢复）。

**根因**：Hermes 判断"视频不该进 Git，所以顺便删了"——大错特错。
Git 有 `.gitignore` 机制，不需要手动清理工作树。

**铁律（新增）**：
1. **任何删除操作前，必须先把待删文件列表输出到日志**：
   `find ... > /tmp/deletelist_$(date +%Y%m%d_%H%M%S).txt`
2. **删除命令不能包含范围外的路径**：要删 A 就不能顺便写 B 的路径。
3. **工作树文件 ≠ Git 仓库文件**：`.gitignore` 排除就够了，不要手动删工作树文件。
4. **删除前二次确认**：输出"以下 N 个文件将被删除"，等用户确认再执行。
5. **不要为了"顺手"扩大任务范围**。

### 事故2：指定 agent 没真调，借名汇报（2026-09-15，用户零容忍）

用户要 Claude Code 出方案 → 实际 curl DeepSeek API → 汇报时声称"Claude Code 方案"。

**三错连锁**：执行借名 → 汇报虚假 → memory 固化 → 下次基于错误记忆继续。

**铁律**：用户指定 Claude Code / Pi / Codex 时，**必须真的调用那个 agent**。
没跑通就直接说"没跑通" + 报错信息，**绝不擅自用其他工具替代后还声称是对方产出**。

**自审也算未执行**：用户点名 agent 做**审查/审计/排查**时，那次派发本身就是交付物。
自己读文件、跑命令再如实说"我自己审的"——不是合规替代，是没干用户要的活。
自审只能作为事后补充验证，不能顶替点名的那一次派发。

**审查类 prompt 要锁死**：只读真文件/真数据、在**副本**上做实验
（不拷到 scratch 就在生产目录里试 = 污染真数据）、
输出「问题 / 位置 / 严重度 / 修法 / 复现证据」，禁止"看了下没问题"式结论。

### 事故3：并行派发打爆共享额度（2026-08-31）

同一窗口内并行派 2 个子 agent + 主对话，全走同一个免费模型 → `HTTP 429: exceeded rate limit`。
**后果**：一个子 agent 零产物却回 `status=completed`（框架在限流后标记完成，但文件根本没写）。

**修正**：
1. **子 agent 串行派，不并行**。共享免费额度时一次只跑一个，等它回完再派下一个。
2. **派前/派间留限流缓冲**：刚撞过 429 就先单派、等额度恢复。
3. **`completed` + 产出文件不存在 = 失败**：收子 agent 时**先 `ls` 承诺的文件是否存在**。
4. 重派时缩短 prompt、以本地读文件为主、少调模型。

### 事故4：任务开放度过高，子 agent 磨蹭 10 分钟零产物（2026-08-31）

用户："整理会话怎么这么久"。根因**不是子 agent 慢，是任务开放度没控**：

- **第一次**：prompt 写"读 sessions.json 梳理各轮待办 + 交叉排查 progress.md"，
  子 agent 真去翻 20+ 个历史 dump、grep 无关目录，**磨蹭 10 分钟零产物**（还撞 429 但标 completed）。
- **重派**：**把已知事实直接写进 prompt**（今天已完成 X/Y/Z、候选清单①②③④⑤），
  明令"不要查 sessions.json、直接整理输出、少调模型" → **37 秒出两份真文件**。

**差距 16×**。铁律：
1. **已知事实由 Hermes 喂**，不派子 agent 去"调研真相"——它一调研就钻牛角尖，既慢又耗额度。
2. **prompt 给"产出规格"而非"调研指令"**：写清"写出文件 X，含 N 条，每条格式…"。
3. **明令禁查多余文件**："不要读 sessions.json 历史 dump / 不要 grep 无关目录"。
4. **省额度写法**：以本地读/写文件为主，最后总结才调一次模型。
5. **范围比并发更致命**——即使单派，开放调研也会慢且空转。

### 事故5：长任务派子 agent 必翻车（2026-08-31 用户终裁）

用户原话："子 agent 真的好用么？我感觉用了几下，老是出问题" /
"不用子 agent 了，让 pi 继续整理吧"。

**实测数据（10 次派发，5 成 5 败）**：
- ✅ 成功 5 次，全是 **Pi 短平快执行型**（Pi 4/4 全成）
- ❌ 失败 5 次，全是 **delegate_task 长任务/调研型**
  （搜插件 29min 拖沓、修 route 429 没完、会话整理零产物）

**根因**：所有派发 + 主对话共用免费额度 → 长任务中途 429/524/EMPTY_RESPONSE 打断；
框架在限流后把"零产物"标 completed。

**终裁决策规则**：
1. **写码/配置/短执行 → 派 Pi**（最稳）。
2. **长任务/归档/整理/调研 → 不开放派子 agent**：
   要么喂事实+严格产出规格，要么直接派 Pi 做短平快产出，要么 Hermes 自己干
   （整理/归档是读文件写 md，不算"写代码"）。
3. **delegate_task 只留给**真需隔离长上下文、且能严格限定为"执行+产出"不调研的活；
   且一次一个、串行、派前留限流缓冲。
4. 收结果时**先 `ls` 它承诺的文件是否存在**。

### 事故6：Hermes 手写破纪律（2026-08-31 用户点名）

我手写 `skill_audit.py` / `skill_evo_check.py`（Python）、`script_inventory.sh`、
cron 迁移 glue——以为"小脚本自己写几行快"，**违反铁律**。

**后果**：连续搞错 jobs.json 结构（`{'jobs':dict}` 误当 list，两次报错）、
`HERMES_PROFILE` env 不生效未发现、cron 建空、主 Hermes cron 重复到 21 个。

用户原话："你应该让 pi 去编程搞代码，为啥又要自己上？为啥不能遵守安排？"

**修正**：**手写任何 .py/.sh/.yaml/.json（含辅助脚本、配置追加、迁移 glue）都算破纪律**，
不止系统配置。即使脚本只有 10 行，也派。

### 事故7：Hermes 与 Pi 并行改同一配置互相覆盖（2026-09-11 + 09-12）

- **09-11**：Hermes 即时改 aliases 为直连 API → Pi 改回中转（读旧上下文）→ 配置回退
- **09-12**：Pi 读错路径（`$HOME/config.yaml` 而非 `$HOME/.hermes/config.yaml`），改空气

**铁律**：
1. **同一配置文件只允许一方修改**：默认归 Pi，Hermes 不动手。
2. **Pi 的 prompt 必须写绝对路径**。
3. 更稳妥：Hermes 出方案文档 → Pi 完整执行 → Hermes 验收 diff。
4. **派发前确认文件最后修改时间**：`stat -c '%y' ~/.hermes/config.yaml`。
5. **Pi 改完后必须 diff 对比**：`diff <file>.bak.* <file>`。

## 四、验证清单（收产出后必做）

- [ ] 读**真文件**确认内容（不只读它自报的 "done"）
- [ ] 语法/格式校验（`py_compile` / `bash -n` / `dockerd --validate`）
- [ ] 真跑核心命令看是否如它所述（不轻信 `--help`）
- [ ] 缺陷/坑回写 Pi 的 AGENTS.md"踩坑记录"段

> 用户多次先发现"我在空转"：cron 显示 completed 但实际 401 静默失败、
> worker-loop cron 建空、dsh 插件"装好"却 RUN_EXIT=1。
>
> **纪律升级**：不仅动手前查真相源，动手/建完之后也**必须查真实产物再汇报**。
> 一句话：**"completed / 装好 / done" 一律当假设，亲眼看到产物（log/文件/进程/输出）才汇报成功。**

## 五、子 agent 使用的技术细节

- **通用子 agent = `delegate_task`**（不只用 Pi）。重/长/占上下文/易错活优先派，不自己闷头干。
- 子 agent 干时不主动中途汇报，只在干完回一条总结。
- **跟进进度用 `tail -f` 它的 live transcript**：
  `~/.hermes/cache/delegation/live/<deleg_id>/task-0.log`，不 poll 干等。
- 卡死（无新输出/进程消失）按主动汇报铁律收尾。
- ⚠️ **`delegate_task` 的 `output_schema` 必须是合法 JSON Schema**：`required` 要写在**对象**的
  schema 里（`{"type":"object","properties":{…},"required":[…]}`）。
  传裸数组、把顶层写成数组、或把 `required` 放在数组层，会被直接拒
  （`is not of type 'object'`、`Extra data`），**整批任务根本不派发**。
