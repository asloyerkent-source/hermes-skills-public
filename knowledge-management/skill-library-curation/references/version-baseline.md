# 技能库版本基线与大改纪律

> 回答「我要作为版本记录」「大改 skill 怕改到面目全非」时走这条。
> 与 `references/publishing-preflight.md` 互补：那条管**传出去别泄露**，这条管**改之前能回滚**。

## 前提：大改前必须有回滚手段

用户明确说自己「很喜欢大改 skill，很容易改到面目全非」，并要求「作为版本记录」。
所以 **`skills/` 没有版本控制时，任何结构性改动都不该开工**——不是因为危险，
是因为改坏了只能靠记忆复原，而记忆复原不了散在十几个文件里的措辞。

开工顺序（不可颠倒）：

```bash
cd ~/.hermes/skills
# 1. 先建仓（此时工作区干净，不会把旧垃圾一起收进去）
git init -q
git config user.name "<名字>" && git config user.email "<邮箱>"

# 2. 写 .gitignore —— 每条排除项都带一句「为什么排」
#    排除清单与判据见 publishing-preflight.md §排除项要写进 .gitignore

# 3. 先提交基线：记录「改之前长什么样」
git add -A && git commit -m "chore: 技能库纳入 git（首次基线，非功能变更）"

# 4. 之后才动刀
```

**首次提交必须写成「基线」而不是「功能」**——它的信息价值全在「此刻的状态」，
写成「新增 XX 功能」会让人误以为可以从这里回滚功能。

⚠️ **`git commit` 可能被安全审批拦住。** 真实发生过：批量 `git add` 已暂存，
`git commit` 因未及时确认而被拒，暂存区内容保留。**此时该说「提交未执行」而不是「已建仓」**——
暂存 ≠ 提交，后者才有基线。

## 量「面目全非」

```bash
cd ~/.hermes/skills
# 历史修改日志的密度（中招则 ≥3）
grep -cE '^#{2,4}.*(修复要点|本轮|第[一二三四五六七八九十]+轮|已修|踩坑记录)' <skill>/SKILL.md
# 正文行数基线
find . -name SKILL.md -not -path './.archive/*' -exec wc -l {} + | sort -rn | head
```

实测 84 个技能里只有 2 个命中（≥3 处），但其中最大的 318 行里塞了 17 段
`P0 修复要点` / `P1/P2 修复要点（本轮）` / `P4 决策记录`。
症状不是文件长，而是**文档变成了修改日志**：读者要先读完几轮历史 bug 修复史，才知道现在该怎么跑。

**判定与处置**

| 命中数 | 处置 |
|---|---|
| 0–1 | 正常。保留 1–2 段有价值的历史（往往是「踩过的坑」），不动 |
| **≥3** | **中招**。新规则进正文；历史每段压成一行 + 指向 `git log`；正文设行数上限（如 200 行），超了强制压缩 |
| 大量且文件超大 | 大概率是 union merge 只跑了内容 pass 没跑结构 pass——**先查拼接指纹**（`structural-health-checks.md`），别当历史问题处理 |

⚠️ **别把「历史」和「冗余」混为一谈。** 实测超标技能的文件内重复段落 0 条、历史类占比 2%，
看着干净——但那只是**没人给它加过修改日志**，不是结构健康。
反过来，被反复修过的技能历史占比会高，但那些历史段落内部**没有重复**，是纯增量。
所以砍内容（治冗余）和压历史（治日志化）是**两套动作**，先分清是哪一个。

## 怎么压：删历史段的正确顺序

压历史不是删段落，**是重写指向它们的所有引用**。直接删会在正文里留下悬空锚点。

```bash
# 1. 先定位要压的区间（用标题定位，别按行号硬切）
grep -nE '^#{2,4} ' <skill>/SKILL.md

# 2. 压之前先查：别处有多少处指向这些段
grep -nE 'P[0-9](-[0-9])?|（P[0-9]' <skill>/SKILL.md
```

**压缩后的四件事，一件不能少：**

| 步骤 | 做法 | 漏了会怎样 |
|---|---|---|
| **新规则进正文** | 把每轮的**结论**（不是过程）提成一个不变量 / 一条规则 | 压完等于丢知识 |
| **历史压成一行** | 表格形式：轮次 → 治的病 → 一句话结论 | 文档仍是修改日志 |
| **指向 git log** | 正文写明「完整缺陷表/复现命令在提交历史里」 | 下一个人找不到为什么这么写 |
| **修掉悬空引用** | 步骤 2 查出的每处 `（P4-1）` 改成描述性文字或指向新的不变量 | 读者按图索骥找不到东西 |

⚠️ **压缩后必跑一遍自检**（本技能自己的体检会报，但先自查更快）：

```bash
# 悬空编号：还提到 P0-1..P5 但正文已无对应小节
grep -nE 'P[0-9](-[0-9])?' <skill>/SKILL.md
# 文档里写的命令是不是真能跑
grep -oE 'scripts/[a-z_]+\.py' <skill>/SKILL.md | sort -u   # 逐个存在性 + --help
# 重复的支持文件条目（多轮追加会积）
grep -nE '^- `scripts/' <skill>/SKILL.md | sort -t: -k3 | uniq -c -f2
```

**验收别只看行数。** 压完重跑该技能自己的自测/验收命令，
**并确认文档里列出的每个脚本都存在且能跑**——压缩时最容易顺手删掉一条仍然有效的验收命令。

## 每次大改之后

1. `git diff --stat` 看一眼真实改动面——**比脑内的「大改」可信**
2. 跑 `skill_ref_lint.py --skill <名>` 单查断链（铁律 11）
3. 历史段数复查（上面的 grep），≥3 就当场压，别攒到下次
4. 提交时**只写本轮做了什么**，不写「顺便清理」——混在一起的提交无法单独回滚

## 与合并的关系

合并流水线（见 `merge-execution-discipline.md`）里，「备份先于删除」是临时备份；
**版本基线是长期可查的记录**。两者不是一回事：备份只保证这一轮能退，
版本控制保证三个月后还能 diff 出「当时到底改了什么」。

已经建了 git 的技能库，合并时优先用 `git diff` 看改动面，而不是重新通读两个版本。
