### 档3 ｜方案级双模型验证（拍板前）
**定义**（user 2026-08-14 硬纪律, 超出审案）：任何全面落地方案(部署/架构/设备接管)须 ≥2 模型交叉验证(HY3+DeepSeek 或 DS+GLM)再定稿, 禁单模型拍板。不止交付物审查, 动手前的方案本身必须双模型交叉。全文见「用户铁律」章的方案级双模型验证块。

**方案级审核必须审「逻辑死循环 / 触发前提」（2026-08-19 用户两次补刀, 多模型审都没抓到）**：
- **用户两次点破方案自相矛盾, 两模型均未抓全**: ①v1写"3046失联→SSH让3046喊"=死循环(3046死了SSH不通) ②L3原写AX6S兜底, 用户指出3046↔台式本就双向, 3046自身可反探台式报失联, 无需AX6S。
- **铁律: 多模型审方案时, 除审技术选型/命令正确性, 必须专门审「触发链路前提是否成立」+「有无逻辑死循环/单点故障」**。具体问模型: "这个方案里每个动作的前提, 在它要解决的场景下是否成立? 有没有A依赖B但B正是出问题的那方?"
- **agent 不自下结论, 但要多模型审时把"找逻辑漏洞"显式写进 prompt**(不要只问"有没有bug")。本次用户原话:"你的方案经常落不了地" → 根因多在逻辑前提错, 非语法错。
- **现成软件优先, 禁止自己造轮子(2026-08-19 用户强纠正)**: 用户原话"为啥不先推荐现成软件, 非要自己做一套" + "尽量用现成的架构, 跑起来再优化, 少返工"。落地任何监控/出声/媒体/备份/智能家居需求, **先搜现成软件(Kuma/HA/Jellyfin/Syncthing/btrbk等)当骨架, 赫米只做现成干不了的(物理通道/胶水/多模型审)**。赫米默认"写脚本解决"的惯性必须压住——先问"这事现成软件能不能干"。
- **插件化防臃肿 = 真不装没用的, 不是拆细分换皮(2026-08-19 DS审计抓出)**: 若把 Kuma 拆成 http/tcp/ssl 三个"插件"反而多开进程, 8G内存更紧。真正防臃肿 = 无依赖不装 + 按需启动 + 赫米维护一张启用清单(homelab-composition.yml 式)一眼看清跑什么。对齐 DS Harness 只借"trigger/action 清单"理念, **不照搬编排框架(过度设计, 管理成本>收益)**。
- **赫米优化边界**: 读运行指标→提"删/降/加"建议→**用户拍板才改**(不自动改 yaml, 防失控/改错禁了监控)。

**落地前锁死「调查→方案→真多模型审→拍板→动手」（2026-08-19 会话强化）**：
用户本次硬纠正(原话: "你先好好调查，做方案，然后多模型审核修改，给我看下，再开始干，你的方案经常落不了地...不要盲目" / "我要用deepseek，跟glm来审核，你自己审核的视角不够全面" / "调用多模型审核技能")。提炼为不可跳过的顺序:
1. **只读调查**: 只查事实(命令/文件/API探测), **不写任何部署文件**, 不中途动手。
2. **写方案草稿到 .md**(非 chat 输出), 含架构+加固项+铁律对齐。
3. **真·多模型交叉**: GLM(深化) + DeepSeek(审计) 直连官方。 **禁止把单模型(含 hy3 多实例)自查标成"多模型审核"** —— 用户明确点名此误导(原话"你自己审核的视角不够全面")。
4. **贴给用户过目**, 等拍板, **绝不在此之前部署**。

**诊断/根因也须多模型验证 (GLM优先, 2026-08-16 强化)**：
- user 原话: "你的诊断再多模型看看，不要盲目下判断，glm优先" + 之前误把"移动大内网"当成虚拟网卡(实际是移动宽带CGNAT无公网IP)。
- **铁律: 下根因判断前, 先抓真实证据, 再喂 GLM(优先)+DeepSeek 审, 让模型结论, 不要 agent 自己定性。**
- **网络/代理诊断优先于任何代码级排查**: 当外部 API 调用失败或模型下载失败时，不要先假设"无外网"。先用 `curl -sI --noproxy '*' https://目标` 和 `curl -sI -x http://127.0.0.1:7890 https://目标` 对比直连 vs 代理。3046 的 Clash (mihomo) 可能未启动、7890 无监听、或 `HTTP_PROXY` 变量指向了不可达的代理。DNS 解析成功 ≠ 网络通，代理路径断裂是最常见的"假断网"原因。确认网络通后，再排查 Python 层的代理继承问题（unset 环境变量或 `proxies={}`）。
- 执行模式: ① 命令抓实测数据(进程/端口/路由表/网卡/代理/DNS)存事实清单 ② 把事实(非推测)喂 GLM主审+DS复核, 明示"不要臆测, 基于实测" ③ 汇总模型结论, agent 不自下结论。
- 此条比"方案级"更宽: 根因诊断也算。误判根因(如把运营商CGNAT当虚拟网卡)会浪费后续所有动作。
- **命令循环即停 (用户 2026-08-18 纠正原话: "多模型分析判断下，不要这样一直刷屏了")**: 若同一类命令(如反复 `hermes serve` 仍 `address already in use`、adb 引号嵌套报错)重试 ≥3 次仍卡同一错误, **立刻停手所有终端调用**。先把已抓的实测事实列成清单(进程/端口/路由/权限/路径), 喂 GLM(优先)+DeepSeek 做根因判断, 让模型下结论, 再动手。刷屏式连发命令既不 progress 又直接惹用户反感——用户要的是"多模型判断"不是"多命令试探"。agent 不自下结论。
- 详见 `references/diagnose_verify.md`。

**脚本/改动落地前须先实跑验证 (2026-08-16 用户: "③⑤ 脚本审核过吗？别又一动就崩盘")**：
- 任何要挂调度/远程部署的脚本, 先在本机 import/运行一次确认**不崩**(含异常分支 try/except 路径), 再挂 cron/推送。
- 验证清单: 语法 import OK; 正常分支退出码0; 异常分支(如端口不可达)不抛未捕获异常; 远程部署用 PTY 脚本喂 sudo 密码(直连 sudo -S 被安全机制拦)。
- Windows 台式无 crontab → 调度改用 Hermes `cronjob` 工具或 3046 本机 cron(3046 不关则调度不依赖台式)。

**复用既有产物, 不重头造 (2026-08-16 用户: "笔记本写过一版...不要再跟今天这样的了,装个系统搞了7小时")**：
- 动手前先搜本地: 过往会话已写的方案/已下固件/已配脚本(如笔记本的 OpenWrt刷机计划 + 已校验固件), 直接复用+多模型补审完善, 禁从零重写。
- 真校验固件: sha256 与官方 sha256sums 逐文件比对(本次 AX6S 四件套全对上, 才敢刷)。

**爬虫/情报类交付物的审查要点（2026-08-20 实测新增）**：当交付物是"每日抓取/情报汇总"类脚本(cron 跑的 fetch+summarize), 多模型审除常规技术选型外, 必须专门审:
- **抓的是正文/摘要还是标题?** 只抓首页 `<title>` = 废话噪声(实测: 旧 cron 产出"Hugging Face – The AI community"无用)。必须抓 `<summary>`/`<description>`/repo desc 级内容, 否则"升级"仍是无效功。
- **防幻觉措施会不会烧额度?** 要求"只基于抓取内容不编造"靠 prompt 硬约束 + 低温(0.3)即可; **不要为"交叉验证"再调第二个模型**——双调用违反不烧额度铁律。DS审计曾抓出"双重验证会烧额度"必须改。
- **绕过 Clash 是否代码级落实?** `requests.Session(trust_env=False); proxies={}` 强制直连, 否则 cron 环境继承全局 Clash 静默失败。
- **旧数据是否清理?** 覆盖式写当日原始, 日志只留轻量摘要, 防累积臃肿。
