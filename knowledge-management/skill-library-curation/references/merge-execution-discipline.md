## 合并执行纪律

24 条，分五批：**1–6 来自合并执行本身**，**7–13 来自验收与合并后的回头复查**，**14–18 来自孤儿清零/退役/房产簇**，**19–24 来自拼接体结构 pass（2026-09-27）**
（含一次「干活方 ↔ 验收方」角色对调，两边各自抓到对方没看见的问题），
**14–17 来自审计工具的假阳性与指针形态**，**18 是技能退役（不是合并）的足迹清理**。

1. **骨架写进 BRIEF 是硬要求。** 簇-2/簇-5 的产出都是「内容零丢失，但把 N 份文档订成一册」
   （无触发条件区 / 无导航 / 中英混杂）。簇-6 在 BRIEF 里**写死骨架**（触发条件 + 导航表 + §编号 +
   铁律速查 + 长文进 refs + `SKILL.md` ≤12KB）后，产出结构一次到位。**但执行者仍做不到完美，
   验收方要独立重排兜底**——BRIEF 写死骨架只降低偏差，不消除偏差。
   **事后最便宜的体检指标 = 跑一遍所有已合并技能的 `SKILL.md` 体积。** 实测 6 簇里 5 个超 12KB
   （最高 5.6x = 69KB），而唯一达标的 3 个恰是 BRIEF 已写死骨架之后做的。
   ⚠️ 但**体积超标只是嫌疑，不是判决**——「内容真的长」和「结构整合从未发生」会产生同一条超限记录，
   体检报告区分不了。判据是**拼接指纹**（`## 源模块:` 计数 ≥2，见 `references/structural-health-checks.md`）：
   命中才说明结构整合从未发生；未命中而只是偏大，那才是内容该下沉。先跑指纹，再决定做哪种修。
2. **「零丢失」单独写会诱导原样存档。** 只写"零丢失逐字搬"，执行者会把整合不进的内容
   原样堆进一个 appendix（簇-6 出现 34.6KB 附件，内部重复 14 组，且与主题 ref 语义撞车）。
   **必须同时规定「整合不进的内容怎么办」**：主题已被别处覆盖 → 删；真·独有 → 搬进主题 ref。
   判据是**主题在别处有没有覆盖**，不是"体积有没有变小"。
3. **体积指标必须含目标技能自身。** BRIEF 若只写「源 N KB → 合并后 0.85~1.15x」，
   执行者会为凑数字删内容。正确口径 = **目标合并前总量 + 源总量 − 去重节省**，
   并明确写「禁止为凑字节数删内容，零丢失优先级高于体积」。
4. **验收用「精确标识符法」要防假阳性。** 反引号包裹的标题、`/model X`→`/model <别名>` 这类改写、
   `9/22`→`9-22` 这类格式差异、正则薅出的 `and/or` 碎片，都会被误报成"缺失"。
   **逐条定性后再下结论，别只看数字。**
5. **引用链要跟到底（最容易漏）。** 只 grep 源技能名只能抓到"指向旧技能名"的断链。
   必须额外检查：**被引用文件是否真的存在**。簇-6 发现 5 处引用指向两个躺在 `.archive/` 里的
   真·独有文件（8KB，覆盖率仅 8%）→ 真·断链。工具：`~/.hermes/scripts/skill_ref_lint.py`
   （纯 stdlib；查 `references/<name>.md` 与 `scripts/<name>` 指针，分 BROKEN/ELSEWHERE/ARCHIVED/MISSING；
   有 MISSING/BROKEN → 退出码 1，可挂 cron；`--skill <name>` 单查）。
   ⚠️ **体检工具自己也会假阳性**，本项目实测两例：裸名自动补 `.md` 会把 `software-development/coding-delegation/references/api-recipes.py`
   误报成 `api-recipes.py.md`；代码块里的**反例**路径（`scripts/scripts/name.py`）会被当成真指针。
   修复后**必须真跑全库复验**，并把 `ARCHIVED/ELSEWHERE` 也改成明确说明（不是只修 MISSING）。
   ⚠️ **断链检查只查一个方向，必须补另一向。** `~/.hermes/scripts/skill_ref_lint.py` 查的是
   「指针→文件」（断链），**查不到「文件→指针」（孤儿）**：文件存在、内容有用，但 SKILL.md
   从未提及，等于写了没人知道。合并产物必须双向查。实测一个技能 1 个孤儿 ref，另一个 **5 个**
   （13.4KB 整批内容无人知道存在）。查法：对 `references/` 下每个文件名在 SKILL.md 里做一次
   子串命中，未命中的即孤儿。
6. **工具自己会错，工具的错误结论会被写进配置当事实。** 簇-6 发现技能自带的
   `probe_providers.sh` 有假阴性 bug（不发送 provider 的 `extra_body.tags` → 免费档 400 被误报成 404），
   而**基于它错误结论的注释被写进了 `config.yaml` 并留存多日**。
   体检类工具修好后必须**真跑复验，并清理它污染过的下游结论**。
   （同批实测：`knowledge-vault-ops` 里一句「`weekly_kb_update.py` 已删除」经查为假——文件仍在、
   cron job 仍在引用它；文档里的"已删除/已迁移"结论同样要复验。）
7. **交接验收前必须冻结版本。** 一边改一边让对方验收 = 对方验的是移动靶：它只能退而求其次报
   「稳定终态」，且无法确认验的就是最终交付，整条独立验收的证据链失效（实测：查验方把这条
   列为第一条验收问题，并因此无法给「合格」）。做法：写完 → **停止改动** → 记哈希 → 再交接；
   验收期间自己只读。同理，不要在同一批里既改 A 又改 B，否则验收方无法定基线。
8. **判断「独有内容」要比对【本次操作之前】的状态，不是操作后。** 搬移操作本身会让内容先消失
   再出现：把源 A 的整节下沉到 ref 之后，再拿源 B 去比「全新的 SKILL.md」，会判那节
   「SKILL.md 里没有」→ 当成独有 → 又搬一遍 → **同一内容三处并存**（实测：一次正确的下沉
   被自己变成三重重复）。校验脚本还因为标题格式不同（`## 标题` vs `**粗体**`）没报错。
   判据：**先列出「本次操作已经搬走了什么」，再判断剩余独有；比对基线是操作前的旧文件。**
   删除任何源文件前，问一句「它的内容是不是已经被我这次搬走了」。
   等价做法：**拿最终交付物的全量文件集再判一次**——基线是 `SKILL.md` + 全部 `references/` +
   `scripts/`，不是单个 `SKILL.md`；只在 `SKILL.md` 里搜不到就判「独有」是本次事故的直接成因。
9. **合并产物的 refs 常有嵌套块级重复。** 源 A 的整节可能被源 B 也包含，两份拼接后整块复制两遍
   （实测 66KB 的 ref 里 13.4KB 是这种重复，另一个 38KB 的 ref 里 4.6KB）。
   去重法：按空行切块，对 >150 字符的块保留首次出现、丢弃后续；**零丢失的验证方式是
   「去重前后独有行数不变」**（实测 265→265、94→94）。删块不要删行，行级去重会破坏结构。
10. **自查有「意图盲区」，独立验收必须换人。** 自己做的改动看不出自己造的语义重复——知道自己的
    意图，就看不见意图与产物之间的偏差。实测的不对称：我验执行方时抓到的是**表面问题**
    （体积超标、断链、陈旧引用、附录冗余）；执行方验我时抓到的是**语义问题**（三重重复、
    独有性误判、静默丢失、自指指针）。两个方向都要做，不能只做一个。
11. **重复的分段编号可能是有意的来源标记，不是拼接事故。** 看到「三套 A、两套 B」这类异常，
    **先读内容再下结论**：实测那 A/B 是刻意的来源标记（每节标题自述出处，如「实现侧技能原文」）。
    把它报成「首尾拼接铁证」是误判。**结构异常只能当线索，不能当证据。**
12. **下沉章节后必须扫陈旧自指。** 把某节搬进 ref 后，SKILL.md 里「见『X』节」/「回写本文件
    『陷阱』段」/「完整实现见…两节」这类自我指涉会全部失效，而断链检查**查不到**（它们不含
    `references/` 字样）。搬运后 grep 一次「见「」「本文件」「本技能内」并逐个改指 ref。
   同理，ref 自称「SKILL.md『某章节』的权威副本」也会失效，要跟着改。
   ⚠️ **反向同样会断：锚点写在逐字 ref 的正文里。** 把一个多段式单体拆成多个 module ref 时，
   原文里的「见**本文件上方**代码块」「见**上文**」「见第 X 节」原先在同一文件内天然成立，
   拆完可能指向了**另一个 ref**（实测：两个模块共用一段代码块，拆分后锚点所在模块里再没有那段 →
   独立查验判 FAIL，这是那轮唯一被判真的缺陷）。判据：**每个锚点的落点 heading 必须与锚点同处一个 ref**，
   逐条把锚点所在文件的全部 heading 列出来即可验。
   **修法只有一条：把换算写进你插在 ref 顶部的说明块，绝不动正文。** 正文是逐字原文，改了就不再可证伪
   （见第 20 条）。说明块里写「原指 X，现位于 `references/<file>.md` 第 N–M 行」——
   **但别让说明块自称行号**：它一插入，正文行号就整体偏移，说明块自己的行号引用当次就失效。
   「正文确实没被改」的证明方式：拿每个 ref 与它在拼接体里的原始切片做 `difflib.unified_diff`，
   **应当只有 1 个 hunk，内容就是那几行说明**；出现第二个 hunk 就是正文漂移了。
13. **活动树里的 `.bak.*` 是垃圾，但往往是唯一的回滚点。** 批量修文件的作业（如断链清零）会在每个被改文件旁留下
   `<file>.bak.<ts>`；它们既不算活内容、又会被下一次审计当噪声，清理是对的——**但清理前必须先搬到
   `~/.hermes/skill-backups/<job>-<ts>/` 再删**，因为它们常常是那次修改之前状态的唯一副本
   （curator 的 blobs 不按路径存，事后无法按文件名找回）。实测教训：一次「顺手清 .bak」删掉 41 个文件，
   横跨 30+ 技能，其中只有 1 个属于当时正在做的那一簇——**批量删除前先打印完整清单并确认范围**，
   别用一个 `*.bak.*` 通配就扫全库。
14. **孤儿（文件存在但 SKILL.md 不提）的收口默认是「加一行指引」，不是删。** 分类先于动作：
   ① `__pycache__` / `.bak` / 逐字相同的重复副本 → 删；② 其余一律在 SKILL.md 的 `## References`
   里补一行 ``- `references/<file>.md` — <从文件首行/文档字符串取的真实描述>``。理由：孤儿里大部分是
   真内容却无人知道，删掉才是丢知识；而写指引只 +80B。**判副本要拿内容比，不是看文件名**
   （实测标着「合并来源：X」的副本对源技能覆盖率只有 86–98%，即含源里已没有的行，不能当重复删）。
   收口完成的判据只有一个：审计复跑 **ORPHAN=0**。
15. **审计工具认不出「绝对路径形态的交叉引用」，会把它报成 BROKEN。** 正确写法
   ``~/.hermes/skills/<other-skill>/references/<file>.md`` 在 `skill_product_audit.py` 早期版本里
   一律被当成 `references/<file>.md` 不存在 → 实测 16 条 BROKEN 里只有 2 条是真问题（相对指针），
   其余 14 条全是合法跨技能引用，噪声会把真断链淹没。修法（已落地）：判 BROKEN 前先剥掉围栏代码块，
   并允许同一行里的绝对路径解析成功；同时跳过 `__pycache__`。**工具修完必须全库复跑对比前后计数。**
   ⚠️ 写本类规则文本时，占位示例必须带尖括号，**且尖括号要包住整个 basename**（形如 `references/<file>.md`）。
   两种写法都会自造断链，本文件实测各踩过一次：①写成真文件名形状；②尖括号只包中间一段——文件名取 `original-` + 尖括号 + `-` + 尖括号 + `.md` 这种形状时，会被 lint 解析成一个**不存在的短名**（`original-` 后面直接接扩展名），**直接计成致命未降级**（实测：`致命未降级: 0 → 3`）。**描述坏例子时，别把 `references/` 和这种形状连写成一行。**写完规则文本，**立刻跑一次 `skill_ref_lint.py` 验自己**。
16. **合并一个簇的实操顺序（Windows 7→1 实测跑通）**：先备份整个簇 → 建新目录 → 每个源「SKILL.md 正文逐字」
   落一个主题 ref，其余支持文件原样搬（搬前查重名，冲突就加前缀）→ 新 SKILL.md 只写导航 + 铁律速查
   （≤12288B）→ 最后才归档源、改外部指针、重建 INDEX。**次序不能反**：先归档再建 ref 会让逐行复验失去基线。
   收尾必做三件：① 外部指针（包括别的技能的 ref 里提到的旧技能名）逐条改指新技能；
   ② 宿主技能里指向旧技能的「副本 ref」用覆盖率判定后删掉 **并**改指针（只删不改 = 自己造断链）；
   ③ 复跑两个工具，看 `skills=` 计数降到预期（本簇 101→95）且 `ORPHAN=0 BROKEN=0`。
   派独立验证者（Codex）时用 `codex exec --sandbox read-only`，防止它「热心地」重写半截文件。
17. **深指针（`skill_view(<skill>)` 文字）两个工具都查不到，合并后必须单跑一条 grep。**
   合并/归档技能后跑：
   `grep -rn 'skill_view(' <skills> --include='*.md' | grep -v '/.archive/'`，
   再把抽出的名字和 `.archive/` 目录名取交集——命中就是“叫你去看一个已经不在活动位的技能”，
   实测就是它（Windows 簇合并后 `transfer-chinese-paths.md:14` 还写 `skill_view(windows-linux-file-xfer)`）。
   同理 `windows-ssh-ops` 这类旧名以普通文字出现在正文里（不是 references/ 形状）也逃过两个工具，
   要靠 `grep -rn '<旧技能名>' | grep -v '/.archive/'` 人工判“活指针 vs 溯源文字”。
   **还有第三种形式：目录路径**——`~/.hermes/skills/<类别>/<已归档技能名>/...`（Codex 独立查验时抳出来的）。
   合并后跑一次：对 `.archive/` 下每个目录名，全库 grep `skills/[^ ]*/<名>/`，实测能抓到 ref 里残留的死路径。

18. **退役一个技能 ≠ 只删技能目录；要清它的整条足迹，并把不可复现的部分记账。**
    顺序：技能目录备份到 `~/.hermes/skill-backups/retire-<名>-<ts>/` → 移入 `.archive/` →
    清 `.usage.json` 条目 → 删它专属的 venv 与模型权重 → 改所有形态的指针 → 重建 INDEX →
    复跑体检确认 `skills=` 计数下降且 `ORPHAN/BROKEN` 未退步。
    - **指针有五种形态，grep 技能名只能抓到其中一种。** 实测一次退役要改 5 处：别的技能 frontmatter
      的 `related_skills:`、正文**推荐语**（「打分/排序优先用 X」——最容易漏，既不含路径也不含
      `skill_view(`）、其它技能的 ref、**环境路径**（`~/.venvs/<名>`）、**现状陈述**（「已建好的可用环境是…」）。
      改法是改写成「已于 <日期> 退役 + 重建出处」，**不是删句子**——读者需要知道东西为什么没了。
    - **`.usage.json` 里常常还躺着早就不存在的技能条目**（同名技能换过名或换过位置）。
      退役时顺手清：判据是「活动库 `os.walk` 找不到同名 SKILL.md」。留着它们会污染后续长尾审计。
    - **不可复现的东西要记账。** venv 和模型权重删掉不是「顺手就能回来」（几 GB 重下）。
      在备份目录里留一份清单：每个被删对象的体积 + 一条恢复命令（`hf download <hub-id>` 或重建出处），
      否则半年后没人知道怎么复现。删大目录前先 `du -sh` 记体积、删完复核，汇报里给出回收的 GB 数。

    - **合并前先查「同一内容在源里写了几遍」。** 实测房产簇：目标技能自己的 SKILL.md 里
      同一套 6 步批量导入流程写了**两遍**（`## 工作流` 与 `## 批量图片导入`，措辞不同、细节互补），
      而两个技能各自还带一份**同一张 6 维权重表**（权重完全相同，只有"核心问题"一列措辞不同）。
      这类"内部重复"和"跨技能重复"不会出现在任何体检输出里——**`DUP_BLOCK` 只查完全相同的块**。
      ⚠️ **处理口径不是"留信息量更大的那份"——那是错的，实测被独立查验推翻。**
      第一版我留了"更丰富"的源版、删掉目标那份，Codex 逐格对表后判定 **FAIL**：
      源版 6 维表的"核心问题"列是**另一种问法**，不是超集——`| 机会成本 | 10% | 投房 vs 理财？ |`
      被换成 `| 这钱投这套 vs 那套？ |` 后，语义从「房产 vs 理财」变成了「候选 vs 候选」；
      `| 价值锚定 | 成交 vs 挂牌价？ |` 被换成 `| 成交价是否真实？低于均价？ |` 后丢了「挂牌价」这个信号。
      **两张措辞不同的同义表，通常各自携带对方没有的信号；"哪份更全"往往是我的错觉。**
      **正确口径：留并集**——把两版并列成一张表（多一列标注来源技能），并在表下写明"两版都在，不要只留一版"。
      真正的重复（逐字相同的块）才删。合并说明里写清删了什么、为什么，否则事后复验会报成内容事故。
    - **"更丰富的那份是超集"这个直觉要用逐格比对证伪，不能靠通读。** 通读时两版都"讲的是同一件事"，
      只有把每一格的原文并排打出来，才看得见被替换掉的词（本例：`挂牌价`、`理财`、`投房` 全库 0 命中）。
    - **零丢失复验的"未命中"必须逐条定性，别只报个数。** 房产簇 24 条未命中全部是
      ①内部重复去重 ②被更丰富的孪生版本取代 ③标题/description 改写，实质丢失 0。
      但如果只报"24 条未命中"，读的人无法区分"我核对过"和"我数过"。**把三类分开列，各举一条原文。**
    - **改写时把承载精确字符串的行保留逐字。** 命令、错误串、路径、参数名（`import_data(path, reset=False)`、
      `analyze.py --import`、`parse_markdown()` 返回值签名）——**改写这些是纯粹的信息损耗**，
      复验时会报未命中且无法用"语义相同"辩护。实测房产簇第一轮就因加空格/改标点丢了 6 行，
      逐行恢复逐字后才干净。

    - **整篇改写前，先把原文逐字留档到 ref——否则"零丢失"永远证明不了。** 实测文件整理簇：
      目标技能原文是英文，我把它整体重写成中文整合版，复验立刻报 **51 行未命中**。
      改写**不等于**丢失（那是翻译），但**没有任何机器检查能证明改写是忠实的**——
      于是"未命中"和"真丢失"在报告里长得一模一样，复核者只能靠我口头保证。
      补救（已用）：把原文完整存进 `references/<original-原文档>.md`（逐字 + frontmatter），
      复验随即回到 0 未命中。**代价只有几 KB，换来的是可证伪。**
    - **搬一个源技能，不是只搬它的 SKILL.md。** 实测漏搬了 `archive-hygiene` 的
      `references/workflow-and-examples.md`（26 行未命中）。**逐源清点必须按文件清单过一遍**：
      `SKILL.md` + `references/*` + `scripts/*` + 任何 `templates/`。SKILL.md 里的 References 段
      是清单来源，但它本身可能就不全（见下条）。
    - **逐字 ref 内部的相对指针依赖原文件名——别顺手改名。** `archive-hygiene` 的正文里写着
      `references/workflow-and-examples.md`；我搬进目标时改名成 `archive-hygiene-examples.md`，
      于是**逐字 ref 内部产生一条指向不存在文件的指针**。**保持原文件名**，冲突时用目录或前缀区分，
      别改 basename。这条也可以自查：把文件里所有形如 `references/`+文件名的字符串抓出来，逐个判存在。
    - **合并是校验"技能里声明的工具是否真在位"的最好时机。** 实测 `safe-rm-trash-design.md` 写着
      `~/.hermes/scripts/safe-rm-selftest.sh` 跑全矩阵——该脚本**只在 orphan 归档里**
      （`~/hermes-infra/archive/orphans/...`），指针早失效了。已复原并**真跑全矩阵**（T1-T17 全过：
      受保护 exit 1 / 正常 trash exit 0 / `-f` 缺文件 exit 0）。
      ⚠️ 跑之前先看 `~/.trash` 有没有真数据——该自测的 T16 会 `trash-empty --force`。
      **合并一个新簇时，顺手把该簇声称的验证脚本跑一遍**，比读十遍更值。
    - **4→1 在 12288B 上限下是"先算账再动笔"。** 主文件必须只放「脊柱 + 高频块」，其余全下沉 ref。
      实测压了 5 轮才进（18455 → 11927B），每轮都是"再移一段到 ref"。
      **开局就先估**：Σ(源主文件体积) 通常远超上限，**动笔前决定哪几段注定下沉**，比写完再删省事。

19. **「拼接体」有指纹，先扫它再谈结构 pass。** 早先的合并如果只搬内容不做结构，产物就是
    N 份源文档端到端摞在一起，每份保留自己的一级标题——指纹是 `## 源模块: <名>`。
    一条命令全库扫：
    `grep -rc '^## 源模块:' <skills> --include=SKILL.md | grep -v ':0'`
    实测 2026-09-27 抓到两个：`connectors/dual-machine-hermes-ops`（8 个源模块 / 122,174 B = **9.9× 上限**）、
    `devops/dual-machine-sync`（7 个源模块 / 36,422 B = 3.0×）。
    **这类问题体检工具全绿**（零丢失、断链 0、frontmatter 正常），只有看结构才看得见——
    因为它们本质是「内容 pass 做了、结构 pass 没做」，而所有自动检查只验内容。
    **结构 pass 的信号**：`SIZE` 里出现 3× 以上的倍数且该技能有 `## 源模块:` 指纹。

20. **只做结构时，绝对不要「统一标题语言」。** 拼接体里的中英混杂是合并前的**原文样貌**，不是缺陷。
    统一标题会连带改动命令、路径、error 串、表格列名——正是 18 条里反复栽的那个坑。
    本轮的取舍是：**宁可保留原样，也不做"顺手润色"**，并把这条决定写进主文件的「结构 pass 记录」，
    免得下一个人以为是没做完。
    判据也随之收紧：结构 pass 的零丢失门槛是**逐行全等**（剔除自己插入的说明行后），
    不是"语义相同"——任何润色都会当场露馅。
    两条保命细节：① **源模块标记行逐字留在 ref 首行**（`## 源模块: <名>`）——它既是溯源，
    也是下次 `grep -rc '^## 源模块:'` 能对上的锚，别当成拼接垃圾一起删掉；
    ② **ref 命名 `module-NN-<源模块名>.md`**，把源技能名留在文件名里，跨技能指针与人工溯源都还能 grep 到。
    逐字 ref 里若出现指向 `.archive/` 的绝对路径，结构 pass 时**把那个文件复制进本技能的
    `references/`**，让技能自此自包含；原文里的 `.archive/` 路径留着当溯源。
    否则被引内容会随下一次归档清理一起消失，而断链检查只在指针形态坏掉时才报。

21. **在正文里写 `references/<glob>.md` 会自造断链（第 4 次踩同一个坑）。**
    本轮写「N 个源模块逐字拆进『references 斜杠 module 星号点 md』」，linter 把通配符抹掉，
    解析成 `module-` 开头的 md 引用 → MISSING。**安全写法是把路径与文件名拆开**：
    「拆进 `references/` 下的 `module-NN-<源模块名>.md`」，中间不要出现 `references/` 后紧跟文件名的形态。
    **写完规则文本立刻跑一次 lint**——这条规则本身已经害我四次，包括写这条教训的时候。

22. **合并/结构 pass 之后主文件变薄 → 体检工具会把二级 ref 全报成 ORPHAN。**
    工具的判据是「文件名是否出现在 SKILL.md 的文本里」（一行代码：`if fn not in skill_md_text`）。
    主文件从 122KB 瘦到 10KB 后，原先被正文顺带提到的 25 个 ref 一夜之间全变"孤儿"（实测 `ORPHAN 0 → 28`）。
    **它们不是真孤儿**——按 2 跳可达性算（SKILL.md → module ref → 细节 ref）**不可达数 = 0**。
    但别去改工具放宽判据（那是"改考卷让自己及格"）。**正确收口 = 在 SKILL.md 末尾加一张「附属文件索引」**，
    把 `references/`+`scripts/`+`templates/` 里**所有**文件名列全（一行一个，带一句话说明）。
    实测补 25 条（ops）+ 3 条（sync）后 `ORPHAN` 回 0，且这张表对人也是真有用的目录。

23. **跨技能的指针必须写全路径，裸相对路径会被判 BROKEN。** 我在 ops 的 SKILL.md 里写
    「`devops/dual-machine-hermes-connect/references/desktop-connection-modes.md`」和
    「`devops/dual-machine-sync` 的 module ref（module-06 那份记忆策展）」——**6 处全部被判 BROKEN**，
    因为审计工具按**本技能**目录解析相对路径，而那两个文件属于别的技能。
    改用可解析的全路径形态 `~/.hermes/skills/<技能>/references/x.md`（工具认这个形态）后清零。
    **规律：只要文件名不属于当前技能，就必须带前缀。**

24. **「旧快照 ref」不能默认是纯子集——两个方向都要比。** 活性副本检查要算两组差集：
    ① 活动技能有、ref 没有 → ref 陈旧（实测覆盖率 81.5%，缺 "Step 0 先读真相源核对地址" 等 24 行）；
    ② **ref 有、活动技能没有 → ref 独有内容**（实测仍有 10 行独有，其中两条规则——「双向 Syncthing 同步记忆
    会损坏 state」与「`hermes serve` 重启即死，改用 `start_serve.bat`」——**只存在于 ref 里**）。
    只算 ① 就会得出"ref 是旧版、可以删"的错误结论，把两条独有规则一起删掉。
    **结论写法**：两边都要看 + 说明哪些内容只有哪边有，别写"以 X 为准"。
