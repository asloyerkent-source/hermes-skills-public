# Skill 建议 + Onboarding (skill-suggester)

本 skill 是三层提醒体系的第 2、3 层：

- 第 1 层 **thinking-frameworks**（§1 静默 7 维自扫）：静默自扫，回复末尾最多一行 ⚠️（已有）
- 第 2 层 **建议层**（本 skill A 段）：匹配到没用的 skill → 回复末尾一行 💡
- 第 3 层 **Onboarding 层**（本 skill B 段）：安装完成后 → 输出 📦 触发清单

三层互不替代：⚠️ 讲风险，💡 讲工具，📦 讲入口。

## A. 建议层（每轮对话，always-on）

### 触发

所有对话**自动生效**，用户不需要说关键词。

### 逻辑

1. 正常理解用户请求、**正常回复**——本层不改变回复的内容和结论。
2. 回复发出前，额外做一步**静默检查**：系统提示里的 skill 索引（或 `skills_list()`）中，有没有哪个 skill 的 description 与这次请求**高度匹配**？
3. 同时满足这三条才算「高度匹配」：
   - 这个 skill 的能力**就是**用户这次要做的事，不是沾边；
   - 本次回复**没有**加载/使用该 skill；
   - 用户不是在问「你有什么 skill / 能干什么」这类元问题（元问题直接答，不加建议）。
4. 命中 → 回复**末尾追加一行**；未命中 → **什么都不加**。

### 输出格式（唯一允许的形式）

```
💡 这个可以用 <skill名>，要我跑吗？
```

### 纪律

- 每次回复**最多 1 条**建议：不并列、不排序、不附候选列表。
- **不输出雷达、不解释为什么匹配**，只给那一行。
- 已经在用的 skill 不提。
- 建议是**问句**，**不自动执行**该 skill——用户答「跑」才加载。
- 同一条建议在一次会话里**不重复提**；用户拒绝过的不再提。
- 用户说了「别建议 / 别插话」后，本层静默，直到用户解除。

### 例子

- 用户：把这份 PDF 的表格导成 Excel → 本次没用 xlsx → 末尾加 `💡 这个可以用 xlsx，要我跑吗？`
- 用户：现在几点了 → 无匹配 skill → **不加任何东西**。
- 用户：你有哪些 skill？ → 元问题，直接答，**不加建议行**。

## B. Onboarding 层（安装完成后）

### 触发

Hermes **自己刚做完一次「安装完成」类操作**时：clone + `install.sh` 跑完、`hermes skills install` 完成、插件装好、批量写入新 skill 目录之后。

### 行为

1. 自动列出**本次安装**的所有 skill / 插件名（只列这次的，不复述库里已有的）。
2. 每个名字后跟**一句「怎么触发」**，只写入口。
3. 用户没问就不展开用法。

### 输出格式

**每项写两段：先「干什么用」（中文一句话人话），再「怎么触发」。**
只写入口不写用途，用户还得追问一次"这个技能到底干嘛用的"——实测踩过。

```
📦 安装完成：
- `humanizer` — 把 AI 腔的文字改回真人写的 → 说"humanize"
- `thinking-frameworks` §2 控制论拷问 → /cyber-grill 或"控制论拷问"
```

### 「怎么触发」怎么写

| 类型 | 写法 |
|------|------|
| 命令触发 | 写命令，如 `/cyber-grill`（现由 `thinking-frameworks` §2 承载） |
| 关键词触发 | 写用户会说的那句话，如「控制论拷问」 |
| 自动生效 | 写「自动生效，无需触发」 |
| 不确定 | 写「用法待补」——**不要编** |

### 纪律

- 只列**本次**安装项；本次没有安装项就不加这一段。
- 一项一行；**「干什么用」必写**（中文一句话人话）。参数、示例、注意事项不写（用户要细节再给）。
- **不要把安装校验过程（INDEX 计数、lint 结果、软链检查）当正文汇报**——
  那是过程不是结论。用户关心的是"这东西能帮我干什么"，不是"装得对不对"。
  校验结果压到最后一行，或直接省略。
- 与建议层的 💡 同时命中时：📦 在前，💡 在后。

## C. 全库技能清单的呈现格式（用户问"有哪些技能"时）

用户要的是**看得懂**，不是**看得全**。他原话：
"排版很糟糕，名字，功能，没有重点，功能有的没的写的太复杂，看不懂。"

### 硬规矩

1. **按功能分组，不按目录、不按字母。** 分 6–8 组（模型与审核 / 本体运维 / 网络与双机 /
   知识与内容 / 业务 / 思考与纪律），组内按重要度排。
2. **每行两列：`技能名` | 干什么。** "干什么"必须是**中文一句话人话，≤20 字**。
   **绝不直接抄 `description` 字段**——库里大量描述是英文、带 `Use when ...` 触发句式、
   或被 INDEX 截断出省略号尾巴，照抄出来就是用户说的"看不懂"。要**自己重写成他的语言**。
3. **必须有重点。** 用**真实调用次数**分档标注（`.usage.json` 的 `use_count`），
   别让用户从 70 行里自己找重点：`★★★` ≥10 次 · `★★` 5–9 · `★` 2–4 · 不标 0–1。
   开头一行写清星号是什么口径（"★ = 真实调用次数"），否则它只是个装饰。
4. **主动把真问题标出来**：重复条目、描述为空/坏的、装了没用过的。
   这些才是用户真正想知道的信息，比多列 10 个技能有用。
5. **说"没用过"必须叠加 mtime 交叉验证**——`use_count=0` 单独不构成证据
   （见 `references/long-tail-inventory-audit.md` 与主文件「先判」第 2 条）。
   实测把前一天刚合并完的 6 个技能说成"没用过"，被用户当场问住。

### 反面清单（凑齐就是"排版很糟糕"）

- ❌ 70+ 行平铺，不分组
- ❌ 每行缀着英文原描述 + 省略号截断
- ❌ 完全没有优先级标注，看不出重点
- ❌ 只列名字，不写"干什么"
- ❌ 把 `description` 字段原文当"功能"贴出来

## 边界

- 本 skill **不改**用户回复的实质内容，只在尾部加一行（💡）或一段（📦）。
- 是否「高度匹配」拿不准时，**不加**——宁缺勿滥。
- 不替用户做决定；建议不自动执行。

## 验证

- 建议层：一轮普通对话后，回复末尾要么恰好一行 💡，要么什么都没有；出现两行以上即违规。
- Onboarding 层：安装类操作结束后，清单里的项数与本次实际安装数一致，且每项都有一句触发入口。
