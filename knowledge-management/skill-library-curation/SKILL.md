# 技能库治理（审计 · 合并 · 长尾 · 重整 · 索引）

技能库变大后，这套流程用来**判断该不该合并、怎么合并、什么时候删**。先判根因，别直接开合并。

**先判：这轮值不值得合并（`references/root-cause-consolidation-pass.md`）**

**用户点名一批技能问「在用么/能合并么」时，先跑一次全量 usage 再开口。** 正确形态是**一张带 use_count / 最近使用 / 大小 / 判定的表**，而不是逐个点评——实测一次「这 28 条都是干嘛的」逐个点评完，用户追问「在用么」时只能靠印象答，等于把可查的数据做成了猜。
```bash
python3 -c "import json;d=json.load(open('$HOME/.hermes/skills/.usage.json'));[print(k,v.get('use_count'),v.get('state'),v.get('pinned'),d[k].get('last_used','')[:10]) for k,v in sorted(d.items())]"
```
判据：`use_count` 与 `last_used` 说「最近在用」，`pinned=true` 是免删名单（铁律 25）。**近 30 天活跃的一律不建议合并**——职责切得清楚时合并只会丢触发精度；表里已经活跃的条目不叫库存堆积，叫使用记录。

**⚠️ 「技能是空壳」有一条好用的指纹：正文引用的兄弟技能目录全部不存在。** 批量导入的技能常带着别的体系的路径（`../<同族技能>/`、`field-journal/`、`MASTER R26` 之类），跑一次就现原形：
```bash
grep -oE '\.\./[a-z0-9-]+/' <skill>/SKILL.md | sort -u | while read p; do
  [ -d "$HOME/.hermes/skills/*/$p" ] || echo "MISSING $p"; done
```
这种技能只值得把**独有的那几行**（如一张工具对照表）并进功能完整的同类技能，然后归档；其余正文是断链模板，留着零价值。配套：正文里带通用模板节标题（「ACTION REQUIRED（读完后立刻执行）」）也是同源信号。
⚠️ **扫断链时要排除「文档里作为例子写的路径」——本技能自己的正文就举了 `field-journal/` 当指纹样例**，全库 grep 会把它一起命中，看形态像真断链。判据是「该路径是否出现在示例/代码块语境里」，不是「文本里有没有这个串」；命中先读上下文再定性，与铁律 28「关键词扫重叠只得到候选」同源。实测一轮真断链是 3 个技能 7 处，而带 `../tool-index.md` 的不止最初报的那 2 个——**必须全库 grep 一次，不能凭印象列清单**。

### 37b. 「技能太多/太难触发」先分清是数量问题还是描述问题——合并是错误的解法

用户的诉求原话往往是「技能太多」「要减少需要我主动触发的数量」。这个诉求有两种完全不同的根因，
**解法相反**，而合并是两者中昂贵的那个：

| 症状 | 真根因 | 正确动作 | 成本 |
|---|---|---|---|
| 描述里没有你真会说的词 | **描述问题** | 改 description（补用户口语） | 几分钟/条 |
| 同族技能职责真重叠、正文大面积逐字重复 | **数量问题** | 合并（走上面两道门） | 几小时/簇 |

**判据：拿一组真实用户话术去查期望技能的 description 有没有出现那些词**，
全部缺 ⇒ 描述问题；覆盖率已经很高（实测 14 条真实话术 10/10 命中）⇒ 合并救不了它，
因为合并后新技能的描述还是那个描述。

跑 `scripts/skill_trigger_regression.py`（用例表就是一组真实用户话术 + 期望技能 + 必需触发词）。
⚠️ **它测的是「描述可读性」，不是唤醒率** —— 真唤醒率要真调一次 API，
但**没有「看它加载了哪些技能」的读数通道**：`hermes chat -Q` 短问路径不写
`sessions/request_dump_*.json`，所以只能改用回复里的**行为证据**反向判断。
成本高一个数量级，且样本量小到不支持全库结论 —— 做法与三个坑见
`references/wake-rate-measurement.md`。脚本 docstring 与退出摘要里都写死「不是唤醒率」，别让人把它的输出当更大的结论。

**合并前必须先答「合并后唤醒会变多吗」。** 答不上来就是拿几小时的昂贵操作
去解决一个几分钟能改完的问题。实测一次：87 个技能里 `use_count>=1` 的有 60 个，
真在用的合并收益为负；而「主动触发困难」全部由描述用词造成。

⚠️ **统计本身要先验判据。** 用「动作词命中数」批量统计描述会产出大量假阳性
（「要长期跟踪」里的「跟踪」在词表外），据此报「56/87 技能缺触发词」是错的。
中文没有词边界，词频/重叠类统计要么引分词器，要么用显式关键词表（同 `flows/measurement-integrity` 22b-11）。

合并是**昂贵**操作（今天实测：7 个簇从 22:06 到 22:55，5 次 Codex 独立查验，抓出 20+ 处指针缺陷）。开跑前先答：
1. 技能数是否**真**超过阈值（`ls ~/.hermes/skills/*/SKILL.md | wc -l`，不是凭记忆）？
2. `.usage.json` 里有没有**长尾**？先跑长尾审计，可能删就够解决。
   ⚠️ **`use_count=0` 本身不是长尾判据。** 它只记 agent 载入（`skill_view`/自动加载），不记脚本直跑、不记 cron；
   而且**刚合并/改写过的簇目标必然是 0**——重写完还没被调用过。拿它当"没用过"会误杀刚做完的工作。
   真判据是三信号交叉（载入 + 被引用 + 可执行物）**叠加 ≥24 天未改**，见 `references/long-tail-inventory-audit.md`。
   **在非审计场合顺口说"这几个没用过"时同样适用"**——不必跑到正式审计才算数。
3. 有没有**保护标记**（Gate A：`grep -rnE 'sacred|never merge|禁止合并|不可合并'`）？命中的立刻踢出簇。
4. **簇里的源是不是早就被逐字搬进目标的 `references/` 了？** 排期前逐源分诊一遍——
   半成品簇的剩余工作是「归档源 + 结构 pass」，不是「内容整合」，工作量差一个数量级。
   判法与探针见 `references/counting-clusters.md` 的「先分诊」与 `scripts/ref_absorption_check.py`。

**簇按"用得多 + 语义相邻"聚，不按目录相邻聚。** 排第一的簇未必最该做——先看它的内容杂不杂。

## 合并执行纪律（最常用的 7 条，全文 18 条见 ref）

1. **骨架写进 BRIEF 是硬要求**（触发条件 + 导航表 + §编号 + 铁律速查 + 长文进 refs + SKILL.md ≤12KB）。
   BRIEF 写死骨架只**降低偏差，不消除偏差**——验收方要独立重排兜底。
2. **「零丢失」单独写会诱导原样存档**——必须同时规定"整合不进的内容怎么办"：主题别处已覆盖 → 删；真·独有 → 搬进主题 ref。
   判据是**主题在别处有没有覆盖**，不是"体积有没有变小"。
3. **体积口径必须含目标技能自身**，且写明「禁止为凑字节数删内容」。
4. **「精确标识符法」要防假阳性**：改写标题、格式差异、正则碎片都会被误报"缺失"。**逐条定性再下结论**。
5. **引用链要跟到底**：grep 技能名只能抓"指向旧技能名"，还要查**被引用文件是否真存在**（`skill_ref_lint.py`）。⚠️ **体检工具自己也会假阳性**（裸名补 `.md`、代码块里的反例路径）——先修工具再信数字。
   **读汇总行要看清口径：`skill_ref_lint.py` 的 `BROKEN: N` 是「各类问题总数」，不是独立类别**——
   `N = 真断链 + ELSEWHERE(跨技能指向) + ARCHIVED(指向归档) + MISSING(文件缺失)`。
   把 `ELSEWHERE: 3` 读成"新增 3 条断链"并向用户报警，是自己吓自己。
   判"我这轮有没有引入断链"要**按文件逐条比前后**，或用 `--skill <名>` 单查，**别看总数**。
6. **备份先于删除**，且备份放**活动目录外**（`~/.hermes/skill-backups/<job>-<ts>/`），删前打印完整清单。批量删 `.bak.*` 前先搬备份——曾一次误删 41 个横跨 30+ 技能。
7. **独立验证用「从源重新推导」**，不是"再叫一个模型"（多模型审稿是可选，不是门禁）。

## 铁律

1. **`agent-communication-discipline` 是 sacred**：永不合并、永不删除（里面是真实事故学来的用户规则）。
2. **独立验证对合并是强制的，多模型审稿是可选的**——门禁是"从源重新推导"，不是"第二个模型"。
3. **保留 `references/`**：合并时把它的内容搬进目标技能，**不要删**。
4. **合并后必须回读**确认内容连贯完整。
5. **保护标记只在别的技能正文里**（不在元数据），没有捷径——grep 到就得逐条读。
6. **外部引用有三类会静默断裂**：cron `jobs.json`（含 prompt 自由文本）、别的技能 `related_skills:` 与"见 `<name>`"正文、生成的 `INDEX.md`。**合并改动里必须一起改。**
7. **`.bak` 是垃圾但常是唯一回滚点**——批量删前先搬备份。
8. **孤儿（文件在但 SKILL.md 不提）默认加一行指引，不删**——大部分是真内容；判副本要拿内容比，不是看文件名。
9. **被搬动的脚本要「真跑一次并看产物落点」**——`bash -n` 只验语法，验不出相对路径算错。路径算错时脚本**不报错**，只是把产物静默写到错目录（`register.sh` 少一级 `..` 时，会在 `skills/<类>/` 下凭空生成一个 INDEX.md）。搬动任何脚本后：数清它到目标目录的层数 → 实跑 → 确认打印的目标路径与产物落点都对。
10. **异步验证不阻塞主线**：派 Codex 查验后立刻推进下一簇，别串成阻塞链；每条回复写明「还在跑什么、预计多久」。冷启动型任务（本地模型加载要几分钟）启动前先说耗时——用户在看不到进度时会直接催「怎么还没好」。
11. **改完任何技能文本就立刻跑一次 `skill_ref_lint.py` 验自己——规则文本本身最容易自造断链。**
    写占位示例时，尖括号必须包住**整个 basename**（形如 `references/<file>.md`）；
    只包中间一段（文件名形如 `original-` + 尖括号 + `-` + 尖括号 + `.md`）会被解析成一个不存在的短名，
    实测把 `致命未降级` 从 0 推到 3。**描述坏例子时，别把 `references/` 与那种形状连写成一行。**
    这条坑同一个文件踩过两次——第一次只是写下规则，第二次是写规则时又踩。
    **写完规则/示例属于「改文本」，跑一次 lint 比读三遍便宜。**
12. **内容绿灯 ≠ 合并完成。** union merge 有两个交付物（内容 + 结构），而**体积超限可能是「结构 pass 从未跑」而不是内容真的长**——两种情况在体检报告里长得一样。判定靠指纹：
    `grep -rc '^## 源模块:' ~/.hermes/skills --include=SKILL.md` 命中 ≥2 就是拼接体，要补的是结构（拆 ref、加导航、统一标题），不是删内容。实测两个拼接体分别吃到上限的 9.9× 和 3.0×，而断链、孤儿、frontmatter、体积以外的所有指标**全是绿的**。
    **允许把一个簇标记为「跳过」，但跳过不等于没发生**——跳过的簇仍要按活动树实点成员数，不然半成品会一直躺在库里（见 `references/counting-clusters.md`）。
13. **备份清单会把「清单文件自己」算进去。** 写法 `find . -type f -exec sha256sum {} \; > SHA256SUMS.txt` 里，重定向文件在 `find` 跑之前就已创建，于是它把自己也扫进去；写完后自身哈希又变了，`sha256sum -c` 必然报 1 条 FAILED。**正确写法：先落 tmp 再排除，`find . -type f -exec sha256sum {} \; | grep -v SHA256SUMS > SHA256SUMS.txt`。**
    真实数据文件那几条是 OK 的——`FAILED` 只指着清单自身，别被它带着去怀疑备份。这条在一个批次内**先说给执行方、执行方改了一半、父级自己又踩一次**（簇10修了簇11没修，父级补第三份时重犯），所以它值得单列而不是塞进脚注。
14. **外部引进的技能是库里的一等成员，不享受豁免。**
    它是「`~/.agents/skills/<name>` 真身 + `~/.hermes/skills/<name>` 软链」两段式。
    ⚠️ **软链是扫描器的盲区，两种口径要各验一次**：`register.sh` 会跟进软链，
    而基于 `os.walk` 的工具默认**不跟进**（`followlinks=False`）——只跑全库扫描会把它当不存在，
    **且不报任何错**（`skill_ref_lint.py` 已补丁修好这个漏扫）。
    装完必须：① 重跑 `register.sh` 并**与装前总数对账（应当 +1）**；
    ② 跑 `skill_ref_lint.py --skill <名>` 单查（报 `no skill matched` 就是没扫到）。
    只看到"装完了"的成功提示不算数。见 `references/external-skill-intake.md`。
14a. **description 长度上限是 60，不是 57 —— 阈值要从代码读，不靠记忆。** 权威值是 `agent/skill_utils.py` 的 `SKILL_PROMPT_DESC_LIMIT`，实测 `=60`（`parse_frontmatter` 的返回是 **tuple** `(dict, body)`，当成 dict 会读出全空）。
    - **验技能必须用 Hermes 自己的解析器**：`from agent.skill_utils import parse_frontmatter; fm, body = parse_frontmatter(raw)`。`yaml.safe_load` 会在闭合 `---` 被缩进时**静默容忍**，而 Hermes 的 `skill_matches_platform()` 不会 —— 用 yaml 验会漏掉平台门禁失效和 description 丢失。
    - **自写检查器时，frontmatter 首行要比对「原始行」而不是 `.strip()` 后的值**。缩进 4 空格的 `    ---` 经 `strip()` 等于 `---`，会蒙混过关——而这正是上面那个 bug 的形态。**判据：`lines[0] != "---"` 用等值比对，闭合 `---` 同样要在顶格找**（`lines[1:].index("---")`），找不到就报「未闭合」，不要退化成宽松匹配。见 `scripts/skill_repo_doctor.py` 的 `check_frontmatter`。
    - 四轮审核里我按"索引截断到 57"压词，压过头删掉了 `skill-library-curation` 的「审计长尾」、`measurement-integrity` 的「检查脚本」—— 那些是正文判据的核心触发词。按 60 重写后 8 条描述同时补回了触发词并划清边界。

14b. **改软链技能的描述/正文，要写它的真身，不是写软链路径。** 库内有 4 个技能是「`~/.agents/skills/<name>` 真身 + `~/.hermes/skills/<name>` 目录软链」（`obsidian-cli` / `obsidian-markdown` / `json-canvas` / `obsidian-bases`），另有 `humanizer` / `find-skills` 同构。
    - **判据**：改之前先 `os.path.realpath(<skill_dir>)`，返回路径不以 `~/.hermes/skills` 开头 ⇒ 改的是真身。写软链路径在多数编辑器里会**跟随软链直接改到目标**（看似成功），但用 `open()` + `write_file` 整目录操作、或先 `unlink` 再写，就会**把软链变成真拷贝**——库内外从此两份独立副本，各自漂移。
    - **反向的坑**：`find-skills` 的描述是英文、看起来"没改"，实际是我按软链路径查不到文件便跳过了；`humanizer` 的 frontmatter 闭合符缩进了两轮都没被扫出来，也是因为按软链路径遍历时 `glob` 默认不跟随。
    - **动作**：`realpath` → 改目标 → 经软链路径回读验证一次。**验的是"经软链读到的值变了"，不是"目标文件变了"。**

15. **判「装了 N 个技能」靠 description 字段抓不准，要实读 frontmatter。**
    `skill_product_audit.py` / `skills_list` 给的 description 经常抓不全（多行、引号、嵌套 metadata），
    表现为「搜得到技能但 description 是空的」——**这是抓取口径问题，不是产物缺字段**。
    审计时用 `glob(**/SKILL.md)` + 打印文件前 ~700 字符实读，才能判它到底有没有可用的触发描述。
    **凭这个空描述说「它没写触发条件」= 把自己的解析失败当成产物缺陷**（与铁律 5 同类）。
16. **ORPHAN 要分两类：真孤儿 vs 扫描器没覆盖到的第二入口——但两者都补指引不删。**
    判据 = **它到底会不会被走到**：
    - 真孤儿（没人引用、文档不提）→ 铁律 8 的默认处置，补一行指引；
    - **回退/备用实现**（代码存在、确实会被走到、只是文档没列）→ 同样补指引，**且必须写清触发条件**
      （例：「系统无 YARA 时自动回退到本引擎」——不写这条，读者以为它坏了）。
    两类的危害相同：**删掉后一旦外部依赖缺失就静默失效**。真副本要拿内容比，不是看文件名。
17. **技能自带的评分/检查器，它自己的通道要先验再用。**
    库里有技能自带质量评分（跑全树给每个技能打分）。实测拿到「多个不同技能分数完全相同且偏低」——
    拆到分项后发现是评委 provider 不可达、fail-closed 记 0 分拖低均值，**被测技能在机械检查项上全满分**。
    动作：**分项跑、看有没有子项报 provider/状态码失败**，再判断是「内容不合格」还是「读数通道坏了」。
    判据：分数出现可疑的整齐值（全表同分 / 一律 0.50 / 一律 0.0）时，无分辨力的可能性高于被测物集体不合格。
    （细则见 `flows/measurement-integrity` 铁律 8。）
    ⚠️ **通道配好不等于评分器可信，还有第二道故障**：provider 403 与「响应里缺一个必需 key」
    症状一样（fail-closed 记 0），但修法不同——后者要动输出契约，不是换端点。
    **回显里说 `provider call failed` 是通道，说 `missing required key` / `malformed` 是解析。**
    ⚠️ **「regressed / improved」是差值，差值比绝对值更容易骗人。**报告没撒谎，但它比较的是
    两次独立抽样而非一次变化。**下结论前先把同一个被测物连跑 2–3 次验评委确定性**；
    分数跳变 ⇒ 那些 delta 是抽样误差，只能当「未测量」。
    **稳定的判据是「跨样本区分开了没有」，不是「单次分多高」。**
18. **自写的检查器只在一个样本上全绿 = 未验证。** 至少三类样本各跑一遍：最简形态 / 变体形态 / 空值形态。
    实测一个手写 frontmatter 解析器在「单行 description」样本上满分通过，
    却把用 `|` 和 `>` **块标量**的技能全判成「缺 description」——**报错的那几个恰恰是块标量写法**。
    机制：块标量的正文行不以 `key:` 开头，先试匹配 key 就会判成「无法解析」；
    且 `cur_list` 与 `fm[key]` 必须是**同一个对象**（写成 `a, b = [], []` 是两个不同 list，
    append 进前者却从后者取值 ⇒ 永远空）。
    **判据：声称「缺 X」的条目，先打开原文确认 X 真的缺**，再怀疑检查器
    （与铁律 15/17 同源，但指纹相反：那些是检查器算错，这条是**压根没测到那个分支**）。
    变体样本从库里现取——找几个**已知合规**的技能当对照组，比自己造样本可靠。
    **YAML 引号会被朴素正则当成内容**：`description: "Gmail, Calendar..."` 用 `re.search(r'description:\s*(.+)$')` 提取时，引号计入长度，59 字符的描述被报成 61 字符超限。**判据：提取 frontmatter 值时必须先 strip 引号（`strip('"').strip("'")`），再量长度。**
    **自测里的假阳性有固定形态：断言名写着 A，断言体只验证了 B。**
    实测一条名为「只读 state.db（文件 mtime/size 不变）」的断言，体内只有 `size > 0`——
    压根没取前后值比较，永远为真。**凡断言名里带「不变 / 相同 / 未被写入」，体内必须有前后两次取值。**
    反向还有一种：**用不真实的夹具换绿**。断言「活跃会话不该被收集」的用例把
    判据字段也置成 0，而真实库里该字段恒有值——缺陷正好被这个假前提掩盖。
    **造「应该被排除」的夹具时，排除字段只留真正为空的那一个。**
    **同一 bug 类在两个调用点出现时，抽共用函数而不是分别修**——实测 `skill_repo_doctor.py` 的 `check_frontmatter` 和 `check_index_consistency` 都用正则提取 description，都没剥 YAML 引号、都没处理块标量。只修一处的话另一处照旧误报。**判据：改检查器时 grep 所有调用点，同一判据只应有一个实现。**
    **修完检查器要拿它扫「本次改动本身」。** 向用户报「已修好」时，那个改动就是待验收的产物，
    而刚改完的那一刻是你最不会怀疑它的时候。实测：改完脱敏规则后直接报「已 patch」，
    用户追问「真的完善了么？你验证过么」，把体检工具指向**自己刚改的那个技能目录**，立刻扫出真值。
    **判据：汇报里每个「已」字背后要有一条本次跑出来的命令输出；跑不了就写「改了但未验证」。**
19. **大改技能前先建版本基线；改完先删历史再删内容。** 用户明确表示自己「很喜欢大改 skill，很容易改到面目全非」，
    且要求「作为版本记录」——所以**没有回滚手段的大改本身就不能开工**。
    开工顺序：`git init` + 写 `.gitignore` + **首次提交当基线**（记录改之前长什么样），
    然后才动刀。`skills/` 若此前无 git，先建仓比先改更重要。
    ⚠️ **「历史」和「冗余」要分开量**：实测超标技能里文件内重复段落 0 条、历史类内容占比 2%，
    看似干净，但那是**没人给它加过修改日志**。反过来，被反复修过的技能
    （实测 318 行里 17 段形如 `P0 修复要点` / `P1/P2 修复要点（本轮）` / `P4 决策记录`）
    会变成**修改日志而非技能文档**——下一个用它的人得先读完五轮历史 bug 修复史才知道现在该怎么跑。
    **判据：`grep -cE '^#{2,4}.*(修复要点|本轮|第[一二三四五六七八九十]+轮|已修)' <skill>/SKILL.md` ≥3 就是中招。**
    正确处置是**新规则进正文、历史只留一行 + 指向 git log**，正文行数设上限（如 200 行），超了强制压缩；
    **不是继续往里追加段落**。详见 `references/version-baseline.md`。
    ⚠️ **「把目录拷一份进仓」不是基线, 是一次快照 —— 建仓之后工作副本会继续变, 两边必然分叉。**
    判据: 定期把仓内文件与工作副本**逐文件比对**(别比目录 mtime, 要比内容哈希), 差异数应当是 0;
    有差异时先看是不是「建仓之后又改过」。**快照与真身不一致时, 不知道哪边是新的** ——
    所以同步方向要靠提交内容判断, 不能默认「仓里的是旧的」或「仓里的是新的」。
    同理, 一个仓只有一两个提交时, 里面的文件从没经过它描述的那些历史改动, **不要拿它当回滚点**。

20. **审计结论落地时，必须同时改 description（触发词），否则整个审计是空转。**
    典型失效链：多模型审出「这个技能定位错了，用户不会主动调用」→ 只改了正文定位 → **description 一个字没动** →
    触发词仍只有那个用户从不说的窄说法 → 技能继续零调用，审计白做。
    **判据**：审计报告凡出现「定位/触发/应该怎么被找到」类结论，**`description` 就是交付物之一**，不是附带项——
    审计前后 `diff` 里必须能看到 description 变了。
    description 要写**用户真会说的词**（含动作动词与具体产物：「让 Pi 写个脚本」「帮我分析这份数据」「写个报告」），
    不写只有 agent 内部流程才会出现的术语（「派活前核对任务书八要素」——用户不会这么说）。
    **审计技能时顺手验一条**：`use_count` 低 + description 全是内部术语 = 上一次审计的结论从未落地。
    ⚠️ **description 会被截断，长度决定触发词能不能被看到。** 上限是 **60 字符**（`agent/skill_utils.py` 的 `SKILL_PROMPT_DESC_LIMIT`，实测值），
    超出部分在索引里变成 `...`，而 `skill_view()` 才读全文。所以「正文里写了 30 个触发词」不等于「我能想起来调用它」——
    全部触发词必须落在**前 60 字内**，否则路由信号为零（实测一个 659 字的 description，索引里一个触发词都没露出）。
    ⚠️ **但 60 是「硬约束」而不是「目标长度」——先问哪条规则在管这件事。**
    **本条管的是「别让触发词被截掉」（把最锐利的词放句首）；铁律 33 管的是「别把 description 写成功能介绍」
    （要写「何时不用」+ 反例）。两者不冲突，但都成立时 33 优先** —— 宁可让某个次要触发词落在 60 字外，
    也不能为了塞进 60 字而删掉排除边界。压缩时优先删「背景介绍」与「能力罗列」，它们才是可牺牲的部分。
    ⚠️ **别按更紧的自设值压**——曾按「索引截断到 57」连压四轮，压过头删掉了正文判据的核心触发词（「审计长尾」「检查脚本」），
    按真实阈值 60 重写时反而同时补回了触发词。**阈值必须读代码，且比实际留余量而不是比记忆。** 见铁律 14a。
    **判据：`len(description) > 60` 就该压，压的时候把最锐利的触发词放句首**，别留「背景介绍 + 触发词在后半段」的写法。
    ⚠️ **中英混排会偷字符数**：`Use when`+英文单词占 8 字符，写「58 字」的候选实测 66 字。压之前先量，不要凭感觉。
    压完顺手同步 `INDEX.md` 那一行——同一个描述维护两处，改一处忘一处就是版本漂移。
21. **把某个判据写进规则当门禁前，先验那个判据自己有区分度。**
    工具/评分器/检查器当门禁前，先跑**正样本 + 负样本 + 变体样本**（与铁律 17/18 同一要求）。
    反面实测：一个本地提示词打分器，空泛请求 25 分、补齐八要素的任务书 41 分、中等任务书 **42 分**——
    **补齐反而更低**；且只认中文关键词（英文任务书 0 命中）。若规则写「分数低就补结构」，会把派活带偏。
    机制：这类打分器按**关键词命中表**算分，不是质量模型，所以它认不出「结构完整但用词不同」。
    **降级用法**：只把它**硬编码的枚举/场景模板**当知识用，**分数只当提示、不当门禁**——
    规则文本里要显式写明，否则下一个会话会当成硬指标。
    判别式：「这个判据输出的是**测量**还是**查表命中**？」查表命中型的一律不能当门禁。

22. **删东西前先 grep 它的名字, 删完再 grep 一次。** 删一个技能或一个 support 文件, 引用可能藏在四个地方, 每一处漏了都是死链: ① `INDEX.md` 的表格行 ② **它自己 SKILL.md 正文里的路径提及**（含指向自己 `references/` 的）③ 别的技能的 `related_skills:` 或正文 ④ cron `jobs.json` 的自由文本。**第 ② 类最容易被忽略** —— 因为它藏在被删技能自己的正文里, 删目录时顺手一起没了, 断链却留了下来。动作: `grep -rn <名字> skills/ INDEX.md` → 逐处改 → 删完 `grep -rn <名字> skills/ INDEX.md` 必须零命中, 才算真删干净。
    ⚠️ **清引用时先分类再动手：活指针要删，历史记录要标注。** 两者都「含该技能名」，
    但删错了不可逆：用「行内含该名字就删行」的批量清理会连带抹掉**决策记录**——
    实测删一个技能时误删 7 处，其中包含用户自己上次的明确判断（「修，不弃」）和整节重叠分析，
    这些是**为什么当初这么决定**的唯一记录，删了以后没人知道能否推翻。**判据：**
    ① 目标是**指针**（路径、表格行、`related_skills:`、cron prompt）→ 删或改指向；
    ② 目标是**对它的评价/决策/复盘**（决策记录、重叠分析、体检结论）→ **绝不删**，在该处下方加一行
    「`<日期>` 已归档：<一句话理由>。备份在 `<路径>`」。**批量删完必须 `git diff` 看删掉的是什么**，
    拿不准的一律 `git checkout` 回滚——恢复的成本远低于事后发现历史被抹。

23. **备份命令成功退出 ≠ 备份里有东西。** 批量删除前的 `tar czf` 里, **路径写错(层级猜错、文件其实在子目录下)不会让命令非零退出**, 你看着 exit 0 就往下走, 到真出事时才发现归档里根本没有它。**判据: 备份之后必须把归档内容列出来数一遍**, 确认每个待删项都在里面 (`tar tzf <包> | grep <名字>`), 再执行删除。删除不可逆, 这一步的代价是 5 秒。

24. **`use_count=0` 有一个「已被解释」的分支, 查了再谈删。** 除了「刚建/刚重写, 还没被调用过」, 还有一类是**前置条件根本没启用**: frontmatter 里的 `requires_toolsets:` / `environments:` / `required_commands:` 指向当前环境不存在的东西, 于是它**永远不可能被触发**, `use_count=0` 是必然结果而非「没价值」。判据: 读 SKILL.md frontmatter, 拿这三个字段的值去实测环境里有没有 —— 有依赖但环境没有 ⇒「待条件启用」, 不是长尾。**把这条和「零使用即长尾」混为一谈, 会误删掉为将来某个环境准备的角色型技能**(例: 面向多 agent 看板流水线的验收角色技能, 在没有看板的机器上必然零调用)。真长尾仍是三信号交叉(载入 + 被引用 + 可执行物)叠加 ≥24 天未改, 见 `references/long-tail-inventory-audit.md`。
    ⚠️ **`use_count` 与 `view_count` 是同一个信号 —— 拿两者的比值当证据是错的。**
    源码里它们在**同一处被一起递增**（`tools/skills_tool.py` 的 `_skill_view_with_bump`：
    `bump_view(...)` 紧跟 `bump_use(...)`，注释还写着 "Viewing is actively loading the skill to act on it —
    that counts as use"），所以 `use_count == view_count` 是**必然**的，不是数据。
    实测把「使用/载入比 = 1.24」当成「载入的技能都真用上了、无误触发」的证据报给用户 ——
    那是**两个同义计数在相除**，恒等于 1 的比值不携带任何信息，结论当场作废。
    **判据：任何两个计数器相除之前，先读源码确认它们在不同的调用点递增；
    同点递增的一律不能当独立信号。** 要判「真用上了没有」得另找通道（产物时间戳、
    被引用次数、cron 是否提到它），`.usage.json` 里没有这个字段。

25. **要给技能加生命周期标签前，先读 `.usage.json` 的字段——这套模型已经内置了，别另造。**
    Hermes 自带 `state`（合法值只有 `active` / `stale` / `archived`）、`pinned`、`archived_at`、`use_count`、`view_count`，
    且**由 `skill_view` 等调用自动更新**。另造一套 `stable/active/draft/archive-candidate` 的后果是**两套标签并存且只有一套会更新**，
    半年后没人知道该信哪个。**判据：要设计任何「状态字段」之前，先 `json.load(.usage.json)` 打印一个样本看有哪些键。**
    同一条铁律的另一个方向：`pinned=true` 是**免删名单**，任何长尾清理必须先过滤它——库里 14 个 pinned 技能里有好几个
    `use_count` 极低（例如只在自己那台机器上才有意义的排障脚本），删它们等于删掉用户的显式保留声明。

26. **说「有 N 份副本 / 版本混乱」之前，先把真实路径拓扑查出来。**
    同一个工具链常有**多个技能根目录**并存（主库、跨工具通用库、某 agent 的私有目录），它们的关系有四种，
    **外观看起来全都是「同一批技能出现在多个地方」**：
    ① 软链到中央库（inode 相同，是设计不是重复）② 真拷贝且内容一致（真冗余）③ 真拷贝且内容已漂移（真混乱）④ 只在那一处存在（不是副本，是该生态独有）。
    **判据：`glob('**/SKILL.md')` 拿到的是「同名命中」，不是「副本」；必须再看 `os.path.islink` + `os.stat().st_ino`（同 inode = 同一个文件）+ 内容哈希比对**，
    并且把每个技能的**归属根目录**分列出来再说话。**只报「N 个技能同名出现在多处」而不区分这四种，等于没查。**
    ⚠️ 更隐蔽的一种：多个根目录里**没有一个是「中央库」**——各自的软链指向各自的目标，压根不存在需要统一的源头。
    实测连续两次据「同名即副本」下达「唯一真问题是那 1 个真拷贝」的结论，两次都错，第二次还错在**路径层级写错**（同名技能同时存在于两个根目录，
    比对时只查了其中一个，就断言另一个不存在）。**连报两次错之后不要再补细节，直接把全部根目录的拓扑打出来。**

27. **「有调用没产物」和「有产物没人用」是两个不同的问题，判据不能互换。**
    - **调用 ≥10 次却只有 `SKILL.md`**：大概率是**纪律型技能**（判据/清单/流程），天生纯文本，**不是浪费**。判别式：**这个技能的产物是「我读完之后怎么判断」，还是「一个能跑的东西」**。前者零脚本是正确的，后者零脚本才是缺陷。
    - **有脚本但 `SKILL.md` 正文从未提及**：分两类——真孤儿（补一行指引，铁律 8）／**测试文件**。**`tests/` 目录测的是技能内部实现的正确性，而技能是被 agent 当文本读的、不是被执行的**，测试目录的体积不会换来任何运行时能力。
    - **判「一个技能是不是 Python 项目而非技能」**：看有没有 `pyproject.toml` / `uv.lock` / `tests/` / `eval_history.jsonl` 这种第三方软件包指纹。真有的话，`SKILL.md` 通常只占个体积的个位数百分比——**这时「技能体积大」是统计口径问题，不是技能本身臃肿**。
      顺带查它的依赖装没装：**依赖缺失 + 没有定时任务 = 已经停止产出的半瘫痪状态**，这比「体量大」严重得多，因为它的 `use_count` 和产出记录都停在过去某天，看上去像还在用。

28. **判断两个技能是不是同一件事、以及外部框架要不要装，都以「本机执行链缺哪一步」为准。** 四个配套判据见 `references/overlap-detection-and-external-tradeoff.md`：
    - **关键词扫重叠只得到候选**：实测一轮扫 84 个技能、按 spec 概念命中 4 个，读正文后**3 个是假阳性**（词被借用 / 同名不同层）。命中行数 ≥2 才进人工分诊，**只读 description 不算**。
    - **合并前跑「交接测试」**：一方明文写着「某类活见另一个技能」⇒ 分层，**不合**。主题相邻（「都讲验证」）不是职责重叠——各自挂着具体命令（`wc -l` 对账 / `--guess` 统计 / `pi_probe.sh` 探活）时，合并必丢命令。
    - **单向引用是缺陷**：`grep -c <对方技能名> <B>/SKILL.md` 为 0 就是单向。补法是在 B 的**第一步**加前置指针，不要加在末尾「相关技能」区。
        - **估「能砍多少」先量交集，职责名不算证据**：「手机访问归手机技能管」这类推断实测常错（伞形 2136 行里专用技能只覆盖 5%，该砍的 195 行只被覆盖 3 行）。先逐行求交集拿百分比、再逐 ref 展开定位，并报价独占行数——整体 5% 可能集中在单个 ref，按整体比例决策会错杀其余39 个。
    - **外部流程框架（spec-kit / BMAD / superpowers 类）先比阶段再比体量**：本机已有阶段不补，只补空的那一步，且**规则条数 ≤10 就抄进已有执行链**，>10 且要求用户改变交互方式才考虑装。

29. **退役一个技能前，拿它自己的产出反查——误报率比 use_count 有说服力。**
    `use_count=0` 只说明没人主动载入它（铁律 24 已给三个例外分支）；
    但一个**每天自动跑的自我分析/体检类技能**，它的价值不在被载入，而在**它报的结论对不对**。
    跑一次它，然后把它报的每一条「弱点」逐条独立核实，再算留/删：
    - 真问题 → 证据成立；
    - 误报（判据本身错）→ 修判据的成本要算进留不留的账；
    - **数字本身错**（分母/窗口口径不对）→ 最严重，说明整套指标不可信。
    实测一个自我分析技能跑出 5 条「弱点」，逐条核实后：2 条误报、1 条数字错（报 27/76，
    全量拉真值 163/314，差在窗口只取 7 天 + 警告块重复计数）、1 条真问题靠**一条独立 SQL**
    挖得比它准、1 条当场改对。**5 条里没有一条是「读了它的报告才知道」的** ⇒ 删。
    **判据：把它最近一次产出里每一条都独立验一遍；验不出来的那些不构成留它的理由。**

    **配套结构检查：SKILL.md 描述的核心流程，可能依赖一个从未安装的外部项目。**
    技能正文写「跑 self-evolution 做技能自进化」，而它 `references/` 里躺着一份 29KB 的
    **别人项目的 README**（带外部 `author` / `version` frontmatter）——依赖模块全盘找不到，
    这条路径从来没通过过。**查法：正文里出现「运行/跑 <某个命令>」的流程段时，
    逐条验那些命令/依赖在本机存不存在；存在才算这条流程是活的。**
    与铁律 27 的「依赖缺失 + 没有定时任务 = 半瘫痪」同源，但这条更隐蔽——
    它藏在 `references/` 里而不是 frontmatter 的 `requires_*` 字段里，`use_count` 也看不出来。

    **退役带「自动修复」能力的工具，必须额外扫一遍它写进库里的产物 —— 只删它自己的文件不够。**
    这类工具把「修复」实现成**写操作**（自动补技能 / 自动 patch / 自动建索引），
    于是误报会落成既成事实，下一轮它读自己的产物还会算成成绩。
    实测：一个分析器跑一次就在库根目录生成 8 个技能，全部 `mtime` 相同、
    frontmatter 带 `generated_by:`、正文是同一段模板套话（含 `unknown error` 占位）。
    **它们不在索引里** —— 索引只扫 `<根>/<分类>/<技能>/`，
    所以任何以「索引」为视野的清理都看不见它们。

    ⚠️ **扫产物要按「内容标记」而不是「目录名像不像垃圾」** —— 这一条最容易只做一半。
    实测：先 `ls` 库根目录、凭名字判断（`csv-parsing` / `docker-management` 看着像垃圾），
    删掉 8 个就收工；后来按 `generated_by:` 标记全库 grep，又挖出 9 个，
    名字是 `terminal-run` / `read-file` / `session-search` —— **每一个都像正常技能**，
    只看名字绝不会怀疑它们。判据：**凡「找某类产物」，一律用内容标记 grep，禁用目录名/文件名筛。**
    同一故障两次落在同一条规则上（铁律 19 的「同名命中≠查过了」），这是第二次。

    动作（在删工具**之前**跑，先保住溯源线索）：
    ```bash
    # ① 自报出身的产物
    grep -rl 'generated_by:' ~/.hermes/skills --include=SKILL.md
    # ② 同批次产物：mtime 落在该工具上次运行时刻附近的一簇
    find ~/.hermes/skills -name SKILL.md -newermt '<该工具上次运行时刻>'
    ```
    **第 ③ 条最关键 —— 对账**：`glob('**/SKILL.md')` 数出来的技能总数，必须与
    INDEX.md 头部的 `Skill 总数` 一致；对不上而多出来的那批，通常就是漏在分类目录之外的产物。
    与铁律 22「删完 grep 必须零命中」配对：那条查**指针**，这条查**产物**。

30. **自写全库检查器只做静态判据，不要靠「跑一下看结果」判断脚本好坏。**
    「把每个脚本执行一遍看它报不报错」会产生大量与被测物无关的假阳性。
    **核心 8 条**：
    1. 静态先查干净：`ast.parse` 验语法、`bash -n` 验 shell、路径存在性验指针
    2. 名字解析单独一道：`ruff check --select=E9,F63,F7,F82`（语法+未定义名+不可达+坏比较）
    3. ruff 规则只取 5 条，不要全开（全开报 120 条噪音）
    4. 未定义名可能藏在"平时走不到"的分支里——接口正常时永远不崩，恰好在节点池空/上游挂掉时才炸
    5. 挂 cron 前必须验它不是哑巴：正常→静默、注入坏态→必须报、撤除→恢复干净
    6. 报警正文的排版也是交付物——逐条重复前缀 = 用户读不懂
    7. 环外不变量报「判据被篡改」时，先证伪再上报——假阳性会让这道闸失效
    8. 静态检查器只能证明「结构没坏」，不能证明「逻辑没问题」——报这个结论前先实测检出率

    **完整案例与细节**（假阳性三来源、ruff 规则选择、环外不变量对账、回归测试、死链检查器选型）
    → `references/static-checker-design.md`
31. **工具会静默死掉——用它之前先实跑一次，尤其是「唯一一道闸」。**
    一个只被 agent 调用的体检/检查脚本，坏了不会报错、只会没人再用它，于是**闸门形同虚设却一直显示绿灯**。
    实测「开源前泄露体检」脚本存在一个三元表达式嵌在元组字面量里的 `SyntaxError`，
    `import` 即崩——而它是判断「能不能传 GitHub」的唯一一道闸，坏多久完全无从得知（脚本自己不记时间戳）。
    **判据：① 体检/门禁类脚本要有「新会话第一次用它时必须实跑一次」的纪律，而不是「建过就行」；
    ② 更根本的做法是把检查逻辑收进**每次都会跑的常规体检**（`skill_repo_doctor.py`），
    而不是一个需要人记得去调用的独立脚本——能被动触发的检查才不会被遗忘。

32. **改完技能走一道「派生件清单」，别等下一个会话发现版本漂移。**
    技能**不是只由 `SKILL.md` 构成**。改完它，至少这几处可能一起需要动，漏一处就是不一致：
    | 派生件 | 何时必须跟着改 | 漏掉的后果 |
    |---|---|---|
    | `INDEX.md` 那一行 | 改了 description 或删/建/归档 | 索引与正文两套描述并存 |
    | frontmatter `related_skills:` | 改了职责边界或指向的技能被归档 | 活指针断链 |
    | **别的技能正文里提到它的地方** | 改名 / 归档 / 改了触发条件 | 对方技能教错路 |
    | cron `jobs.json` 的 prompt 自由文本 | 同上（cron 里常有一句完整的人话描述） | 无人值守任务指向已不存在的技能 |
    | 铁律 / references 里引它的判据 | 它被归档或行为变了 | 规则文本指向空处 |
    | **本技能正文里新增的 references 指针** | 写指针的同一次改动 | 指针指向不存在的文件（见下） |

    ⚠️ **写 references 指针与写那个文件必须是同一次改动 —— 指针先行就会留下死指针。**
    写「本判据的展开见 `references/xxx.md`」时若先落指针、文件下一次才补，
    中间任何一次体检/交接都可能把一个指向空处的指针交出去，而它看起来完全正常。
    实测：给三条新铁律写交叉引用时，指针进了 SKILL.md 而文件不存在，
    靠「指向的路径看起来对」完全看不出问题。**动作：写完指针当场确认文件存在再收工**；
    与铁律 11「写完文本立刻跑一次 lint」同源——那条管断链，这条管空文件。

    **判据: 交付前 `grep -rn <技能名> skills/ INDEX.md ~/.hermes/cron/jobs.json` 一次**,
    逐处问「这条描述现在还成立吗」—— 不成立的改, 描述的是历史决策的**加一行归档说明而不删**（铁律 22）。
    **动作清单构成执行保证, 规则文本不构成** —— 已实测两次「规则写进 playbook 后下一轮仍漏同类指针」。
    配套: 这条清单与 `skill_repo_doctor.py` 的**九项检查****互补不重叠** —— 检查器验「引用的文件在不在」,
    这条验「引用的**说法**还对不对」。后者只能人读。

33. **description 写路由条件，不写功能介绍——且「何时不用」和反例是必填项。**

    来源：bojieli《深入理解 AI Agent》第 2 章。description 是**唯一的路由信号**，
    它应当「明确写出何时使用和**何时不使用**的边界，并给出**几条典型反例**」；
    「描述太宽泛（如 `help with backend`）等于任何后端相关的工作都能触发，路由就会失准」；
    「何时该用我」比「我能做什么」重要得多。

    现状：`Use when …` + **≤60 字符** 的格式**从设计上就排除了负边界和反例**，
    剩下纯正向触发词。2026-10-02 为 `android` 的三条描述改了三轮（各加一条否定边界），
    每次都卡在字数上限 —— 这不是措辞问题，是格式禁止了这块信息。
    旁证：bojieli 自己 22 个 skill 的单行 description 实测 118–248 字（中位约 200），**全部超过 60 字符**。2026-10-02 实测数字，此前写的「21 个 / 150–200 字」不实已改。

    **判据：写完 description 后自问「有没有一句是排除用的」**。没有 → 路由会误触发。
    字符上限让位于路由信息量（与铁律 20 的优先级关系见那里）。

    **指纹：同一个 description 反复改措辞却总改不动** —— 多轮都在「换触发词」而没有一条是排除句，
    **从格式上就写不出负边界**。这时该改的是格式约束，不是措辞。
    另一个同族信号：审核时「多派几个审稿人」得到的一致批评是「描述太宽泛」，
    但按字符上限根本写不出更精确的描述 —— 批评与约束冲突时，先信约束这条线索。
    **可行配方（2026-10-02 实测，否定边界放尾部即可装进 60 字）**：
    `_normalize_skill_description` 超 60 才截到 `57+"..."`，所以写法顺序决定生死 ——
    **把「何时不用」写在最后，别放开头**。实测 4 组：否定在尾部/中段/前部/超长，
    只有「否定在尾部」能在 60 字内容纳。写成
    `Use when <触发>（非<易混场景>）。` 或 `...（<X>交<Y>）。`

    **实测现状（别再当缺口重复做）**：79 条里 **0 条被截断**（上限没在截东西，
    是主动写短的）；**12 条已含否定边界**（dashboard/webshell/relay/gateway/
    selfhost 一簇是今天下午刚加的）。**60 字装得下负边界** ——
    `hermes-dashboard-access` 56 字同时含触发 + 反例指向 `selfhost-local-debug`。

    ⚠️ **别把「缺否定边界」做成全库计数 —— 它只在「有易混兄弟技能」时才成立。**
    实测按全库扫「description 里有没有 `非/不用/交`」得到 61/89 = 69%，看着是最大缺口；
    逐条读下来，**有边界的那些全部位于有兄弟的家族里**（安全审计三件套
    `security-audit`/`skill-security`/`llm-security`、网关排障簇、技能治理
    `skill-forensics-tooling`/`skill-library-curation`、双机簇），
    而无边界的多数**根本没有邻居**（`github`、`china-briefing`、`commodity-price-tracking`、
    `android-apk-analysis`）—— 没有可能被混淆的对象时，负边界是纯字符浪费。
    **真缺口只有 2 组**：`system-doctor` ↔ `system-health-check`（单项异常 vs 全栈体检）、
    `network-throughput-measurement` ↔ `network-management-system`（纯测速 vs 断网排障）。
    名字前缀相同 ≠ 同族（`local-vlm` 看图 vs `local-voice-transcription` 听语音，语义不重叠）；
    要按「用户会不会用同一个词问到两者」判，不是按前缀。
    **判据：先给技能分家族，只在家族内部查有没有互斥句。**
    「缺 X 的百分比」会把「不需要 X 的」算成「缺 X」—— 69% 与 4.5% 的差别全在这里。

    **🔴 我算错过一次，别再犯**：我曾用中文 2-4 字滑窗统计出「dashboard 被 5 条抢」，
    当成真缺口。**逐条查证是假的** —— 5 条里只有 `hermes-dashboard-access` 的
    触发段含 dashboard，另外 4 条的 dashboard 都在**负边界段**
    （`（非dashboard白屏）`、`（dashboard交专属技能）`），那正是它们正确地让开。
    73 条 description 的中文触发词**没有任何片段被 3 条以上共用**。
    滑窗统计的错法：2-4 字把「各交各的专技能」切成 '各交各的'/'专技能'，
    同族技能的样板中文全命中同一碎片词 —— 实测因此误报 6 条、真信号 0 条。
    **判据：断言「某词被 N 条共用」之前，必须逐条打印那条词的触发段看它在不在触发段里。**

    体检器第 9 项 `check_desc_collision` 只查**拉丁技术词**（端口/命令/服务名），
    中文那半边**查不了**（要分词器，另一个依赖）。它全绿 ≠ 路由没问题。

    **⚠️ 上限不在本技能里**，在 `agent/skill_utils.py` 的 `SKILL_PROMPT_DESC_LIMIT`
    （agent 不能随手改，铁律 16：阈值要从代码读）。所以「让上限让位于路由信息量」
    目前**没有可执行落点** —— 这是规则文本，不是执行保证（铁律 32）。
    真要放开得改源码，那一次改必须重跑全库体检。

34. **技能规模要对应披露策略，两者别混为一谈。**

    来源：bojieli 第 2/4 章。「形态决定每条能力常驻多少 token、参数怎么传、谁能改；
    **披露策略决定有多少条同时摆在模型面前**」——**两个独立决策**，别把两者混为一谈，
    也别把「全量常驻」当默认。

    书上给的三层解法（**不是**一张条数分档表）：层次化组织与按需加载 →
    主动工具发现（元工具 + 服务器级→工具级两层语义路由）→ Skills 渐进式披露。
    书里的量化门槛只有一处：**工具数量超过一百个时容易出错**；
    「只暴露索引」是 Cursor 的做法（A/B 见原书）。
    本技能早前写的「十几/几十/上百/上千」那张分档表**没有出处，已删**。

    现状：79 条（73 实体 + 6 软链）按「全量目录常驻」处理，没有层次化组织，
    也没有检索层。**注意 79 < 100，按书上那唯一一条量化门槛尚未越线** ——
    但第 4 章点名的陷阱是另一回事：「只做索引不做检索，也不做层次化组织，
    **索引本身长得和全量列表一样**」。79 条平铺已经长这样了。
    另有一份 `INDEX.md` 与 description 并行 —— 书里路由信号唯一地放在 description，
    **多一份要保持一致 = 多一个漂移源，且不解决检索问题**（铁律 32 的三向一致性检查
    本质是在给自己擦屁股）。**冲突未解**：34 说 INDEX 是债，20/32 又在强制维护它，
    同一技能里两条并存，重做披露策略时须先定哪条优先。

    **判据：目录长得和全量列表一样时就该重新决策披露策略**，而不是继续往常驻目录里塞。
    与条数无关。
    相关：ch2 的位置偏好实验——模型对上下文首尾分配更高注意力，
    79 条平铺里真正相关的那条常落在被忽视的中部。

    **派生件联动**：改 description 后必须重建 `INDEX.md`（铁律 32 第一行）。

36. **规则要指向一个本技能能改的东西——阈值在源码里，规则就没有可执行落点。**

    写铁律时先问一句：**这条判据的阈值/开关在本技能范围内吗？**
    不在的话，规则只是一句**诉求**，不是**可执行保证**（铁律 32）。
    实测：写「description 长度要让位于路由信息量」时，那个上限根本不在本技能里，
    而在 `agent/skill_utils.py` 的 `SKILL_PROMPT_DESC_LIMIT` —— agent 不能随手改。
    于是这条规则在库内**没有任何可执行落点**，却会一直“看起来已被处理”。

    **三条动作：**
    1. **在规则里显式写明落点在哪**（哪个源码常量 / 哪个配置文件），
       写「上限在 `agent/skill_utils.py` 的 `SKILL_PROMPT_DESC_LIMIT`，本技能改不了」。
    2. **在规则里写出“当前无落点”**并给出真要改时的代价（改源码必须重跑全库体检）。
    3. **别把“写进规则”当成“已整改”**——汇报时给第三个数字（铁律 35 已要求）。

    **指纹：规则的「应当」与现状长期不符，而没人报这个矛盾。**
    判据：库里一条反例都没有，规则却写着“应当带反例”——下一个会话读到会以为已按此整改。
    **动作：判据落地时把「现状与判据的差距」写进规则本身**（铁律 33/34 的「现状」段就是这个作用）。

    **通用形式：判据的载体不止 SKILL.md。** 阈值可能在源码常量、可能在**插件的配置文件**、
    可能在 harness 代码里；而最后一类最隐蔽——写在可变的配置文件/提示词里的约束**会被改掉**。
    **判据：问“这个数字/开关被改时，我需要改几个文件、其中几个在本技能之外”。** 大于 0 就要在规则里写出来。

37. **行为规则累到二三十条时，先量孤岛率与冲突，再加规则——条数不是问题，无仲裁才是。**

    实测一个 32 条的行为规则集：**10 条（31%）是孤岛**（不引用、也不被任何其它条目引用），
    而它们正是将来两两打架时无法互相定位自己的那些。

    **先量（别凭印象，实测「36 条」实为 32 条）**：用正则切条目、统计每条的交叉引用，
    得出孤岛率 / 载荷失衡 / 编号是否按时间排。三个指标缺一不可。

    **模型不能靠自觉仲裁规则冲突**——Anthropic 官方承认矛盾时 Claude「may pick one arbitrarily」；
    ConInstruct 实测冲突检测 F1 87.3% 但**主动上报仅 45%**。所以：
    ① 给规则分层（L0 安全不可逆 → L1 用户当轮 → L2 现实 → L3 流程 → L4 硬纪律 → L5 优化类 → L6 方法论），
    **🚨 最常见的漏洞是把「不可逆要确认」与「少写代码」放同一层**——后者会理所当然地压掉前者；
    ② 冲突时**先问「这两条管的是同一个轴吗」**——多数冲突不是二选一而是两个轴，
    「静默 vs 必须给证据」的正解是「不主动推送 + 回复内必带证据」，两条都守住；
    ③ 同轴才仲裁，且**先明说冲突再选边**，不许默默挑一条（默默挑 = 下轮原地复发）。

    **新增条目前必查**：先搜现有条目避同源分裂；确实冲突就在新条目里写明与哪条冲突、怎么共存。
    现成件（promptdiff / AgentLint / ConInstruct）只能查**文本形态**的矛盾指令，
    **语义冲突查不出来**，别指望装工具就解决。

    → 完整方法、脚本与工具清单见 `references/rule-set-conflict-governance.md`

14c. **批量引进外部技能包前，先量description 规范符合率 —— 它决定的是「抄」还是「装」。**

一个技能包动辄几十个子技能，而 description 的写法规范**按 harness 而定**：
Claude Code 系用 `Use for <用途>`（陈述能力），Hermes 用 `Use when <触发场景> + 反例`（陈述路由条件）。
两者**不是同义改写** —— `Use for authorized source-code security review` 直译成
`Use when authorized source-code security review` 语法不通（缺 when 引导的完整条件句）。

实测一个43 子技能的外部包：合规 3 / 不合规 40，开头形态为 `Use for` 25 个、块标量 `|` 10 个、
其余 8 个各不相同。**批量替换解决不了** —— 前者要逐个重写成路由句，后者要专门解析块标量。

**装之前必须先跑一遍统计**（一条命令，出四个数）：
```bash
grep -h '^description:' <包>/skills/*/SKILL.md | sed 's/description: *//' \
  | awk '{print ($1=="Use"&&$2=="for")?"Use for":($1=="Use"&&$2=="when")?"Use when":($1=="|"?"块标量":"其他")}' \
  | sort | uniq -c
```

**按结果选动作，不要默认「全装」或「全不装」：**

| 符合率 | 含义 | 动作 |
|---|---|---|
| 全合规 | 同一 harness 写的 | 可整装 |
| **少数合规 + 多数不合规** | 异 harness 写的 | **只挑合规/高价值的少数装**，不合规的不重写 |
| 几乎全不合规 | 为别的生态写的 | **只抄方法论，不装技能** |

**判据：「要不要为它重写 43 个 description」是个真实的成本项，要在汇报里报价。**
一个用户场景用不上的技能包，重写完仍然用不上——那笔钱花在了零价值的地方。

**区分「技能」与「方法论」再决定装不装。** 大包真正值钱的是它沉淀的**方法论**
（证据链格式、路由回归测试、同意门措辞），而方法论可以**手抄进已有技能**，
不需要连带装几十个子技能 + 几十个重写过的description。
**判据：问「我要的是它的能力，还是它的做法」—— 要做法就抄做法。**

**配套：只挑少数装时，抄进来的那两个也要实测。** 带脚本的外部技能
先跑它自带的测试（`python3 -m pytest tests/ -q`）再拿真实数据跑一遍，
确认不是「文件搬过来了但跑不动」。

35. **外部审稿人对「你自己的系统」有盲区——他们的「缺失」断言要回源核实。**

    把外部资料（开源书 / 框架 / 审稿 agent）拿来对照自己的设计时，它们的结论里
    混着一类**结构性的错**：**它们按「一个通用实现会长什么样」来审，
    而你的系统里有它们没见过的东西**。实测一次三方审读里，
    「你缺轨迹层/会话检索入口」「你缺业务状态层」「写入失败率是最可靠的验证器信号被丢掉」
    三条批评全部不成立——`session_search` 一直在工具列表里、`state.db` 有六万条消息、
    那次失败率的成因是我的**工具调用参数格式错**而非 Agent 行为缺陷。

    ⚠️ **多数票也会错，而且会错得很整齐。** 三方审读里两方独立提出同一根因（输入被截断），
    而实测那条规则的阈值从未触发过（样本最长 500 字符 / 阈值 700）。**两票同向不等于对**——
    审稿人共享同一套推理习惯时错误也同向，而「都这么说」会让人放弃查证。
    **判据：多个审稿人给出同一根因时，仍要拿一条能证伪的实测去撞它**（打印真实样本的输入长度、
    跑一次会触发那条规则的分支）。撞不倒才收；撞倒了要**在汇报里写明哪几票被推翻**，
    否则下一个人还会被同一个伪根因带走。

    与铁律 15/17/18 同源（**「它没有」≠「它不在」**），但指纹不同：
    那几条是「我的抓取/解析失败」，这条是**「对方对被审对象无知」**。

    **判据：审稿人说「你没有 X」时，先 `grep` / `ls` 一次确认 X 真的不存在再采信。**
    成本一次搜索，省掉把不存在的缺口当成待补项写进规则。

    **外部审稿人的三类结构性失败（实测）**：
    - **重复循环**：给大规模扫描任务（如"检查 90 个文件"）时，模型可能陷入重复循环，
      响应被系统停止（`Response Stopped — Repetition Detected`），零产出。
      解法：分批（每批 20-30 个），或要求"简洁输出，不要重复"。
    - **假阳性率高**：报告 11 个问题，验证后只有 1 个真问题。9 个"断链"全部 `exists=True`，
      1 个"凭据"是讲解 `api_key:` vs `key_env:` 用法（不是真泄露）。
      **解法：审稿结果必须人工验证，不能直接采纳。**
    - **覆盖率不足**：报告检查了 83 个，实际有 90 个。
      **解法：用 `find ... | wc -l` 独立核对总数，不轻信审稿人的计数。**
    **而且要区分两类断言**——「设计差异」（如只做手写 vs 自动分层）是真差异，
    「功能缺失」（如某个入口/能力不存在）通常是他们没查。
    **凡「功能缺失」类断言，逐条实测后才进规则**；只有设计差异类可以直接收。

    **配套：派多个审稿人时，要求每个只报「读到了什么 + 依据出处在哪」。**
    没给出处的断言先归入待核。收敛判据同 `references/overlap-detection-and-external-tradeoff.md` §8b
    （多派几个不等于换模型），§8 负责「先验真伪与危害量级」。

    ⚠️ **但「审稿人的盲区」与「我自己的覆盖率」是两个不同的问题，都要主动报出来。**
    验完对方之后还要自查**自己实际读了哪几篇、落地了几条**——
    实测一次三方对照：对方三个来源，我只精读了其中一个来源的 3/24 篇；
    落地的也只是判据没改实现（79 条描述一条反例都没有、全量常驻未动），
    而汇报若只写「已吸收三方判据」，读的人会以为机制已经变了。
    **判据：凡「已借鉴 / 已落地」类汇报，必须同时给出三个数——读了几个中的几个、
    落了几条判据、有几条判据对应的实现还没动。** 第三个数字是留给下一轮的待办；
    隐去它等于把「写进规则」当成「改好了」。

    **指纹：写进规则的判据与当前实现矛盾时，规则本身会开始骗人。**
    一条判据说「description 该带反例」而库里一条反例都没有时，
    下一个会话读到它会以为「已按此整改过」而跳过。
    **动作：判据落地时把「现状与判据的差距」写进规则本身**（铁律 33/34 的「现状」段就是这个作用），
    不要只写「应当怎样」。

    ⚠️ **临时备份不要落在会被发布的目录里。** 验证检查器新判据时习惯性在它旁边
    `cp` 一份做回滚点，那份 `.crit_bak.py` 就留在了技能的 `scripts/` 下：
    语法合法所以所有检查都放行，它却带着**旧判据**（扫描根挂错、键名不一致的那一版）
    一起出现在技能的脚本清单里。**动作：回滚点放 `~/.hermes/cache/trash/` 或仓外**，
    不要放在会被扫、会随技能发布的位置（与铁律 6 备份放活动目录外同源）。


1. 归档源技能到 `.archive/`（**逐字节验过**与备份一致）。
2. 改外部引用：`skill_view(旧名)`、正文旧名、**目录路径形态** `skills/<类>/<旧名>/`、cron jobs.json。
3. 重建 INDEX：`scripts/register.sh`——脚本刚被搬过位置时，**人眼确认它打印的目标路径与产物落点**。
4. 复跑两个工具，比对**前后计数**：`skill_product_audit.py`（ORPHAN/BROKEN/SIZE）+ `skill_ref_lint.py`（致命未降级）。
   - ⚠️ **主文件变薄 `ORPHAN` 会暴涨**（判据只算 1 跳）；收口 = 末尾补**附属文件索引**，别放宽工具判据。
     详见 `references/merge-execution-discipline.md` 第 19–24 条。
   - 复扫拼接体指纹：`grep -rc '^## 源模块:' <skills> --include=SKILL.md | grep -v ':0'`。
5. **交付前**先写预测（`flows/calibration-log`）：这次预计会在哪类事上出错 + 自评把握。贴进汇报第一屏。
6. 派 Codex 独立查验：`codex exec --sandbox read-only --skip-git-repo-check`（防它热心地重写半截文件）。
7. 收尾时再主动扫一遍"深指针三形态"——**审计工具只在合并那一刻查，之后新增的编辑不会再查**。
   ⚠️ 实测：这条规则写进 playbook 后，下一簇仍然漏了同类指针（校准日志 C-002/C-003）。**规则不构成执行保证，动作才构成。**
8. **交付后**对账：`calib.py settle <ID> --verdict hit|miss --actual "<Codex 结论>" --cmd "<可复现命令>"`
   （判 miss 必须给 `--new-class`，否则脚本报错——生存者偏差防护）。

38. **找技能前先查本机仓库自带的 `skills/` 树——bundled 技能默认不在 `~/.hermes/skills/` 里。**

    Hermes 仓库里带着整套 bundled 技能（`<repo>/skills/`）与 `optional-skills/`，
    但它们**默认不会被装进 profile 的 `~/.hermes/skills/`**。
    于是 `skills_list` / `skill_view` 都看不到它们——**而「看不到」不等于「没有」**。
    实测一次要处理 Gmail 批量操作，直接去 GitHub 搜外部技能 + 手搓裸 IMAP 脚本，
    踩了三个坑（Gmail 的 EXPUNGE 语义、UID 跨文件夹漂移、误删邮件）之后才发现
    仓库里早就躺着官方的 `google-workspace` 技能。用户当场判定「你在瞎搞」。

    **动作（顺序不能反）**：
    ```bash
    hermes skills list                       # ① 已装的
    ls <repo>/skills/                        # ② bundled，可能没装
    ls <repo>/optional-skills/               # ③ 可选的 bundled
    ```
    ②③ 命中就直接拷进来，不需要外部搜索：
    ```bash
    cp -r <repo>/skills/<类>/<技能> ~/.hermes/skills/<类>/
    ```
    拷完用 `hermes skills list | grep <名>` 确认它真的被加载（不是「拷了就生效」）。

    **判据：用户问「有没有能干 X 的技能」而 `skills_list` 里没有时，先 `ls <repo>/skills/`，
    再考虑外部检索。** 外部检索（GitHub / `npx skills` / 网页）是第三条路，不是第一条。

    ⚠️ **bundled 技能是只读的（protected），但装进来的副本可以改。**
    需要收窄 scope / 改配置时改 `~/.hermes/skills/` 下的副本，别去改仓库原件。
