# 唤醒率实测（真调API 的那条路）

> 铁律 37b 说「真唤醒率要真调一次API」——这里是那条路的做法。
> **先读判据：这条很贵，跑之前先过闸。**

## 什么时候才真跑

| 前置 | 动作 |
|---|---|
| `scripts/skill_trigger_regression.py` 10/10 | **别跑**。描述可读性已够，别拿成本换置信度 |
| 脚本有 MISS，且用户明确要证据 | 跑，且**汇报里必须写清样本量**（5 条话术 vs 87 个技能，样本量本身是结论的一部分） |
| 想验证「改了 description 有没有用」 | 跑，但**必须带对照组**，见下「归因陷阱」 |

---

## 做法

```bash
mkdir -p ~/.hermes/cache/wake_test && cd ~/.hermes/cache/wake_test
# cases.txt: <真实话术>|<期望技能>
while IFS='|' read -r text exp; do
  timeout 400 hermes chat -q "$text" -Q --provider nousfree
done < cases.txt
```

话术必须是**用户真说过的原话**，不是你想出来的标准指令。
自造话术会显著高估命中率——它天然贴着description 的措辞。

---

## 三个坑

### 1. `hermes chat -Q` 不落request dump ⇒ 读不到「实际加载了哪些 skill」

`sessions/request_dump_*.json` 只在部分调用路径生成，CLI 短问路径**不写**。
所以「去看它加载了什么」这条路直接不通。

**替代判据：指纹词法。** 给每个期望技能挑 3–5 个**独有**指纹词
（独有的命令名 / 参数名 / 反直觉的产物名），在回复文本里 grep。

⚠️ **单向有效**：提到 ⇒ 大概率真加载了；没提到 ⇏ 没加载
（模型照常识做也能命中）。**所以它只能报「确认唤醒」，报不了「漏唤醒」。**
要判漏唤醒，读回复**行为**——它做的是不是那件技能特有的事。

### 2. 归因陷阱：改完 description 再跑，测不出改动有没有用

模型可能**本来就知道**那条规则。实测一条「删掉旧脚本」唤醒成功，
回复里引用的是用户长期规则里的删除门槛——**跟这次改的 description 无关**。

**要归因必须跑对照**：改前跑一批、改后跑同一批，只认**两次的差**。
单次跑通不是改动的证据。

### 3. 负样本：不放一条「输入不成立」的用例，会把「任务不成立」误判成「漏唤醒」

实测「审一下这段源码有没有洞」配一段提示词文本 → 模型回「这不是源码」，
**没加载技能是对的**（任务不成立），记成漏唤醒就是误判。

**每个批次至少一条这种用例**，用来区分「技能没醒」和「这活根本不该走技能」。

---

## 汇报口径

跑完只报三件事，**不要外推**：

1. 样本量（几条话术 / 库里多少技能）
2. 确认唤醒的条数 + 每条的**行为证据**（不是关键词命中）
3. 剩下的说「没跑」或「判据不成立」——**不猜**

⚠️ 5 条里3 条成功 **不支持**「技能库唤醒正常」这种全库结论。
能说的只是「这5 条里 3 条触发正常」。
