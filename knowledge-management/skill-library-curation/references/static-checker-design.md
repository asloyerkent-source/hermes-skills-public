# 静态检查器设计：案例与细节

> 从 SKILL.md 铁律 30 外移（2026-10-10）。
> 触发时机：**改 `skill_repo_doctor.py` 或写新检查器时**读它。日常体检不需要。

## 坑：清空列表后没跳过报告逻辑

`_curator_backed` 返回 True 时原来写 `changed = []`，但没跳过下面的 `issues.append`——
于是拼出「判据文件被改动：」（空列表）的假警报。
**修法**：用 `skip_report` 标记 + `if changed:` 包裹 `issues.append`，让流程继续走到基线续期。
**通用形态**：清空列表/集合后，后续代码若仍引用该变量做字符串拼接或 append，会产生空值假阳性。
**注意**：`return False` 会跳过基线续期逻辑，导致下一轮仍拿旧基线比，重复报同样的错——函数无返回值时不能 return，只能用标记跳过。

## 核心规则（SKILL.md 保留 8 条）

1. 静态先查干净：`ast.parse` 验语法、`bash -n` 验 shell、路径存在性验指针
2. 名字解析单独一道：`ruff check --select=E9,F63,F7,F82`
3. ruff 规则只取 5 条，不要全开
4. 未定义名可能藏在"平时走不到"的分支里
5. 挂 cron 前必须验它不是哑巴
6. 报警正文的排版也是交付物
7. 环外不变量报「判据被篡改」时，先证伪再上报
8. 静态检查器只能证明「结构没坏」，不能证明「逻辑没问题」

## 案例与细节

- **改完技能要重建 INDEX.md**：检查器会三向比对（幽灵条目 / 漏登记 / 描述过期）。**最常见的漏是「改了 description 但没跑 register.sh」—— 磁盘对了、索引里还是旧描述，别的技能引用它就会拿到过期路由信号。** 修法一律 `bash scripts/register.sh`。
    - **数技能要用 `find -L` 跟随软链**。库里有 6 个软链技能指向 `~/.agents/skills/`（find-skills / humanizer / json-canvas / obsidian-{cli,markdown,bases}），而 `os.walk` 默认 `followlinks=False` 会整个跳过它们 —— 2026-10-02 实测报 73 个、实际 79 个。检查器已修（两处 os.walk 加 followlinks=True），负样本验证过软链技能里的坏 frontmatter 会被抓到。**INDEX 登记 79 = 实体 73 + 软链 6，对不上就是漏了软链。**
    `skill_repo_doctor.py` 已内建 ruff + shellcheck + vulture 三道（工具没装则静默跳过，缺依赖不报成问题）。
    - **ruff 规则集只取 `E9,F63,F7,F82,S105` 五条，不要全开**。全开 `+S` 实测报 120 条噪音：
      `S603/S607/S310` 是脚本的正常写法（调 subprocess、urllib），`S608` 三处全是参数化查询
      （`marks="?,?"` 教科书写法），`S324` 是拿 hash 算缓存 key 不是安全用途，
      `S104` 绑 0.0.0.0 是手机访问聊天壳的前提。**安全规则要按本库实际写法筛，不是按工具默认。**
      接进来的误报用 `# noqa: <规则> — 为什么这里安全` **逐处标注保留**，别删规则。
      `S105` **不认 `API_KEY`**（只匹配 password/token/secret 类名），而那才是最常泄露的一类——
      另配一条正则查 `api_key|secret_key|access_token|private_key` 的硬编码长串（≥16 字符），
      跳过 `#` 注释与含 `noqa` 的行，负样本要验「读 `os.environ[...]` 不误报」。
    - **每 6 小时自动跑一次**（cron `7507eed3bc97` → `skill_doctor_watchdog.sh`，干净则 stdout 空= 不推）。
          ⚠️ **挂 cron 前必须验它不是哑巴**：① 正常→静默 ② 注入一个已知坏态→必须报 ③ 撤除→恢复干净。
          **自动化一个哑巴检查器比不自动化更糟** —— 它会一直显示绿灯，让人以为有闸门。
          ⚠️ **报警正文的排版也是交付物 —— 逐条重复前缀 = 用户读不懂。**
          实测第一版把每条问题都打成 `index  INDEX.md  「<技能名」...`，
          同一句话里的 `index` 和 `INDEX.md` 重复了三遍，用户原话是「写的看不懂，排版很乱」。
          两条修法：① **按 kind 分组，同类只打一次标题**，条目降为 `· <定位>` + 缩进详情；
          ② **转发给用户时只截「问题清单」，把头部统计行切掉**
          （`sed -n '/🔴/,$p'`，而不是把整段 stdout 原样塞进正文）。
          判据：**同一个词在正文里出现的次数 ≥ 条目数，就是没分组。**

        #### 环外不变量报「判据被篡改」时，先证伪再上报 —— 假阳性会让这道闸失效

        第 8 项检查拿「指纹文件的哈希 vs 当前判据文件的哈希」判改动，再用 ledger 对账放行
        合法自学习（curator 把经验 patch 回技能正文）。**对账那一环只要解析路径错一层，
        就会把每次合法自学习都报成篡改。**

        实测形态：指纹的 key 由 `_key()` 相对 `base`（检查器所在目录）生成，技能根下的文件
        键里带 `../` 前缀；而对账函数拿 `skill_root`（技能根）去拼路径 → 差一层 → 读不到文件
        → `OSError` → 返回 False → 「没记账」→ 照报。
        **生成用 base、解析用 skill_root —— 同一组键被两个不同的基准解释。**

        **⛔ 判据：「某文件被篡改」是安全断言，指控前必须先证明它真的没被记账。**
        先取该文件的当前 sha256 去 ledger 里查：命中就是合法自学习，是检查器的 bug 不是安全问题。
        实测三个被报文件的 sha 在 ledger 里全部命中 —— **改动完全合法，是解析路径错了才说没记账。**
        （注意：`return False` 的短路语义意味着**只要有一项对不上，整份列表全被报**，
        所以「自己改的那个文件没记账」会连带把合法的几个一起拖下水。）

        **指纹基线过期不等于有人篡改** —— curator 高频自学习时指纹会长期落后，
        实测 9 天内同一组判据文件被 patch 133 次。**先查 ledger 再谈篡改。**

        **跑 `--update-stamp`（签基线）之前必须先证明闸门还抓得住真篡改**：
        ① 注入一个真篡改（新增/改写一个判据文件）→ 必须报 ② 撤除 → 恢复干净。
        签字不是绕过，是走正门；**没验②就签字 = 把唯一那道安全边界降级成装饰**。
        ⚠️ 造样本改的是**判据文件本身**，抄完立刻撤 —— 用 `cp` 备份到 `~/.hermes/cache/trash/`
        或仓外，别留在会被扫的位置（铁律 35 末段）。

        **一条带假阳性的安全告警比没有更糟**：真出事那天你已经在习惯性忽略它。
        合法活动每天触发一次 ⇒ 这道闸在真篡改那天也大概率被当噪音。
    - **静态检查之外另有一层回归测试**（`~/.hermes/hermes-code/tests/`），体检脚本每轮先跑它。
      写完测试要**变异测试**验它能失败：把判据改回旧错形式 / 删掉关键分支 / 删一个 import，
      跑一遍**必须变红**；不变红就是那条测试没测到它声称测的东西。
      ⚠️ 最隐蔽的一种是 mock 设成恒定失败——两条代码路径结果相同，**删掉被测分支测试照样过**；
      要用状态化 mock（「第一次通、之后不通」）让断言落在两条路径结果不同的变量上。
      ⚠️ 写测试的第一个小时就抓出一个**从未生效**的 bug：排序谓词 `endswith(('-2','-3'))`
      对真实节点名命中 0/27（真名是「优化2」没有连字符），而代码语法正确、逻辑连贯、看上去在工作。
      **凡「按模式匹配外部数据」的分支，上线前先数真实数据上的命中率，恒为 0 就是死代码。**
      （完整方法见 **技能 `flows/measurement-integrity`** 铁律 22，及其同名参考文件
      `flows/measurement-integrity/references/mutation-testing.md`）

    ⚠️ 集成时 ruff 成功那行输出是 `All checks passed!`，**那是通过信号不是问题**，不过滤会变成恒假阳性。
    **死指针必须全局查**：只在 `<技能目录>/` 下找会误报一大片——脚本常在 `~/.hermes/scripts/`，
    把那些根一起纳入文件名索引再判（实测：只查技能目录误报 16 个，全局查后真死指针只剩 3 个）。
    **同类误报第二次落在同一条铁律上**（铁律 19/26 的「证据范围 vs 结论范围」）——
    扫全库的检查器本身就是「同名命中」，第一次写的版本就犯了这个错。
    ⚠️ **名字解析还没盖住「恒假分支」—— 那一层只有现成工具能穿透。**
    `ast.parse` / ruff / shellcheck 全绿的代码仍然可能在骗人:
    ```python
    print("⚠️ 确认删除? (yes/no)")
    if False:            # ← 取消分支永不执行, input() 早被删了
        print("❌ 已取消"); return
    # 直接往下删
    ```
    语法合法、ruff 通过、docstring 还写着「✅ 安全清理工具」，**但它从不读用户输入**。
    成因是当初为非交互运行删掉 `input()` 却留着提示语 —— **看起来有防护, 实际没有**。
    接 `vulture` 并**只取 `unsatisfiable` 那一类**（未用变量噪音太大）：
    ```bash
    uv tool install vulture && vulture <root> --min-confidence 80 | grep unsatisfiable
    ```
    ⚠️ 实测它是唯一报出上面那段的东西。

    ⚠️ **静态检查器只能证明「结构没坏」，不能证明「逻辑没问题」——报这个结论前先实测检出率。**
    用**已知答案出题**（拿刚抓到的 bug 当考题）会得到满分假象：全 5 题通过，看起来很强；
    换**没见过的类别**（命令注入 / 路径穿越 / SQL 拼接 / 裸 except / 除零 / 资源泄漏 /
    int-str 比较 / 死循环）真实检出 **0/8**——全绿只覆盖了「语法 + 未定义名 + 引用存在」。
    **动作：出题分两轮。第一轮用已知 bug 验「已知能力没退化」，第二轮用陌生类别验「真实边界在哪」，
    两轮结果都报，只报第二轮等于给自己打分。**
    ⚠️ **测试样本本身必须先合法**，否则报的是样本的错不是被测物的错。实测造「命令注入」样本时
    忘了 `import os` / 定义 `user_input`，三条"抓到"全是 `F821 未定义名`——
    **每条命中都要看它到底报了什么规则编号**，看到 F8xx 就该知道那是未定义名不是注入检测。
    机制：造样本时为了省事留未定义符号，会让另一个规则顺带命中，统计成「检出」。
    ⚠️ **部分安全规则与已装规则重叠但覆盖不同**：`ruff --select=S` 能抓 `shell=True` 拼接（S602），
    但全库 120 条噪音（S603/S607 是脚本正常写法、S608 三处全是参数化查询的教科书写法、
    S324 是算缓存 key、S104 绑 0.0.0.0 是手机访问前提）。**逐条量化后再决定接哪几条**，
    不要整组开。接进来的误报用 `# noqa: <规则>` **标注保留**（写清为何安全），别删规则——
    删了规则就再也拦不住真凭据。
    ⚠️ **`ruff S105` 不认 `API_KEY`**（只匹配 password/token/secret 类名），而那是最常泄露的一类。
    补一条自己的正则查 `api_key|secret_key|access_token|private_key` 的硬编码长串（≥16 字符），
    跳过 `#` 注释与含 `noqa` 的行；负样本要验「读 `os.environ[...]` 不误报」。

    **规则: 不可逆动作（删/移/改权限/发外部请求）的脚本, 「提示语」与「读输入的调用」必须成对存在。**
    审这类脚本先 `grep -c 'input('` —— 提示语在而 `input()` 为 0 ⇒ 假防护。
    **防呆分支被硬编码关掉（`if False` / `if 0` / 提前 `return` 吞掉）与没有防呆等价,
    而外观上更像有防护 —— 这比裸奔更糟。**（full discipline 归 `flows/measurement-integrity` 铁律 21）

    现成实现见 `scripts/skill_repo_doctor.py`（exit 1 = 有问题，`--json` 机器可读，`--root` 可扫任意代码库）。

    **判「这行是不是在让你执行它」有三个坑，按顺序都会踩：**
    ① **「只在 ``` 代码块里出现」要跟踪块的开关状态**，不能靠「跳过以 ``` 开头的行」——
       那样代码块**内部**的行会被算成「块外」，判据自我否定（`in_block=True` 而 `outside` 也 True ⇒ 恒返回 False）。
       逐行扫 + `in_block = not in_block` 才对。
    ② **「注释行」不能只判 `startswith("#")`**：中文正文里「参见 xxx.py（旧的做法，已废弃）」
       不是注释，会被判成真引用。标记要含「已废弃 / 旧的做法 / 不要再用 / 不存在 / 已移除 / 示例」等中文否定词。
    ③ **同一段里既声明「不存在」又在块外提到该文件 → 仍要报**（声明只在块内生效）。判据是
       「见声明」与「见执行」两个布尔量的**合取**，不是任一命中就放行。

    **先问 GitHub 有没有现成的，别急着自写——但要问对了：**
    市面上的死链检查器（`lychee` / `markdown-link-check` / 各类 pre-commit hook）查的都是
    **markdown 链接语法 `[x](path)`**，查不到**正文里的裸路径引用** `scripts/xxx.py`。
    后者正是技能库里「脚本指到哪」的主要形态。**查工具前先确认它的判据形态覆盖的是哪一种**，
    覆盖不到就自写，别为了用现成工具把判据降级成只查链接语法。
    另：`shellcheck` / `ruff` 这类**静态分析器**与本检查器互补而非替代——前者查「脚本本身写得对不对」，
    后者查「技能指向的脚本在不在」。实测 31 个 .sh 跑 `shellcheck` 得到 **0 个 error**、
    38 条 warning/note（`A && B || C` 在 `pass`/`fail` 都 return 0 时是误报），
    说明**别拿 lint 的 warning 数当技能库健康度**——只有 error 级才对应真问题。
