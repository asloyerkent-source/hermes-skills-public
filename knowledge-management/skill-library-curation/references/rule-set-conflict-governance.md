# 规则集治理：冲突检测、优先级、孤岛审计

> 适用：当一个 SKILL.md（或 MEMORY）里的行为规则累到二三十条，开始出现「两条规则打架」、
> 「不知道还有别的规则」时。规则**条数不是问题，孤岛与无仲裁才是**。

## 一、先量，别凭印象

规则条数靠印象一定会错（实测「36 条」实为32 条）。机械提取：

```python
import re
sk = open('<skill>/SKILL.md').read()
rows = []
for m in re.finditer(r"^### (\d+(?:\.\d+)?[a-c]?)\s+([^\n]+)\n(.*?)(?=^### |\Z)", sk, re.S | re.M):
    num, title, body = m.groups()
    refs = sorted(set(re.findall(r"5\.(\d+[a-c]?)", body)) - {num})   # 前缀按实际改
    rows.append((num, title.strip(), len(body), refs))
```

三个指标，缺一不可：

| 指标 | 判据 | 实测样例 |
|---|---|---|
| **孤岛率** | `refs` 为空的条目占比 | 10/32 = 31% |
| **载荷失衡** | 单条正文 ÷ 中位条正文 | 1432 vs 153 = 9× |
| **编号序 vs 时间序** | 编号是否按插入时间排（乱序 = 插入痕迹） | 是 |

⚠️ **`refs` 的正则要按实际编号前缀写**，别照抄。`5\.(\d+)` 会把 `5.33b`截成 `5`，
统计出的「有引用」是假的。

## 二、孤岛条目才是真问题

孤岛 = 该规则不知道自己与谁相关。后果不是「规则错」，是**它在别的规则的上下文里无法定位自己**，
于是两条规则指向同一情形时，谁也不让谁。

处置（按优先级）：
1. 能并进已有条目的 → 并，别新开一条（同源分裂是孤岛的主要来源）
2. 确实是新维度 → 在新条目里**写明它与哪条交叉**、为什么不能合并
3. 与其它条目轴不同 → 显式标注「本条管 X，不管 Y」，让人知道边界

## 三、优先级表：唯一被工业界验证的机制

模型**不能**靠自觉仲裁冲突。两处硬证据：

- Anthropic 官方文档承认：两条规则矛盾时 Claude「**may pick one arbitrarily**」。
- OpenAI ConInstruct benchmark 实测：冲突**检测** F1 87.3%，但**主动上报仅 45%**；
  GPT-4o 97.5% 直接闷头答。（arxiv 2511.14342，代码 `NLPCode/ConInstruct`）

被验证的两个机制：
- **OpenAI Instruction Hierarchy**（arxiv 2404.13208）：`system > developer > user > tool`，低优先级被压制。
- **Anthropic Constitution**：「conflict 时按列出顺序优先」。

翻译成个人规则库 = **给每层规则一个显式优先级数字，机械可比，不靠判断力。**

表至少要有这几层（从实测的冲突倒推）：
```
L0 安全与不可逆（护栏，永不被优化类规则压掉）
L1 用户当轮指令
L2 现实（实测输出 > 记忆 > 训练数据）
L3 决策流程
L4 硬纪律（少而硬）
L5 优化类（省事 / 最短 diff / 别做没请求的）
L6 方法论（无否决权）
```

🚨 **最常见的漏洞是 L0 缺失**：把「不可逆操作要确认」和「少写代码别过度设计」放在同一层，
后者会理所当然地压掉前者——**优化类规则绝不能与护栏同级**。

## 四、多数冲突不是二选一，是两个轴

实测反复出现的形态：两条规则都成立，因为**它们管的不是同一个轴**。

| 冲突表象 | 实际是两个轴 | 正确解 |
|---|---|---|
| 「默认静默」vs「改完必须实测给证据」 | 静默=**要不要主动开新话题**；证据=**回复里有没有凭据** | 不主动推送（守静默）+ 回复内必带证据（守实测）。两者都守住。 |
| 「段落 50-200 字」vs「尽量短、只留一个下一步」 | 前者含**下限**，后者管**下限** | 删掉下限，只留上限。上限/下限分工后不打架。 |

**判据：遇到冲突先问「这两条管的是同一个轴吗」。** 同轴才需要仲裁；不同轴直接拆开。
这比每次做优先级裁决便宜得多，也更少牺牲。

## 五、元规则：冲突先明说，不许静默二选一

ConInstruct 的核心缺陷就是模型自己挑一条不告诉你。所以必须写成硬规则而非提醒：

- 检测到两条规则指向同一情形且结论不同 → **回复里一句话点明冲突**（「X 要求 A，Y 要求 B，这里按 B，因为…」），然后选边执行。
- **不许默默挑一条照做**——默默挑 = 下一轮原地复发。
- 判不准算不算冲突 → 按优先级取**更保守**的那个。

## 六、新增条目前必查（防孤岛再生）

1. `search_files`（content 模式）搜现有条目关键词，确认没有近似的（避免同源分裂）。
2. 确实冲突 → **在新条目里写明与哪条冲突、怎么共存**，不留悬空矛盾。
3. 定期（季度）跑一次第一节的脚本，看孤岛率有没有回升。回升 = 有人在绕过前查步骤直接加条目。

## 配套工具（查冲突的现成件）

- `promptdiff` — 10 条 lint 规则，专抓 conflicting constraints / 角色混淆 / 模糊措辞
- `AgentLint` — 51 项确定性检查，可作 GitHub Action
- `ConInstruct` — 冲突检测 benchmark + 代码，做评测用

⚠️ 这些查的是**文本形态**（矛盾指令、冲突约束）。**语义冲突**（A 要静默 / B 要证据）
查不出来——那层只能靠第五节的元规则 + 人工裁决。
**别指望装个工具就解决了。**

## 七、别把「写了规则」当成「已治理」

规则文件本身也会骗人：一条规则写着「应当带反例」而库里一条都没有时，
下一个会话读到它会以为已按此整改而跳过。
**判据：每条规则旁边写清「现状是什么」，现状与判据的差距要写在规则里**（与铁律 36 同源）。
