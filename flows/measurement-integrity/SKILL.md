# 读数可信度 — 报故障之前先验探针

## When to Use（触发）
- 任何**探针 / 检查脚本 / 终端命令**报出“对方坏了 / 配置错了 / 服务挂了”, 而你准备据此动手修
- 自建检查器报出“问题”、体检工具给出告警、状态码显示失败
- 修完一个“故障”后症状**毫无变化**（强烈提示原故障可能不存在）

## 铁律

### 1. 先问“这个读数是谁生成的”
工具的**回显层会加工真实数据**。终端输出即是一例: 密钥 / 令牌类字符串被自动替换成 `***`。
看到 `Bearer ***` 就断定“文件里写死了 `***`、这是个 bug”, 是**把回显层的加工当成了文件内容** ——
源文件里可能本来就是正确的变量引用。
**判断文件真实内容只读原文**（`read_file` / 带行号逐行读）, **不从终端回显反推文件内容**。
代价: 会去修一个**不存在的故障**, 还可能把本来正确的文件改坏。

### 2. 为隔离而设的环境变量, 在同一个调用里清掉
终端环境在**工具调用之间是持久的**。为测试把 `HOME` / `HERMES_HOME` / `XDG_*` 指向临时目录
却忘了 `unset`, 后面每一步“真实”操作都继续写进那个临时目录, 表现成
“工具不认我的配置”“装完找不到文件” —— **根因是自己的变量还在**。
判据: 先怀疑变量, 再怀疑工具; 下结论前 `echo` 一次确认。

### 3. 探针可能“答了, 但答的不是你问的那个问题”
典型: 本机 `HTTP_PROXY` 让内网探测出**假 502** —— 响应头带 `Proxy-Connection`, 说明应答者是代理,
请求根本没到设备。**直连必须绕代理**: `curl -s --noproxy '*' http://<IP>:<PORT>/`。
同族: DNS 被代理劫持、被重映射的路径、只证实了 TCP 握手就断言“链路通”。

### 4. 报“对方坏了”之前, 先用一个已知正确的样本验自己的读数通道
手搓的检查器 / 扫描器**自己会假阳性**。先用一个**已知正确答案的样本**跑一遍,
确认检查器本身是对的, 再报问题。同理: 任何“这里有故障”的结论,
都要经得起“换一个干净通道再问一次”。

**4a. `pgrep -f <pattern>` 会匹配到你自己那条命令。**
用它监视长任务(编译/打包/迁移)时, **你的 shell 命令行本身就含那个 pattern**, 于是每轮查询
都命中自己 → 报告“进程还在跑”, 而它其实几分钟前就死了。实测据此空等 40 分钟。
**规则: 查进程用 `ps -C <name> --no-headers` 或读它自己的日志文件**, 不要用 `pgrep -f` 监视自己发起的长任务。
**判据: 探针输出恒为「在跑」而内容毫无变化 → 先怀疑探针命中了自己。**

**4c. 用**字面命令行**当判据的探针，会在「组件改了启动方式」那一刻集体失效。**
典型：监控脚本写死 `pgrep -f "hermes_cli.main gateway run"`，而升级后该进程改用
`runpy.run_module(...)` 启动，cmdline 里不再有那个**连续字符串** ⇒ 探针从那一刻起报「进程未运行」，
而进程好好地跑着。**它是真命中、只是判据过期了**——所以这类误报会被当成真故障去排查。
- **判据要拆成多个独立特征**（模块名 + 角色名分两段），而不是靠一段长字面量；再配 `comm` 白名单。
- **别退化成宽泛的单段匹配**（那会重新引入铁律 4a 的自匹配）。
- **探针报「某核心进程没跑」时，先去读它的真实 cmdline**（`tr '\0' ' ' < /proc/<pid>/cmdline`），
  而不是先去重启它。升级类变更后，这类字面判据应当**全库扫一遍**。
- 改完仍要正负样本双测（真进程命中 / 缺特征的非目标进程不命中）。

**4d. 探针说「对方全死了」时，最便宜的证伪是一次换路径的对照 —— 而最快的路径往往是问用户。**

本机探针的全部证据都来自**同一条网络路径**。它能证明「从这台机器出不去」，
**不能**证明「对面那批东西都挂了」—— 而后者才是你要下的结论。

实测：逐个测 27 个节点全超时、对照组（百度/GitHub）正常，据此写了一份
「机场入口被封、换代理软件无效、等它自己恢复」的诊断。实际是**本机缓存了旧 IP**，
一条重启命令就修好了。**用户的手机当时能正常用同一个代理** —— 一句话就推翻整份诊断。

**规则：当探针给出「远端整批不可用」这类大范围否定结论时，动手修/写报告之前先找一个
走不同路径的对照：另一台设备、另一条出口（手机热点）、另一种客户端。
用户手边现成的那个设备是最便宜的对照，问一句的成本远低于写错一份诊断。**

**判据：你的全部证据是否都来自同一个出口/同一台机器？是 ⇒ 结论只能限在「本机视角不可达」，
不能升格为「对方坏了」。** 这与铁律 4 同源（验读数通道），但错的方向相反：
铁律 4 防「检查器算错」，这条防「检查器算对了、但它只看得见一条路」。

**配套：大范围故障先分「本机 / 本机到对端 / 对端自身」三段，再谈原因。**
分段只需要几个已知可达/不可达的锚点（国内站点 + 中立境外站点 + 目标），
比直接去查目标服务的日志快得多。

**4e. 交叉验证的独立性来自「判据构造方式」，不来自「换了个工具」—— 同一个心智模型写出的两个工具，盲区一模一样。**

「换个工具再验一遍」是防假阳性的标准动作（铁律 4），但它有个常被忽略的前提：
**两个工具得真的从不同角度看问题。** 自己再写一个检查器去验自己写的脱敏器/探针时，
两边会带着**同一个盲区** —— 实测两套工具的内网地址判据都要求末两段是数字，
于是末位写成字面 `x` 的网段写法（`192.168.99.X`）**两边一起报 0**，
而它在产物里真实残留了几十处。**「换工具扫出 0」被当成了干净的证据，实际是双份的假阴性。**

**判据：问「这个交叉验证的两个判据，是我按同一个假设构造出来的吗？」**
是 ⇒ 它们只能互相确认「没写错」，不能确认「没漏」。
真独立的第二视角要么来自**判据构造方式不同**的工具（如熵 + 形态特征，不看白名单），
要么来自**原始数据本身**（直接 `grep` 那个字面量的各种变体形态，绕开所有工具）。

**配对坑（修完假阴性立刻换来假阳性）：检查器必须显式剔除「自己产出的占位形态」。**
给判据补上通配写法支持后，产物立刻报出几百处「内网地址」—— 全是脱敏器写进去的占位符，
**占位符与真值形态相同**。做法是先把占位形态从行里 `sub` 掉再匹配，
**不要用「整行含占位符就跳过」**（那会让「占位符 + 真值同行」的整行漏检）。
**判据：加了新判据后告警数暴涨 ⇒ 先看命中的是不是自己的占位符/示例/生成物，再看被测物。**

**4b. 审计器报「文件不存在 / 缺 SKILL.md」时，先换调用形式，而不是先信它。**

实测一个格式审计器对 5 个已知 100 分的技能全报 `[error] 缺 SKILL.md`。
文件确实在，坏的是**调用形式**：它按相对路径枚举，而我是从别的 cwd 调的。
改成 `cd <技能根> && audit --single flows/<名字>` 后全部恢复正常。

**指纹：「文件不存在」类报错在多个确定存在的文件上成片出现 = 调用形式错了，不是被测物没了。**
（与铁律 4 同源：检查器自己会假阳性；而路径型工具的「根」是它隐含的第二个入参，
不写出来也不会报错——它只是安静地枚举了另一个空目录。）

**动作**：报「缺文件」之前，先用一条不走该工具的命令确认它真在
（`find -L <根> -name SKILL.md | wc -l`），再把审计器的 cwd 切到它预期的根重试一次。
**路径型工具的「根」是它的第一个入参** —— 换根比改判据便宜两个数量级。

**判据: 检查器在同一类数据上给出自相矛盾的结论 → 它没有分辨力, 不是“结果偏弱”。**
**同源的更隐蔽一条: 拿真实数据去跑你的判据, 确认它真的命中过。**
写「按后缀挑节点」这类**匹配外部数据形态**的判据时, 模式可能与真实命名差一个字符,
于是**匹配率恒为 0 而代码毫无异常** —— 实测 `endswith(('-2','-3'))` 对真实节点名命中 0/27,
因为真名是「优化2」没有连字符; 排序规则从那时起就从未生效, 而它语法正确、逻辑连贯、看上去在工作。
**判据: 凡「按某个模式匹配外部数据」的分支, 上线前先 `count` 一下命中率; 恒为 0 就是死代码, 与写了但没区别。**
这只能靠真数据测出来 —— 读代码看不出一个字符串该带不该带连字符。
实测: 用粗糙的正负词计数当情感代理, 量「输出长度 vs 好评倾向」,
两个同类数据集给出 `r = -0.713` 与 `r = +0.996` —— **符号相反**。
此时的正确动作是**判该代理无效并放弃汇报**, 而不是挑一个顺眼的报上去
（样本小时，单个离群值就能把相关系数拉到接近 ±1）。
**报一个自己都不信的数, 比不报更糟 —— 它会被当成证据继续用下去。**

### 5. 代理指标只用来**定位**嫌疑人, 不产生**判决**
体积 / 词数 / 计数这类**代理指标**(proxy metric) 与被测性质之间没有必然关系,
所以它只能回答“先去读哪几个”, 不能回答“这几个有问题”。

**廉价信息常是反向的**: 写得好的东西往往是删繁就简的 —— 体积最小的那批可能密度最高。
按阈值筛出“可疑名单”后**必须逐个读原文定性**, 名单本身不是结论。
直接拿名单当结论报出去 = 用一个没被验证过的指标当证据, 与铁律 4 同类, 只是换了方向:
铁律 4 防的是**检查器算错**, 这条防的是**检查器算对了、但它量的不是你要的东西**。

**自检**: 报“这些有问题”之前问一句 —— **如果这个指标指的是优点方向, 结论会反过来吗?**
会, 就说明它没在测你要测的东西。

### 6a. 「报错 N 次」的历史日志 ≠ 现在的故障 —— 报出任何计数之前先确认它**现在还在发生**

旧日志里的累计计数很容易被当成现症：它有具体数字、有时间跨度、看起来像证据，
于是直接被写进「体检报告」并推给用户去修。**而那个组件可能早就被移除/修好了。**

**报出任何崩溃/异常/失败计数之前，MUST 做二次确认：**
```bash
journalctl --since '<本次会话开始时间>' | grep -ci '<unit>'   # 0 次 ⇒ 旧日志里的历史故障
systemctl list-unit-files | grep '<unit>'                      # 单元已不存在 ⇒ 早被移除
systemctl show <unit> -p NRestarts -p ActiveState              # 计数器归零/单元消失 ⇒ 已恢复
```
**指纹：计数大得离谱（几万次）而「组件现在是否存在」没被查——这正是历史故障的形状。**
真正正在发生的故障，`--since` 窗口内一定有近期记录。

**机制：清理日志/vacuum 会抹掉时间边界**，剩下的旧记录与当前记录在同一个文件里无法区分；
而「N 次」这种数字自带权威感，比「我查了它现在不在」更容易被采信。**数字的权威感和它的时效性无关。**

### 6b. 批量探测的 FAIL/SHORT 里混着提取器的噪声 —— 报数前逐条判读

从脚本/配置里 `grep -oE 'https?://...'` 提取待查目标时，会捞进两类**不是目标**的东西：
**API 端点**（`https://api.x.com/v1/chat/completions`——它是接口不是网页）
与**代码拼接残片**（`...?id={h.get(`——模板字符串没被求值）。
它们会被判成 FAIL/SHORT，让结论看起来像「源坏了/工具不行」。

**规则：报 SHORT/FAIL 之前必须逐条人工判读一次**，把「提取噪声」从「真失败」里剔出来；
否则报告里的失败率是虚高的，而读者会以为新工具或数据源有问题。
**配套：报告失败项时给出总数与逐条判读后的差**（「34 条里 32 OK，2 条 SHORT 经判读均为提取噪声，实失败 0」），
不要只报汇总数（与铁律 9 同源）。

### 6. 自愈 / 健康检查必须测「目标结果」, 不能测通往它的中间信号
自愈脚本最危险的失效模式是**用自己的中间指标自证成功**。

实测: 一个代理自愈脚本每 5 分钟打印 `0 alive nodes -> flush-caches + restart` / `heal done: alive=9` ——
它读的是代理软件自报的 `alive` 字段（基于 TCP 握手 / 健康检查延迟）,
**不是「能不能真正出网」**。上游半死时握手偶通、实际过不去, 于是得到「9 个节点活着」,
脚本**从头到尾都在宣布修复成功**, 而真实 HTTP 请求全程失败 —— **故障一次都没被上报过**。

**规则**: 判定「X 好了没有」的探针, 必须打**真实请求到真实目标**
（`curl -x <proxy> -o /dev/null -w '%{http_code}' <目标站点>`）, 不能信连接层信号
（`alive` / 延迟 / TCP 握手 / ping / 进程存活 / 端口在听）。
**端口在听 ≠ 服务可用; 握手成功 ≠ 出得去网。**
探针测的必须就是你要的那个结果, 中间信号只能用来**定位**。

**推论（反直觉）**: 加了自愈之后, 故障告警反而可能**消失** —— 因为自愈把它「消化」掉了。
自愈脚本的**成功判据**必须用目标指标, 否则它会持续「修好」一个从没修好的东西,
并把真正的告警掩盖掉。审一个看门狗/自愈脚本时, 第一个要问的就是「它拿什么当成功」。

**推论 2: 验证要放在「动作之后」, 不能只在切换之前验一次就宣布成功。**
切换会重建连接、重算组状态, 甚至被上游回收 —— **切之前能出网, 不蕴含切之后还能出网**。
只在切换前验、然后直接报成功, 是把「我验过的那一瞬间」当成了「结果」。
实测一个节点看门狗每 15 分钟自愈: 报「已自动修复, 切到 X」后, 40 分钟后再测 X 已Timeout。
**规则: 切 → 等连接重建(秒级, 实测 3 秒量级) → 用目标判据复验 → 不通就试下一个 → 两次都不通才算这个节点没用。**
复验前的等待给不够, 会把「还没建好」当成「这个节点坏了」而白切。
**配套负样本最关键: 「切前通、切后全死」这一组必须测到** —— 只测「切前就不通」验证不了复验逻辑。

**推论 2b: 等真故障来验复验逻辑, 通常等不到 —— 主动注入一个。**
复验逻辑的分支只有「真出事时」才会走到, 所以等真实故障验证它等于不验证。
做法: 用控制口把状态**拨到一个已知不利的值**(切到一个探测过不通的候选 / 改坏一个判据字段 /
喂一条格式非法的记录), 再跑被测组件, 观察它是否走了「复验」那条分支。
**判据: 注入前先确认被注入的那个状态确实不利** —— 用独立判据实测一遍(而不是相信自己的假设),
否则「注入成功」和「注入了个无害状态」长得一样。
**配套: 组件自报「已修复」之后, 由你用组件之外的判据复测一次**, 不采信它的自报;
这一步只隔几秒, 成本远低于下次故障时才发现自报是假的。

**推论 3: 上游给的数据源可能混进非条目, 要在配置层排除而不是靠排序。**
实测机场把「剩余流量：349 GB」「套餐到期：长期有效」这类**状态信息伪装成节点条目**
塞进订阅, 它们与真节点同类型, 于是 auto/url-test 组会选中其中一个 —— 而那东西根本不是代理。
症状: 自动选择组停在一个怪名字上、同时所有节点全 Timeout。
根因是**订阅内容污染**, 不是本地配置错误, **靠排序治不了**。
**动作: 在 provider 声明里按名字模式排除(如 `exclude-filter`), 改完重载并核对条目数变化。**
判据: 自动组选中的名字不像地区/线路, 就去列 provider 的全部条目 ——
伪条目通常伪装成「状态公告」而不是「线路名」, 一眼可辨。

### 7. 判据是否有效, 取决于**谁在写这个字段** —— 别按字段名归类
同一个字段名, 在不同任务里可能一个是有效判决、一个是假信号。
实测: 定时任务的 `last_status` 在某个任务上确实是假阳性（脚本静默跑完、什么都没投递,
状态照样是 `ok`）; 但另一个任务的**投递失败会把它写成 `delivery_failed`**,
而看门狗的通过集合不含这个值 —— 同一个字段在那个任务上是**有效判决**。
只看字段名像不像已知的假信号就据此指控看门狗, 是**造了一个不存在的故障**。

**规则: 要判一个状态字段是不是假信号, 去读写它的那段代码**
（用 `search_files` 搜字段名 → 找到赋值那一行 → 看失败路径改不改它）, 而不是看它名字像不像。
铁律 6 要求“别信中间信号”, 这条要求**先把中间信号认准** ——
认错信号会把好组件判成坏的, 白修一轮。

### 8. 「合格/不合格」的打分通道可能把**工具失败**混进**内容判决**
fail-closed 的评分器（评委调不通就判 0 分）在**样本之间没有内容差异**时也会给出**完全相同的分数**——
因为那 0 分来自 provider 不可达, 不来自被评内容。多个**明显不同**的样本拿到**同一个**分数, 是读数通道坏了的指纹, 不是“它们一样差”。

**移植别人的校验器时, 第一个样本全绿不等于移植成功——先在**变体样本**上跑。
手搓的 YAML/frontmatter 解析器最常见的静默失败是「自己新建的容器和后续 append 的容器不是同一个对象」,
症状是**所有块标量字段（`|` / `>` 多行 description）一律解析成空**, 而单行字段全部正常。
判据: 拿一个**单行值样本**和一个**块标量样本**对照跑, 分数必须都合理;
只有单行样本对, 就是解析器坏了, 不是被测物差。
**「我自己的检查器」比「不存在的检查器」更危险**——它报的每个数字都会被人当真。

**规则: 分数出现可疑的整齐值（0.50 / 0.0 / 全表同分）时, 先把评分拆到分项再下结论。**
做法: 逐个 evaluator 单独跑, 打出每个分项的名字/分数/失败原因——
判别工具的失败回显通常自报 provider、状态码或 “failed closed”, 那就说明是**通道**的问题, 不是**被测物**的问题。
只报聚合分会把这个区分彻底抹平, 让你把工具故障当成被测物的质量结论说出去。

**推论: “某物不合格”要有非零的差异证据。** 全部样本同分 = 无分辨力（与铁律 4 同源, 但指纹相反:
铁律 4 是同类数据**符号相反**, 这条是异类数据**分数恒等**）。修好通道之前, 那些分数只能当“未测量”处理。

**修复动作: 找到评委/采集环节的 provider 配置, 用**已知能跑通**的替代端点重配, 而不是放弃打分。**
评分器通常把 provider 选择放在环境变量里, 且**默认往往指向一个本机没配的供应商**——
症状是每分项报 `HTTP 403/401` 或 "provider call failed" 后 fail-closed 记 0 分。
按这个顺序做:
1. `grep -oE "(os\.environ\.get|os\.getenv)\(\s*[\"']([A-Z_]+)[\"']" <脚本>` 列出全部候选变量名,
   **不要凭直觉猜**——猜错变量名会得出一套"配了但没生效"的假结论。
2. 确认它在**往哪个 base_url / 哪个供应商**打, 以及需要哪个环境变量当 key。
   **兼容 OpenAI 协议的第三方端点**通常只需换 `*_BASE_URL` + `*_MODEL`, key 变量名照旧。
3. **先用一个最便宜的一次调用验通道**（发一句 "reply OK" 看有没有回声）, 再跑整套打分。
4. 通道修好后必须**复跑并确认分数已经区分开**（不同样本不再同分）——这才是修复成功的证据。

**修好 provider 之后的第二道故障: 通道通了, 评委仍会因「解析失败」记 0 分。**
provider 403 与「响应里缺一个必需 key」是**两回事**, 但症状一样 —— fail-closed 记 0。
只把 `*_BASE_URL` / `*_MODEL` 配对就宣布修好, 会留下一半样本仍在假装被评。
**判据: 把分项回显读到底, 分清回显里说的是 `provider call failed`(通道) 还是
`response missing required key` / `malformed`(解析)。后者要动的是 prompt 里的输出契约
——要求评委补齐全部字段, 或让解析器对缺字段给中性分而不是 0 分。
**fail-closed 的方向永远是「把工具故障记成被测物质量问题」, 所以任何一个 fail-closed
评分器的 0 分都必须先假定是通道问题。**

**同源的判别式版本（比 0 分更隐蔽）：让审查函数「失败时返回空」而不是 raise。**
空列表在下游的含义是「模型正常回答了，但没规则命中」⇒ **放行**；而它同时也是
「模块 import 失败 / 模型名写错 / 响应解析不出来」时的返回值 ——
**故障路径与放行路径在返回值上完全一样**。实测新写的审批闸门第一版就这样静默放行了全部请求，
逐条测下来才发现每一次都走了降级而没人看见。

**规则：审查/判别函数的失败必须 `raise`，让调用方显式降级；返回空值的含义只能是「正常回答但都不匹配」。**
配套：`except` 分支要打一行 stderr（`-v` 可见）——
**你不会知道自己一直在走降级路径，除非降级路径自己出声。**

**配套自检项：降级路径要能独立测到。** 用一个**故意不存在的模型名**强制走降级分支，
断言结论仍然正确 —— 模型挂掉时不能变成全放行或全拒。
这是三态验证（正常 / 注入坏态 / 恢复）在判别器上的应用（铁律 22）。

**「regressed / improved」是差值, 差值比绝对值更容易骗人。**
同一次运行里被评两次的同一个被测物可能给出 0.95 与 0.50, 于是报告把它写成
「从 0.95 跌到 0.50」—— 报告没撒谎, 但**它比较的是两次独立抽样, 不是一次变化**。
**用差值下结论前先验确定性: 把同一个被测物连跑 2–3 次。分数跳变 ⇒ 评委有噪声,
那些 delta 是抽样误差不是质量变化, 只能当「未测量」。**
小/免费模型做主观评分时这条尤其常中: 实测同一技能四次跑出 0.95 / 0.50 / 0.95 / 1.00,
其中 0.50 的回显是解析失败。**稳定的判据是「跨样本是否区分开」, 不是「单次分多高」。**

**同族信号: 评了 N 个却报 "evaluated: 0" 或漏掉某些条目 ⇒ 扫描器的目录假设不成立, 不是被测物不存在。**
路径型扫描器常只认 `<根>/<分类>/<技能>/SKILL.md` 这一种嵌套, 而**装在根目录下的技能会被静默漏扫**,
且**不报任何错**。判据: 拿"工具报出的总数"与"直接 `glob(**/SKILL.md)` 数出来的个数"对账, 不相等就有漏扫。
漏扫的那批要单独跑, 否则全库排名/报告会给他们一个不存在的均分。

### 9. 汇总行只统计了一种失败类 —— 「失败 0 次」是恒真句式
批量任务（逐项 LLM 调用、逐文件迁移、逐条检查）的汇总行**必须报成功数/总数，并按失败原因分组**。
只报「解析失败 0 次」这类单一失败类时，**另一条失败路径存在它照样输出 0**：网络 429、超时、进程未启动、
子任务异常被吞进 `ok: false` 字段——全都不计入那个计数。
实测: 一次 1534 次 LLM 调用的全库审计，汇总报「解析失败 0 次，退出 0」，
而真实成功率是 149/314（47%）、199 条全部 `HTTP 429` 存在 `{"ok": false, "error": ...}` 里，从未进汇总。
**退出码 0 只说明没抛异常, 不说明每项都做成了。**

**规则: 逐项任务完成后, 从落盘结果里数 `ok: true` / `ok: false`, 不要信聚合计数。**
自查问法: “除了这个计数统计的失败, 还能以什么形式失败?” 只要答得上来, 汇总就是残缺的。
**配对要求: 报告里必须带覆盖率**（成功/总数 + 百分比），覆盖率低于 90% 时在报告顶部打告警——
否则读者会把“未测量”当成“已通过”。漏掉的那一半可能藏着全部要报的问题。

### 9b. 判「命令成功」要取实际数字, 不要用关键词子串

写「跑完某命令, 看输出里有没有 X 就报成功」时, **X 这个词常在失败路径里也出现**。
实测清理脚本第一版判 `if "已删除" in out` —— 而**一次都没删成功时的输出正是「已删除 0 项」**,
于是每月一次的自动清理会发一条「清理完成」的假报告。
同族: `Found N errors` / `0 errors` 都能让「含 errors」为真; `All checks passed!` 让「含 passed」为真。
**规则: 用正则取回实际数量, 再按数量分支**（`re.search(r"已删除\s*(\d+)\s*项", out)`）,
**不要用「输出里出现了某个词」当成功标志**。这与铁律 21 是同一个机制（成功标记不是发现）,
但发生在**你自己调用**的命令上, 后果是你自己的汇报出错。

**配套**: 这类分支必须有一组**「命令跑了但什么都没做」**的样本 —— 它与「命令失败」不是同一支。

### 9c. 计数型读数两次对不上时, 先搞清哪个对, 再报异常

批量操作（归档/迁移/删除）后验证数量变化, 最容易犯的错是**用两种方式各数一次、对不上就报紧急**。

实测: IMAP 归档 94 封后, 用 `int(d[0])` 解析 SELECT 的 EXISTS 得到 4014, 而操作前测得 4379 → 差 365, 远超预期的 94。据此报「出事了, 271 封丢失」。
实际是 **EXISTS 解析不可靠**（响应格式随连接变化, 同一文件夹两次 SELECT 可能给出不同解析结果）, 用 `UID SEARCH ALL` 测得真实值是 4287 → 差值正好 94, **零丢失**。

**规则: 报「数据丢失/N 封不见了」之前, 必须用 `UID SEARCH ALL` 或等价的独立计数通道交叉验证。两个读数对不上时, 先搞清哪个对, 再报异常。**
判据: 你的「丢失数」= 两个读数之差, 而两个读数来自不同解析方式 → 差值可能全部来自解析差异, 不是真实丢失。
**紧急报告的成本远高于多跑一条验证命令** —— 假警报会让用户恐慌并浪费排查时间。

### 10. 代理执行体的自报：先 stat 路径，再读内容

执行体（Codex / Pi / 子 agent）说「已写好 N 行、跑过、结论如下」时，**产物可能不在你指定的路径**——
沙箱把目标目录挂成只读时，它会静默改写到 scratch/ 或 `/tmp`，并附一份 INSTALL.md 说明原因。
自报里的行号、函数名、验证结论**全都是真的，只是不是在你要求的地方**。
**判据: 先 `os.path.exists(<指定路径>)`，存在才读内容。** 路径不存在时再去找它实际落在哪（`find -newermt`）。

**反向信号（正向的）: 主动标注「未能验证」的执行体比全标 done 的可信**。
沙箱禁网（`CODEX_SANDBOX_NETWORK_DISABLED=1`）时它只能验不需外部调用的部分（纯逻辑、粗筛、schema），
此时它**只能把粗筛结果说成粗筛、不能包装成语义结论**。
实测一个执行体明确写「语义结论 NOT produced，沙箱禁网跑不了，只验了粗筛会选中哪些对」——
**这种自报可直接采信**，因为它标注了每个结论的证据强度。
把未验证的部分说成已验证的才是造假。判据: **看它有没有区分「已验证」与「未能验证」。**

### 11. 批量调 LLM 时, 一个模型额度耗尽会连坐掉一半结论
铁律 9 说「汇总要报成功率」, 但即使报了, 若轮换策略是「每个条目都从列表头重试」,
一个已耗尽额度的模型会让**它之后每个条目**都先撞它一次, 整轮结论被它连坐。
**这不是工具坏了, 是没写「失效成员退出」这条。**

三条必备:
- **429 即时把该模型移出本轮轮换**(线程安全集合, 一次 remove 全局生效),
  不是「这一条跳过」——下一条不该再撞它第二次。
- **单条目尝试上限压到 3**(实测默认 6 次退避会把整轮时间耗在一个死模型上)。
- **默认模型清单只用当轮实测能连且能稳定输出 JSON 的**; 派活前逐个发一次极小 JSON 请求探活。

**探活不能只看 HTTP 200**: 实测同一批免费模型里, 有的返回 404「已不再免费」,
有的 200 但 `choices` 为 `None` 抛 `'NoneType' object is not subscriptable` ——
**两者都算不可用**, 判据是「能否解析出预期结构」, 不是状态码。
反面: 模型超时会**占掉整轮 wall-clock**, 所以探活要在派活前做, 不是失败后才做。

### 12. 给检查器加过滤规则时, 先改文档措辞, 别先改正则
自建检查器开始误报某类「举例/占位」内容时, 修检查器的直觉是加一条排除规则。
实测连续三轮全失败: 整行 `continue` 吞掉同一段里的真断链 → `fullmatch` 不匹配带前缀的片段 →
用 `re.sub` 按行号盲切代码切出 `IndentationError`, 而**该脚本没有备份**, 只能手修。

**规则: 排除规则加到第三轮还搞不定, 说明方向错了 —— 改被检查的内容。**
把文档里的举例改成**不带路径形态的描述**(「把 A 目录下的文件误写成 B + C 两段拼接」
而不是「引用写成 `a/b/x.md` 实际在 `b/x.md`」), 举例就不再长得像路径, 规则可以完全不写。

**配套硬规则: 改自己的检查器之前先 `cp <f> <f>.bak.$(date +%s)`。**
同一天里给配置、插件、脚本都备份了, 唯独漏了这个, 坏掉即无退路。
以及: **用行号盲切多行字符串改代码** (`t[:n] + new + t[n:]`) 极易留下碎片行 —— 改完立刻
`py_compile`, 报错就说明切错了。

**验证新规则的双向门禁**: 造一个假技能, 同时含**真断链**与**占位路径**,
要求前者照报、后者剔除、分数合理。只测「假阳性消失了」不够 ——
整行跳过那种实现正是**假阳性和真断链一起消失**(假技能仍 100 分)。

#### 12b. 例外: 当被检查的文档**本身就是讲这个误报的**, 必须改检查器

上面那条「改文档措辞」有前提: 那篇文档是**普通正文**, 举例只是顺带写的。
**若文档的主题恰好就是「引用检查器如何假阳性」, 改文档等于毁掉它的全部价值** ——
那些占位路径不是随手举的例, 它们就是论据。

实测: 9 条「致命断链」全部来自两个专门讲假阳性的技能, 而把占位名
(`x` / `...` / `guide` / `repro_bug`) 降级后 9→0, 检查器退出码从 1 变 0。
**判据: 误报集中在「讲这个问题的文档」里 ⇒ 改检查器; 误报散在普通正文 ⇒ 改文档。**

#### 12c. 表格里的假阳性, 判据要**位置**不要**词**

同一行里既有真引用又有「我误判成 xxx」的反例列时, 按词过滤必然两头出错。

- ✗ 按词降级: 拿「反例 / 误判成 / 错误示范」当标记 —— ① 标记在**表头行**、指针在**下一行**,
  规则压根不命中; ② 放宽到任意行含这些词, 真断链行只要写了「反例」就被放过。
- ✓ 按位置降级: **否定词(缺/漏/找不到/不存在)必须出现在指针之前**, 才判为误判示范列。
  判据写成「同行内 `PTR_RE.search(line, 否定词位置)` 有命中」。

**推论: 判据的判别维度要和被误报对象的差异维度一致。**
真引用与反例的区别是**位置**(否定词在前), 不是**用词** —— 用词两边一样。
选错维度时, 规则要么打不中, 要么连真信号一起吃掉。

### 13. LLM 判型审计器: 先验「正确性锚点」, 再看它报了什么
铁律 4 是「用已知正确样本验读数通道」; 对**做语义判断**的审计器（LLM 逐项给判定并出报告）还要加三条。

**① 锚点必须含「该不报的也别报」。** 只给真阳性样本, 工具会把所有东西都判成有问题。
派活时给 3–5 组已人工定过真伪的样本: 一组该判强重叠、一组**名字像但审计对象不同**、
一组事前 vs 事后零重叠。跑完先对答案, **判错 = 工具不可信, 它的其他输出一律不采纳**。

**② 适配度/评分类结论的条件是「你给的画像」, 画像错则整个结论翻。**
这类工具的 verdict 是在**给定前提下**推出来的, 前提偏一点结论就反向, 而且输出看起来同样笃定。
实测: 给「外贸从业者, 不写生产代码」的画像, 审计器把一个代码审计技能判 `retire / fit=0.15`,
理由「无代码库可审」—— 而被审者当天刚在该机器上审出一个通过机器校验的真实漏洞。
**判据: 结论与你的已知事实冲突时, 先怀疑喂进去的画像, 再怀疑结论。** 别直接采信低分。

**③ 选工具看「错了怎么表现」, 不看覆盖面。**
会自己喊停的（证据不足就拒收, 如要求给出实际观察结果/可复现步骤才认一条发现）
**优先于**覆盖面更大但静默降级的。静默降级的工具会把环境问题说成被测物质量问题。

**④ 工具找出你没判出的真问题, 是它的价值不是你判错了。**
人工分诊有目录盲区（实测人工只扫一个分类目录, 漏掉另一分类下的强重叠对,
而工具在同一批里把它挑了出来）。**别因为「和我结论不同」就弃用**, 先逐条看它的依据。

## 14. 改完源码先清字节码 —— 你可能一直在给旧代码做体检

**症状**: 改完正则/常量/分支, 跑验证, 行为**完全没变**。于是开始怀疑改动没保存、
路径不对、逻辑写错 —— 实际执行的是**改动前的版本**。

实测: 修完失败判据后重测, 新写的匹配逻辑一条没生效; 用 `inspect.getsource` 打印
内存里的函数, 确认是**新代码**, 但 `re.compile` 的结果仍是旧行为。两处同时成立,
因为**磁盘上有新 .py, 而 Python 加载的是旧 .pyc**。

**机制**: 字节码缓存按**源文件 mtime** 判定新鲜度。改文件、跑测试、清缓存, 若
导入发生在清缓存之前, 进程内拿到的旧模块会被整个会话复用 —— 尤其**常驻解释器**
(`execute_code` 的 session kernel、`python -i`、长跑服务、cron 复用进程)。
规则 2 讲的是**环境变量**跨调用残留, 这条是**模块对象**跨调用残留, 同源不同载体。

**规则**:
```bash
# 改完 .py 立刻清, 顺序不能反
find . -name __pycache__ -type d -exec rm -rf {} + 2>/dev/null
```
常驻解释器里还要**逐个重导**:
```python
for m in [k for k in sys.modules if k in ("mymod", "helper")]:
    del sys.modules[m]
import mymod  # 此刻才是新代码
```

**判据: 「我改了 A, 行为完全没变」且没有报错 —— 先怀疑自己在测旧代码, 而不是先怀疑改动写错。**
先把执行单元的**版本**确认了（清缓存 + 重导 + `inspect.getsource` 交叉验）,
再开始读逻辑。验证时顺手记下源文件 mtime 与行数, 后续报告里也能证明测的是哪一版。

**附带**: 审查/评测别人代码时, 要求对方**先记所审文件的 md5 与行数**。
它审的是派发那一刻的快照, 你并行改过之后它报的就不是你手上的东西了。

## 15. 一直报同一件事的告警 = 基线卡住了, 不是信号

一条告警**连续每次都一模一样**、且已经持续多个周期时, 它携带的**新信息量是零**。
每小时都报一次的「管线漏提取, 需要人工介入」和真实的一次漏提取, 在通知里长得一模一样——
于是真正出事的那一次也会被一起忽略。**常亮的告警不是提醒, 是背景噪声源。**

判据: 告警内容、涉及对象、条目数在多个周期内**逐字相同** → 先去找「哪一条输入让状态永远回不来」,
再谈别的。健康的检查器会随新输入变化; 永远不变的失败说明**读数通道钉死在一个陈旧状态上**。

**修的位置在写入端, 不在报警端。** 报错的那个检查通常是对的, 错的是**当初允许坏数据落盘的那一步**。
本例: 写入端对空输入不做校验(`json.loads(stdin or "{}")` 把空输入当合法空对象),
于是空壳记录进了只追加层; 而只追加层**不允许删**, 所以报警端无论怎么改都消不掉。

由此得一条设计规则:

> **只追加(append-only)的审计层里, 坏记录一旦落盘就不可撤回。**
> 因此「拒绝坏输入」必须在**写入时**做, 「识别坏记录」只能在**读取时**补。
> 事后补救的唯一手段是让读端宽容——但那是降级, 不是修复。

**别把「报警的检查有问题」当成第一嫌疑人**, 尤其当它对**同类输入**判得对、
只对某一条历史记录判错时: 判据没错, 样本错了。

**自检**: 接到一条告警时先问「这条我上一次见到它是什么时候、是不是逐字相同」。
是 → 先清基线, 别按新故障排查。

## 16. 写校验/护栏时，字段名要照 schema 抄, 不是照你刚读的下游代码抄

铁律 15 讲「拒绝坏输入必须在写入时做」。真去做这一步时, 会掉进一个**只有实现者看得见**的坑:

**手边刚读过某段派生代码, 顺手就把里面的字段名写进了护栏的判据。**

实测: 给「只有 meta、没有内容」的事件加空壳拦截, 判据里的字段名取自**中间层**的
`exec_summary`(那是 `ingest-mid` 造出来的名字), 而**schema 里原始事件的字段叫 `exec`**。
结果「只带执行步骤」这种完全合法的事件被误判成空壳拒收 —— **护栏本身成了 bug**,
而且这类 bug 天生隐蔽: 它只在真实数据流里出现, 而手写测例通常会带上 `goal`, 照样绿。

**规则: 写「哪些字段算有效内容 / 哪些算合法」这类判据前, 先用 `search_files` 搜一遍 schema 确认真名。**
派生物的名字经常和源层不同名(源层 `exec` → 中间层 `exec_summary`)。
**判据抄错字段名 = 护栏拒掉合法数据**, 修复方向是「查 schema」, 不是「把判据放宽」——
放宽会连真的坏数据一起放过去, 回到起点。

**配套: 护栏和它的测试必须同批写, 且测试要自带前置条件。**
第二层坑: 新加了护栏 A, 测试 T 却假设「库里已存在 A 要拦的那种坏数据」。
A 上线后坏数据根本写不进去了, T 的前置条件永远不成立 —— 表现为**断言无故失败**。
这类「自己造的测试把自己搞挂」很容易被误判成「刚加的护栏有 bug」, 实际是测试没造数据。
**判据: 断言失败先问「它的前置条件现在还成立吗」, 再怀疑被测代码。**
造前置条件就直接手写那份坏数据进去(legacy 场景本来就需要), 别指望前面的流程会生成。

## 17. 断言「不存在 / 装不了 / 不支持」之前，先查本机权威来源

否定结论的代价不对称：多查一次是几十秒，否掉一整条方案是几小时。**「我没找到」和「它没有」是两句话，别混用。**

- **本机目录才是权威，官网与搜索只是外部视角。** 断言「某项目没有 X 集成」之前，先翻本机的 plugin / catalog / manifest 索引目录 —— 项目可能已把它收进官方目录，甚至随本机这个版本一起发布，只是文档还没跟上。
- **报错里列出的合法值，是最好的权威名单。** 当服务报 `invalid provider: X, must be one of A, B, C`，那份清单直接告诉你叫什么，别逐个试。
- **配置模板的注释里就预置了解法。** 卡住时不要只读报错附近那几行 —— `grep` 你要找的那个选项名。模板常以注释形式给出受限环境的出路（离线源 / 国内镜像 / 强制降级），而这些注释恰恰不在报错附近。
- **变量名的权威来源是装好的源码，不是文档、更不是你的记忆。** 一个服务常有多层各自命名（上层向导的选项名 / 服务进程读的 ENV / 底层 SDK 认的字面量），三者经常不一致；按向导填的值，服务进程可能整条不认。
  ```bash
  grep -rhoE '<PREFIX>_[A-Z_]+' <venv>/lib/python*/site-packages/<pkg>/ | sort -u
  ```

**自检**：这个否定结论，我是查了本机还是查了搜索？**查搜索得到的否定结论，一律降级为「暂未确认」。**

### 3b. 报“它坏了”之前，先确认你用的是它**本来的那个用法**

报“停止控制失效 / 输出格式不稳 / 太慢 / 质量差”之前，先读它自己的配置与接口声明，
确认你是**按它设计的方式在调**，而不是按同类组件的习惯在调。

**判别式组件（打分/分类/决策）被当生成式组件测，会伪造出一整套“硬伤”**，而那些全是用法错：
- 读 logits 取概率的模型，你让它 `generate()` 出JSON ⇒ 「停止不住、重复输出、JSON 非法、慢一个数量级」四条同时出现；
- 改用 `logits[字母token]` 打分后，同样四问题全部消失，而准确率与速度都是量级上的正常值。
- 生成式模型反过来也一样：拿开放问答去测一个专精小模型，它会**自信地编造事实**（造术语、造货币名、造行政区划），
  于是被记成“会幻觉的次品”——而那正是「不给选项就让它答」的超纲用法。

**动作**：动手实测前先 `ls` 模型目录并读全部 `*.json`/config/接口声明。
`decision_config.json` 里的 `letter_token_ids` 只看文件名完全想不到，
但它一句话决定了整个用法（判别式 vs 生成式）。**这个文件是权威，不是文档，也不是同类项目的惯例。**

**判据：你测出的“缺陷”是否恰好是你**没按接口调用**会产生的那些？** 全中⇒先换用法复测一次，
再下结论。反之（缺陷与用法无关）才是真的。

**配套: 同一组件被测出三份互相矛盾的报告时，第一反应不是「它时好时坏」，而是「我用了三种不同的错接口」。**
三次矛盾结论的成本远高于开一次目录的成本。

### 3c. 小样本算出来的校准/统计指标**没有分辨力**，不能当「校准良好」汇报

实测4 题得出 ECE 0.003（近乎完美校准），扩到 200 题后真实 ECE 是 **0.0742，差 25 倍**，
且校准曲线是**非单调**的（>90% 置信区间极准、中间区间严重过度自信）——而这在4 题上完全看不出来。

**规则: ECE / 相关系数 / 准确率这类指标，样本 <30 一律不汇报“该性质好”**，只能说“当前样本下为X”。
**判据：报一个比例型指标前，先说得出分母**；分母只有个位数时把结论降级为观察。

**配套: 分层报告，别只报总均值。** 同一批样本按难度分层后差异极大（实测明显题 100% / 一步推理 85% /
有干扰项 76%，总均值 87% 掩盖了这个梯度）。**总均值“还行”时更要看分层**——它常是“简单题满分+难题不及格”的平均。

## 26. 「配了」不等于「生效」—— 阈值型配置要拿实际数据量反推

阈值写成一个百分比或一个数，看起来配好了，实际可能**永远不会触发**。
这类失效不会报错、不会告警，只是让一个本该起作用的机制静默死掉。

实测：上下文压缩配了 `threshold: 0.75`，看上去是「用了 75% 就压缩，很安全」。
但阈值是**窗口的百分比**—— 512K × 0.75 = 触发线 38 万 token，
而平均输入只有 12 万 ⇒ **压缩一次都没执行过**。
不是失败，是永远轮不到启动。默认值往往更高（0.50），所以**默认值也不能当安全值**。

**规则：凡阈值型配置，验收问的不是「配了吗」，而是「阈值换算成绝对量之后，覆盖得住实际数据量吗」。**

判据动作：
- 把百分比换算成绝对值（`阈值 × 上限`），与**实际**的分布比（均值、分位数），不是与上限比。
- 阈值高于实际分布的高分位 ⇒ 这个机制是装饰品，删掉或调低，别留着当心理安慰。
- 配置文件里如果有**多个同名小节**（如多处 `compression:`），只报匹配到的那一行，
  并把整行一起打出来让人确认匹配对了位置—— 只报值不报行等于让人盲信。

**同族：主开关关着但配套规则已配齐 = 半配置状态。** 实测 `proactive_prune_tokens: 0`
而 `proactive_prune_min_result_chars` / `_min_reclaim_tokens` 都已填好值——看起来「裁剪配好了」，
实际主开关是 0，那些规则一行都不会执行。**判据：配了 N 项却有一项是「关」，就是半配置，不是配置完成。**
读配置时把一组相关键**一起列出来**（`grep` 出全部键名再逐个看），不要一次只读一个。

## 27. 「感觉慢」先查输入量与输出比，再查模型

延迟几乎随输入长度线性增长（延迟 ≈ 固定开销 + 每 token 开销），
所以**输入巨大时换模型救不回来**——先量输入。

**第一步读数**（`~/.hermes/state.db` 的 `session_model_usage` 表，只读打开）：

```sql
select sum(api_call_count), sum(input_tokens), sum(output_tokens),
       avg(input_tokens), max(input_tokens) from session_model_usage;
```

判据：
- **in : out 比 > 5** ⇒ 上下文膨胀（输出几十字而输入几十万）。
- **avg 与 max 量级差** ⇒ 有失控循环的任务，不是正常上下文增长。实测 max 是 avg 的 256 倍，
  这种条目**本身就是个待查故障**，比平均延迟高更要紧。
- 单次输入换算延迟（近似线性）后超预算 ⇒ 先压上下文，别换模型。

配套：`max_turns` / `threshold` 这类参数**不能只看当前值合理**，
要用上一步量出的实际分布反推它们会不会触发（铁律 26）。

→ `scripts/context_bloat_probe.py`（只读；in:out、离群会话、阈值反推、半配置检测、重复进程；
全正常 exit 0 打印 OK，有告警 exit 1 打告警）

## 28. **配置值与聚合字段都不是观测量 —— 诊断前先读日志原文**

铁律 26/27 讲「阈值要拿实际数据反推」，但两条都用**配置字段**当输入，于是会连错两次。
真正的观测量在**运行日志**里，它同时纠正窗口大小、机制是否触发、以及字段的真实粒度。

**① 阈值要拿日志里的绝对量算，不是拿配置文件里的窗口乘。**
配置文件只写「窗口的百分之几触发」，**窗口的真实值与配置项不是同一个来源**：
实测按配置推测是 512K 窗口，日志原文是 `threshold: 85% of 256,000 = 217,600` —— **窗口是 256K**。
按错的窗口算出的触发线差一倍，据此做的调参（降阈值）建立在错误前提上。
**判据：阈值型配置的换算，窗口大小只能从日志/接口声明读，不能从配置项推断。**

**② 「机制从没触发过」这个结论，要用日志原文证伪，不要用「没触发条件」推出来。**
实测连续三次断言「压缩一次都没执行过」（依据是阈值高于平均输入），
而日志里有三条 `auto-compressing` 记录，其中一次是 `compressed 1377 → 1377 msgs, ~276,401 → ~276,401 tokens`
外加 `WARNING: still ~276,401 tokens after compression` —— **机制触发了，但压不动。**
这与「够不着阈值」是完全不同的故障（铁律 26），修法也相反：
一个要调阈值，另一个要改压缩算法；按前者的解法去做，后者只会让压缩更频繁且一样压不动。

**③ 聚合表的字段不是单次观测。**
`max(input_tokens)` 在「每行 = 一个 (会话, 模型) 组合」的表里是**最大的累计值**，不是最大单次。
实测据此报「单次输入 3100 万 token（按线性延迟折算 4.3 小时）」，
真实情况是同一行 `api_call_count = 1881`，均摊后 16,547 token/次，完全正常。
**判据：报任何 max/avg 之前，先看这行代表几次观测**（相邻列的计数列、分组键的粒度）。
聚合值只用于**圈定嫌疑对象**，单次量级必须回到日志里的 per-call 记录取。

**共同机制**：配置项、聚合表、阈值换算都是**间接推算**，三者各自都可能与运行态不符；
而它们给出的数字看起来同样精确，于是错误不会被格式暴露出来。
**推算出来的数只能用来决定「下一步去哪儿读原文」，不能直接进结论。**

## 29. **「需要某硬件/某宿主才能跑」是断言, 不是事实 —— 先查有没有 headless/CPU 路径**

装前检查里最容易先入为主的一条：「它要 GPU，本机是 2GB 显存的小卡，headless 大概率跑不起来」——
**这句话里的「大概率」是推断, 而结论会被当成否决理由用。**

实测：读 README 时看到渲染层写着 GPU 合成器（wgpu/Vulkan），据此推断容器环境跑不起来；
实际编译 7 分钟通过，**headless CLI 全流程纯 CPU 跑通**——建图 / 填色 / 导出 PNG 全部实测通过。

三条：
- **README/文档里的硬件依赖指的是渲染路径，不是存在的前提。** 桌面应用类项目几乎总带一条
  headless/CLI/export 路径来服务服务器与自动化——那条路径通常就是纯 CPU 的。
- **动手前先看 `--help` 的子命令列表**：`convert` / `info` / `batch` / `run` 这类词出现，
  就说明有无头入口；有就说明编译值得做（成本只是一次 `cargo build`）。
- **装前查的排序：编译成本低的先验，高成本的先看子命令。** 一条 `git clone --depth 1` +
  `--help` 能拍掉大部分「装不了」的误判，而编译一次才发现是几十行的排查更贵。

**与铁律 17 同源**：否定结论（「跑不起来」「不支持」「没得用」）的成本不对称。
多花一条 `--help` 换掉一个基于推断的否决，是极值的交换。
- 你换了一个工具复验同一批数据, 两次都报「干净」→ 先问这两个工具的判据**是不是你按同一个假设写的**; 同源判据只能互相确认「没写错」, 不能确认「没漏」（铁律 4e）
- 你给检查器加了新判据后告警数暴涨 → 先看命中的是不是它自己的占位符/示例/生成物形态（铁律 4e）
- 你要断言「某类东西一个都没有」, 而验证手段全是自己写的工具 → 补一条**不依赖工具**的直查: 拿字面量的各种变体形态直接 grep 原始数据（铁律 4e）
- 修完一个“故障”后现象**完全没变** → 回头查读数通道, 而不是继续改
- 报出的问题**数量多且集中**（“十几处断链”/“一片红”） → 先怀疑扫描器的正则、路径解析或过滤逻辑有 bug
- 症状**只有你自己能复现**, 用户侧一切正常 → 先怀疑本地环境（代理 / 变量 / 缓存）
- 一个“损坏”的值**恰好等于某个工具或平台的显示约定**（如 `***`） → 那多半是显示层, 不是数据
- 报出的问题**恰好等于某个阈值筛出来的名单**（“体积最小/词数最少的 N 个”） → 先问该指标是优点方向还是缺点方向; 代理指标只定位, 不判决（铁律 5）
- 一个自愈 / 健康检查脚本**持续宣布成功**, 而用户侧症状不变 → 它的成功判据多半是中间信号而非目标结果（铁律 6）; 同时意味着**真正的告警被自愈掩盖了**
- 多个**明显不同**的样本拿到**同一个**分数, 或分数整齐地等于 0.50 / 0.0 → 先把评分拆到分项查有没有 evaluator 失败被计成内容分; 通道修好前这些分只能当“未测量”（铁律 8）
- 报告说某被测物「regressed / improved」→ 先把**同一个**被测物连跑 2–3 次验评委确定性; 分数跳变说明那是抽样误差不是变化（铁律 8）
- 你自己刚写的检查器在一个样本上全绿, 却还没在**变体样本**上跑过（多行值、块标量、嵌套结构、空值）→ 那是未验证, 不是通过（铁律 4）
- 统计量在**同类数据**上符号相反（同一个 r 一会儿 −0.7 一会儿 +0.99） → 该统计量没有分辨力, 不是“数据本身矛盾”; 判无效并停止汇报（铁律 4）
- 你要指控的组件用的判据**名字上很像**已知的假信号字段 → 先去读写那个字段的代码再指控; 字段名相同不代表语义相同（铁律 7）
- 批量任务的汇总报“失败 0 次 / 退出 0”, 而你还没**逐条数过落盘结果里的成功数** → 汇总只统计了某一种失败类, 另一种被藏在 `ok:false` 字段里; 退出码 0 不等于每项都做成了（铁律 9）
- 你要用 `pgrep -f <pattern>` 监视一个自己发起的长任务, 而它每轮都报「还在跑」→ 探针匹配到了你自己那条命令行; 改 `ps -C <name>` 或读它自己的日志（铁律 4a）
- 你要报「某服务崩了 N 次」, 而那个计数是从**旧日志/旧journal** 里统计的 → 先 `journalctl --since '<现在>'` 确认它还在发生, 并 `systemctl list-unit-files` 确认单元还在; 0 次 ⇒ 那是历史故障, 不要让用户去修（铁律 6a）
- 批量探测报了一批 FAIL/SHORT, 而目标是从脚本里grep 出来的 → 逐条判读: API 端点不是网页、模板字符串残片不是链接; 剔掉噪声后的真实失败数要单独报（铁律 6b）
- 你要断言某个 site-packages 包「零引用可删」, 而证据是 grep 了应用代码 → 查依赖图 `grep -rl '<包名>' .../site-packages/*.dist-info/METADATA`; A 可能只是 B 的依赖而 B 自己无引用, 手删 = B 立刻 ImportError; 删包走 `pip uninstall`
- 你要删 `.env` 里某行, 而它位于某个「已弃用组件」的配置块内 → `grep -rl '<VAR名>'` 查引用数; 同块内常混着与该组件无关的通用设置(镜像源/公共 key), 被别的脚本引用, 删了连带打死别的功能
- 你用 heredoc 内联多行脚本跑命令, 而命令卡住不动 → stdin 不关闭, 工具层会一直等到超时; 写多行脚本一律 `write_file` 落盘再执行
- 改完配置写入成功, 而你只验证了「写入没报错」 → 回读 `hermes config get <键>` + `config check`; YAML 重复 key 不报解析错但会让 Hermes 回退到 last-good settings, 于是用户改动静默失效
- 探针报「某核心进程没运行」而进程明明在 → 先读它的真实 cmdline; 升级/换启动方式后, 字面命令行判据全部过期, 改成多特征匹配（铁律 4c）
- 你要说「某机制从没触发过 / 某配置从没生效过」, 而依据是**按配置字段换算出的触发条件** → 去日志里搜该机制的原文记录; 实测连续断言「压缩从未触发」而日志有三条记录(铁律 28)
- 你要报某个 `max`/离群值很大, 而那张表是**聚合表**(一行 = 一组观测) → 先看它代表几次观测再谈单次量级; 累计值当单次值会报出数量级错误(铁律 28)
- 阈值型配置的「窗口大小」你是**从配置项推断的**, 不是从日志/接口声明读的 → 窗口差一倍会让全部换算作废(铁律 28)
- 你判「命令成功了」用的是「输出里含某个词」→ 那个词在「删了 0 个」这类失败路径里同样出现; 正则取实际数量再分支（铁律 9b）
- 报某个模型/组件「停止不住、格式不稳、太慢、质量差」, 而你**没先读它的 config/接口声明** → 判别式组件被当生成式测会伪造出这四条全部; 先按它本来的接口复测（铁律 3b）
- 同一组件给出三份互相矛盾的实测报告 → 大概率是你用了三种不同的错接口, 不是它时好时坏（铁律 3b）
- 你要说「它需要 GPU / 需要宿主应用才能跑」而你只读了 README 的硬件依赖那一句 → 先看 `--help` 的子命令列表有没有 `convert`/`info`/`batch` 这类无头入口; 渲染路径≠ 存在前提(铁律 29)
- 用 4 个样本算出 ECE 0.003 就汇报「校准极好」→ 扩到 200 题后是 0.074, 差 25 倍; 比例型指标先报分母（铁律 3c）
- 只有总准确率、没分层→ 简单题满分与难题不及格会被平均成一个「还不错」; 分层差异才是可用的信息（铁律 3c）
- 报告没写**覆盖率**（成功/总数）就给出结论 → “未测量”与“已通过”长得一模一样, 低覆盖率时结论只覆盖了一小部分语料
- 批量 LLM 任务里**某一个模型反复出现在错误信息里** → 那是额度耗尽, 不是「这批数据难处理」; 该模型应被移出本轮轮换（铁律 11）
- 检查器要「自动从散文里抽出被查对象」→ 正则抽语义槽位三轮全败, 改显式清单（铁律 22b-14）
- 造负样本时对**真实常驻文件**跑了破坏性 `sed`/`>` 覆盖 → 负样本一律造假数据; 且 `cp .bak` 必须在破坏命令**之前**, 之后取到的是损坏态（铁律 22b-15）
- 真实数据里待查对象只有 1-3 个 → 手工修 + 清单脚本盯新增, 别写通用检测器（铁律 22b-14 的 YAGNI 判据）
- 要给检查器加「忽略某类内容」的规则, 连改三轮仍在误报/漏报之间摆动 → 改被检查的文档措辞, 别再改正则（铁律 12）
- 误报**集中出现在专门讲这个误报问题的文档里** → 那些路径是论据不是举例, 改检查器别改文档（铁律 12b）
- 同一条新判据既不命中、又把真信号一起放过 → 判别维度选错（真信号与反例差在**位置**不在**用词**）（铁律 12c）
- 改检查器时脚本输出不再是合法输出（不再是 JSON / 报 `IndentationError`）→ 按行号盲切留了碎片, 立即 `py_compile` 定位
- LLM 审计器给了某个技能/组件很低的适配分, 理由与你的已知事实冲突 → 先查喂给它的画像写偏了没, 而不是直接采信（铁律 13）
- LLM 审计器的结论与你的人工判断不一致 → 先逐条看它的依据; 人工分诊有目录盲区, 工具挑出你漏的真问题是它的价值（铁律 13）
- 两个审计工具摆在面前, 一个覆盖面大但会把失败记成 0 分, 一个覆盖面小但证据不足就拒收 → 选会喊停的那个（铁律 13）
- 改完源码后**行为完全没变**且无报错 → 先清 `__pycache__` + 重导模块, 确认没在给旧代码做体检（铁律 14）
- 一条告警**连续多个周期逐字相同**、对象与条目数都不变 → 基线卡在陈旧状态上, 先找是哪条输入让状态回不来, 别当新故障排查（铁律 15）
- 只追加层里已经落了坏记录、删不掉 → 改写入端只能防新的, 消不掉旧的; 让读端识别它是唯一补救, 且那是降级（铁律 15）
- 刚加的护栏把**合法**数据也拒了 → 先用 `search_files` 搜 schema 核判据里的字段名, 多半抄了派生层的名字; 别直接放宽判据（铁律 16）
- 新加的断言无故失败, 但被测代码看起来没问题 → 问它的**前置条件**还成立吗; 护栏上线后坏数据写不进去, 测试就没数据可验了（铁律 16）
- 派给子 agent / 执行体的活「日志零输出」→ 别当卡死证据; 非交互模式输出常缓冲到结束才刷, 先给超时再看
- 你给「评估器不可自我修改」的实现只是把指纹存在判据文件的邻居目录 → 那不是环外, 是把不变量藏起来了; 问「骗过它第一步删哪个文件」（铁律 23）
- 你写的自检里有一句「状态缺失/损坏时不该报」→ 那多半在给 fail-open 盖章; 问「骗过它第一步删哪个文件」（铁律 22b-8）
- 你只比了「两边都有且值不同」的差分, 规则文件被**删**或**新增**都是零信号 → 三种差分都要报（铁律 22b-8）
- 检查器跑完输出空白/只有 traceback, 而退出码仍是 1 → 一处异常吞掉了整份报告; 靠退出码的自动化分辨不出「有问题」和「它崩了」（铁律 22b-9）
- 自检样本写死了绝对日期, 过了几十天后自己转红 → 相对日期生成 + 替换时钟做时间旅行（铁律 22b-10）
- 刚写完的检查器只做过自验（变异/正负样本/真数据）就说「可用」→ 派独立审读者攻一次; 换模型、不传你的结论、只批评不给修法（铁律 25）
- 你实现的「覆盖检查」只报「已覆盖 N 个」而没人工数过 N 该是多少 → 扫描根挂在脚本目录上, 判据最集中的技能根与 references/ 反而漏了（铁律 23）
- 检查一直红而使用者开始无脑跑「接受新基线」→ 基线漂移把真信号一起淹掉; 接受时必须打印改了什么（铁律 23）
- 你要说「某功能不存在 / 装不了 / 不支持」, 而证据是**官网、搜索、项目 README** → 先翻本机 plugin/catalog/manifest 索引目录再断言; 本机才是权威（铁律 17）
- 你为“副本 / 重复 / 版本混乱”下了结论, 而证据是**分几次查了几个根目录** → 把所有相关根连归属方一次倒出来; 连续被推翻两次就别再补细节, 换手段（铁律 19）
- 工具报「共 N 个 X」而你要把它当事实转述, 但还没用**一条不走该工具的命令**数过一遍 → 先对账; 尤其库里有软链/挂载点时, 遍历器默认跳过它们, 漏扫是静默的（铁律 19 第 4 条）
- 卡在某个服务起不来, 而你只读了报错附近几行 → `grep` 你要的那个选项名; 模板注释里常预置了受限环境的解法（镜像 / 离线源 / 强制降级）
- 服务报 `invalid provider: X` 而你在逐个试 → 报错里那份合法值清单就是权威名单, 直接照抄
- 你要判断某个记忆层「有没有在工作」, 却没有做过往返测试 → 装上不等于能用; 查有没有 `retrieval_count` 全 0 的条目（铁律 6 的同源应用）
- 一个自愈脚本报「已切到 X / 已修复」, 但事后测 X 又不通 → 它只验了切换前, 没验切换后（铁律 6 推论 2）
- 自动选择组停在某个不像线路名的条目上, 且全部节点 Timeout → 去列 provider 全部条目, 找伪装成节点的状态公告并按名排除（铁律 6 推论 3）
- 插件日志连打 `initialized` / `registered (N tools)` / `activated`, 但实际请求从没跑通过 → 端口可达 ≠ 连对了服务（铁律 18）
- 一个自我分析工具报了 5 条「弱点」, 你逐条独立核实后发现多数是误报或数字本身错 → 它不是「我在变弱」的读数源, 别拿它当仪表盘（铁律 20）
- 报告「缺技能/无覆盖」的自动工具跑完后, 库里多出一批 mtime 相同、`generated_by:` 开头、不在索引里的新技能 → 它的误报已落成既成事实, 误差在自我繁殖（铁律 20）
- 你已经删掉一批「看着像垃圾」的自动产物 → 改用 `grep -rl '<自报出身字段>'` 全库再扫一遍; 实测按名字删 8 个、按内容标记查出 17 个（铁律 20）
- 你要写一个「扫全库」的自检脚本, 打算靠跑每个脚本看它报不报错来判好坏 → 三类假阳性（`--help` 非通用参数 / 库模块没有 `__main__` / 跨平台脚本），先改纯静态判据; 且死指针必须连 `~/.hermes/scripts/` 一起查（只查技能目录实测误报 16 个）
- 评估器/评分器与被它评估的东西在同一可写范围里, 或你只打算输出一个总分/一个 exit code → 先读铁律 23/24（环外不变量 + 可归因输出）
- 自检脚本报「语法全绿」就认为代码能跑 → 语法层不管未定义名; 接 ruff, 并注意这类 bug 多半是**你刚改出来的**（铁律 21）
- 不可逆动作的脚本里有「确认删除?」提示, 而 `grep -c 'input('` 为 0 → 假防护, `if False` 让取消分支永不执行（铁律 21）
- 新接的 linter 报了一堆问题, 第一条是 `All checks passed!` / `Found N errors` → 那是成功标记不是发现, 解析器要显式过滤（铁律 21）
- 测试全绿就认为代码是对的 → 改坏一个具体方式（判据改回旧错形式/删关键分支/删 import）跑一遍, **不变红就是没测到**（铁律 22）
- 变异「没生效」而被跳过 → 那不是通过; 替换没匹配上与通过在输出上一样（铁律 22）
- mock 设成恒定失败、于是两条代码路径结果相同 → 那种测试删掉被测分支也照样过（铁律 22）
- 一个检查器/watchdog 从没报过任何东西 → 可能是哑的; 注入一个已知坏态验一次（铁律 22）
- 新接一批规则报了几十条 → 先 `--statistics` 按条量命中数并逐条看, 多为设计所时就标注 noqas 而不是整批关（铁律 22）
- 规则报「没找到凭据」而你确知那里有个`API_KEY` → 该规则不认这个名字, 是覆盖洞不是环境干净（铁律 22）
- 自检里某条判据改坏了照样全绿 → 那条判据没有专属样本, 被别的分支的同结论兜住了; 数「判据条数 vs 样本条数」并逐条改坏验一遍（铁律 22b）
- 自检样本断言「超过 45 天应淘汰」, 改阈值后自检变红 → 样本把结论钉死了, 改成断言序关系 `旧 > LIMIT > 新`（铁律 22b）
- 写好 demo 样本自检全绿, 拿真实文件一跑就抛异常 → 手写样本比真实数据干净; 解析分支的样本必须含当初崩过的那串（铁律 22b）
- 自检红而你觉得判据没问题 → 先算样本的实际值; 期望值本身可能写错（铁律 22b）
- 一段「按名字/后缀/前缀匹配外部数据」的排序或筛选代码看着在工作 → 先数真实数据上的命中率; 恒为 0 = 死代码（铁律 4）
- 一个判据的触发词与它的标签用词重叠（如「作废条件」里含「作废」）→ 标签自己命中触发词; 匹配前先把标签挖掉（铁律 22b 第 6 条）
- 用 lookbehind 写「排除前面那段」的判据, 遇到 `\s`/`+`/`*` → 静默永不匹配不报错; 改用 search 定位 + 切片（铁律 22b 第 7 条）
- 报「已提交/入库干净」而依据是 `git status --porcelain` 为空 → 未跟踪的新文件不显示在干净表象里, 用 `git ls-files <新文件>` 确认
- 新写的文件只落在工作目录、没进仓库目录 → 先确认两处**是不是同一个目录**（`readlink -f`, 软链才是）; 同步后逐字节比对并反向全量查漏（缺文件 + 同名不同内容两类都报）

## 18. 端口可达 ≠ 连对了服务 —— 「打错端口」的指纹是初始化日志全绿

铁律 6 说「别信中间信号」。这条是它的**镜像**: 连对了端口、拿到 200、初始化成功, **依然是错的**——
因为那个端口上跑的是**另一个服务**, 它对探测请求的回应被当成了「兼容的旧版 API」。

实测: 一个本地记忆后端按配置模板的默认端口连, 而那台机器上该端口已被**无关服务**占用。
日志连打三行, 每行都正常:
```
initialized: mode=local_embedded, api_url=http://localhost:8888
Memory provider 'hindsight' registered (3 tools)
Memory provider 'hindsight' activated
```
它的版本探测打到了那个无关服务, 失败被当成「旧版 API」**静默降级**——**不报错、不降权、只是把记忆写到错的去处**。
若停在这里, 用户拿到的是一个**看起来装好了的假记忆系统**, 且无从察觉。

**规则: 初始化成功后, 第一件事是确认「那个端口上跑的是不是它自己」**, 而不是确认「端口有东西在应答」。
```bash
# 权威判据: 服务自己的身份端点, 不是 health 的 status 字段
curl -s http://127.0.0.1:<port>/version | head -c 120
# 对不上就认输: 认得出是别的服务(HTML 页面 / 另一个 JSON schema)说明打错了
```
**配置里显式写死端口, 不靠默认值。** 硬编码的默认端口是**假定那台机器上没人占**——而那正是它静默连错的成因。

**更一般的形式: 任何「连上就认为成功」的探测, 都要能被问「你连的是谁?」**
只回答「连上了」的探测不足以支撑成功判据; 能回答「连的是 <服务端自报的身份>」才算。

## 19. 「同名命中」不等于「查过了」—— 分多次查多个根目录 = 必然错一次

前面 18 条防的都是**工具给的读数**不可信。这条防的是**你自己**：
你分三次查了三处, 每次都查对了那一处, 然后把它们合起来当结论——**而“还有第四处”从未被枚举过**。

典型现场: 问“是不是有多份副本/版本混乱”。第一轮 `glob` 命中 N 个同名目录 ⇒ 报「N 份副本」;
复核时发现其中大部分是软链（同 inode）⇒ 改口「只有 1 个真拷贝」; 再查发现**真拷贝压根不在那批路径里**,
而在另一个根目录下 ⇒ 结论第三次改。**三次结论都不对, 而每一步的局部测量都是真的。**

**机制**: 结论的范围（“有几个副本”）大于证据的范围（“我查过的那几个目录”）。
`glob('**/SKILL.md')` 命中的是**同名**, 不是**全部** —— 它只在给定根下命中, 而“有哪些根”本身是待查项。

四条硬规矩:
1. **拓扑类问题（副本/冲突/重复/谁引用谁）必须一次性把所有相关根连归属方一起倒出来**, 再逐项定性。
   一次性倒出来 = 一次命令同时打印所有根 + 每个条目属于哪个根 + 是否软链 + inode + 内容哈希。
2. **同一对象被连续推翻两次时, 禁止继续补细节** —— 直接换手段, 换成“把全部状态一次倒出来”的那条命令。
   连错两次说明**手段选错了**, 不是数据没查全; 第三次去补一个细节仍然是错的。
3. **给用户的每个数字都要能当场复现**。自己都没法再跑一遍的数字不配出现在结论里。
4. **工具自报的总数, 报给用户之前必须用一条独立命令对账** —— 尤其当那个总数就是这条工具自己算出来的。
   「检查器报 73 个技能」和 `find -L <根> -name SKILL.md | wc -l` 给出两个数时, **不要选你更信的那个, 要解释差在哪**。
   实测: 检查器用 `os.walk`(默认 `followlinks=False`) 报 73, 而 `find -L` 与 INDEX 都给 79 ——
   差的 6 个是软链技能, **它们不只是没被计数, 而是从头到尾没被检查过**(frontmatter/死指针/生成物全跳过),
   而这个工具全程 exit 0「✅ 无问题」。
   机制: `os.walk` 默认不跟随软链, 而软链指向的目录**整体**不出现在遍历结果里 —— 不报错、不计数、不告警。
   **判据: 凡工具报的「共 N 个」, 必须有一条不走该工具的枚举命令能复现这个 N; 对不上就是工具漏扫, 不是数据变了。**
   尤其在库含软链/挂载点/外部目录时 —— 这些是遍历器默认跳过的形态。
   配套: 修完要用**负样本**证明确实扫到了（破坏一个软链目标里的东西, 看抓不抓得到）,
   光看总数从 73 变 79 不算证明 —— 数字变了也可能只是换了个更糟的 bug。

**自检: 报结论前问一句「我这次的证据范围, 比我这次结论的范围大吗」。**
一样大 = 有多少根/多少对象是**事先枚举的**? 没枚举过就只是“在我看的这批里”——**那要把这个限定写进结论**。

**配对信号**: 用户问的是“是不是有 N 个”而不是“为什么有 N 个”时, 你大概率已经预设了“重复”这个前提。
去问“它们分别属于谁”, 往往得到“不是重复 / 没有统一的源头”这种与前提相反的答案。

## 20. **自我改进类工具的信号，本身要先验**——它报「我在变弱」时最危险

前面 19 条防的都是**外部工具**给的读数。这条防的是**报告你自己的那个工具**。
自我分析器（Dojo / 复盘 / 指标看板）的读数有两个额外风险，因为它对错误的**自我强化**：
读数错 → 你去改技能 → 指标变好 → 你更信这个读数。

四个必查点（2026-10-02 实测，四个全中）：

1. **它是不是根本没在跑。** SKILL.md 里写「每天 6:00 自动分析」**只是文档**。
   实测跑了 15 天才第一次手动触发。查法：`grep <关键词> cron/jobs.json`，
   以及指标文件的 mtime——**指标停更的时间就是它没跑的时间**。

2. **演示数据有没有混进正式指标。** 实测学习曲线 5 条里 4 条是 `demo.py` 造的
   （`Day 1 baseline 34% → Day 5 83%` 这个漂亮曲线是演出来的），写进了正式 `metrics.json`。
   判据：**指标文件里出现 `Day N` / `baseline` / `first fixes` 这类模板化 label，
   或数值整齐递增 ⇒ 先假设是 fixture**，再去找哪个 demo 脚本写的。
   配套修法：demo 走独立文件 + 断言防呆（`assert demo_file.name != METRICS_FILE.name`），
   并用 **md5 前后不变**证明没污染。

3. **「能力缺口」有没有真的查过能力存不存在 —— 而它拿到结论后会不会顺手把缺口「填」上。**
   实测报「database 45x / docker 32x / git 17x，无技能存在」——它只做关键词命中，
   **从不查技能库**；实际这几个都有技能覆盖。
   判据：**任何输出「no X exists / 未覆盖」的探针，必须能看到它查过目标位置**；
   看不到就先自己 `grep` 一次。查不到 ≠ 不存在（与铁律 17 同源）。

   **升级形态（比误报严重得多）：这类工具的「修复」动作可能是往库里写。**
   误报只是说错话；**自动补一个空壳填上，错误就变成了既成事实**——
   下一轮它读到自己的产物，还会把这批「已修复」算进成绩，于是误差自我繁殖。
   实测一个分析器跑一次就在技能库根目录生成 8 个技能：frontmatter 自报出身、
   正文是同一段模板套话，连错误类型都填成了 `Most common error pattern observed: unknown error`。

   **三个指纹，用来在被污染的库里认出这批产物：**
   - frontmatter 带 `generated_by:` / `generated_reason:` 这类**自报出身**字段；
   - 正文含占位语（`unknown error` / `based on observed user request patterns`）与通用 workflow 段；
   - 一批文件 **mtime 完全相同**（= 那一次运行的时刻），且**落在分类目录之外**——
     索引生成器只扫 `<根>/<分类>/<技能>/`，根目录的产物**永远不进索引**，
     于是任何以「索引」为视野的清理都看不见它们。

   **判据：报告「缺口/未覆盖」的自动工具，先问它拿到结论之后会不会写库。**
   会写 ⇒ 先在一次性副本上跑，或整个禁用它的写入分支，**只取读数不取写入**。
   已经跑过的 ⇒ 按上面三个指纹扫一遍再谈别的，**别只删它自己那几个文件**。

   **扫描产物时，筛选用「自报出身的内容字段」而不是「名字看着像不像垃圾」。**
   实测：先 `ls` 库根目录、按名字判断（`csv-parsing` / `docker-management` 看着像垃圾），
   删掉 8 个就收工；改用 `grep -rl 'generated_by:'` 全库扫，又挖出 9 个——
   名字是 `terminal-run` / `read-file` / `session-search`，
   **每一个都像正常技能，只看名字一个都怀疑不到**。最终 17 个。
   机制同铁律 19：**「哪些看着可疑」本身是待查项，不能当筛子**。
   判据：**凡「找某类产物」，一律按内容标记 grep，禁用文件名/目录名筛选。**

4. **错误分类靠关键词扫正文时，会把「提到错误」当成「发生错误」。**
   实测 `(?i)timeout|could not` 这类模式让成功率显示 80.7%，改成解析结构化字段
   （`exit_code != 0` / `success == false`）后是 92.6%。低报的那 12% 里，
   一部分是**报告正文里写了「20 分钟被 timeout 杀」**。
   判据：**分类器应当解析结构化字段，不是扫散文**；正则兜底只认行首锚定的标记。

**更狠的一层: 报告的统计口径要和原始数据对账。** 上面那次修完仍不可信——
分析器报「memory 64.5%，27/76 失败」，全量拉 `state.db` 数真实值是 **48.1%，163/314**。
差在两处：**窗口只取 7 天**（长期问题看不到）+ **警告块被重复计数**（同一失败重复落库）。
判据: **报任何率之前，先用一条独立 SQL 数一遍分母**。分母对不上就别报。

**配套: 被它指出的「弱点」要先分清是我的错还是它的错。** 那 163 次 memory 写入失败里，
**~70 次是我自己的调用格式错**（`replace` 少给 `old_text`、凭记忆写已被改过的旧文本、
用了不存在的 `action='list'`），而且工具都喊 `failed 4 times, stop retrying` 了还在重试。
判据: **失败归因先分「参数/用法」「容量/限额」「环境/通道」三类**，只修第一类——
把格式错修成「工具故障」会指向错误的修复方向。

## 20.5 修一个判据时连改多版：**先插桩，别接着改**

改判据改到第二三版还不对时，最常见的错误不是「再想一个判据」，而是**一直没看过是哪一维在抖**。
在 return 之前打一行，把各个判据的布尔值一次打全：

```python
print(f"chg={changed} new={len(new)} drop={len(dropped)} "
      f"sig={sig != prev} aa={sig_aa != prev_aa} or={sig_or != prev_or}", file=sys.stderr)
```

跑一次就知道是哪一维在变。**重写三轮判据不如插一行桩看一次。**

**发现两个要求互相矛盾时（例：比率型判据与绝对次数型判据在样本量小时互斥），
在撞上矛盾的那一刻就停下来问决策者，不要自己挑一个接着改** ——
自己挑的结果通常是改完才发现挑错了，前面的修改全部作废。

**止损线**：

- 同一症状连改两版不对 → 停止修改，回到插桩定位。
- 连改三版仍不对 → 大概率是需求矛盾，不是实现问题。
- **预算按症状严重度缩放**：先问「这个故障最坏造成什么」。看起来严重的
  （静默失效、签名失配）实际后果常常只是**噪音**，而噪音不值得连烧二十次工具调用。
- **用户开始问「怎么这么久/肯定有问题」时，立刻停手交底**（已花的调用、根因、
  当前真实状态、剩余选项），并诚实报「我判断错了」——比如把一个不致命的抖动
  当成了彻底失效。用户据此决定收工还是换方向；继续跑完手��循环是替他做了决定。

## 21. 自检脚本要**分层接成熟 linter**, 别自己手搓 —— 每层盲区不同, 而且最深那层只有现成工具能穿透

前面 20 条防的是**读数不可信**。这条防的是**读数看起来全绿, 但它只看得到最浅的一层**。
自己写的「语法检查」只是冰山一角, 而**真正会伤人的那类 bug 恰好全在水面下**。

**各层的实际覆盖面**（实测同一批 97 个 .py）:

| 层 | 能抓 | 抓不到 |
|---|---|---|
| `py_compile` / `ast.parse` | 语法错误 | **未定义名**、恒假分支 |
| `ruff --select=E9,F63,F7,F82` | 语法 + 未定义名 + 不可达 + 坏比较 | 逻辑错 |
| `shellcheck -S error` | shell 静态（warning/note 噪音太大, 滤掉） | 跨脚本行为 |
| `vulture` (`unsatisfiable` only) | **恒假分支** | 正常的未用变量（噪音大, 必须只取 unsatisfiable） |

**为什么未定义名是重点**: 它不在「语法」里, 也不在「类型」里, 但**一运行就崩**。
实测一个脚本被改脱敏时把 `os.environ.get(...)` 引进来却没加 `import os`,
`ast.parse` 全绿、ruff 一抓一个准 —— **这类 bug 恰恰是你自己改出来的**, 手工检查最容易漏。
配套: `ast.parse` 而非 `py_compile`, 后者会写 `__pycache__` 污染被检查的库。

**vulture 那层是唯一能穿透「全绿代码在骗人」的**:

```python
print("⚠️ 确认删除? (yes/no)")
if False:            # ← 这行让取消分支永远不执行
    print("❌ 已取消"); return
# 直接往下删文件
```

语法合法、ruff 通过、逻辑连贯, 脚本 docstring 还写着「✅ 安全清理工具」。
**但它从不读用户输入**—— `input()` 被删了换成 `if False`, 提示语留着, 询问行为没了。
成因是当初为了非交互运行删掉了 `input()`, 却没删提示语, 于是**看起来有防护, 实际没有**。
vulture 的 `unsatisfiable 'if' condition (100%)` 是唯一报它的东西。

**规则: 任何不可逆动作（删/移/改权限/发外部请求）的脚本, 「提示语」与「读输入的调用」必须成对存在。**
审这类脚本先 `grep -c 'input('` —— 提示语在而 `input()` 为 0 ⇒ 假防护。
**判据: 防呆分支被硬编码关掉（`if False` / `if 0` / `return True` 提前吞掉）, 与没有防呆等价,
而外观上更像有防护 —— 这是比裸奔更糟的形态。**

**接进来之后仍要过负样本门禁**: 加了 linter ≠ 判据对。
实测第一版把 ruff 成功时的 `All checks passed!` 当成了问题报出来。
**规则: 工具的成功标记不是发现** —— 解析器必须显式过滤 `All checks passed!` / `Found N errors` 这类汇总行,
并且跑「干净库必须 exit 0」的负样本, 否则新工具只会制造噪音。

**泛化**: 自己手搓检查器前先问「这一层的成熟方案是什么」。
GitHub 上 ruff / shellcheck / vulture / lychee / gitleaks / bandit 各自覆盖不同层,
**它们的层与你的层不重叠时, 装上比手写便宜两个数量级**。
不装的判据很具体: **依赖不成立就别装**（hypothesis/mutmut 需要先有测试套件才有意义;
gitleaks 查不出中文 PII, 已有专用脱敏器时是重复）。

## 22. 测试与检查器自己也要验：全绿和全错在输出上长得一样

铁律 4 是「用**已知正确**的样本验读数通道」。这条是对称的另一半：用**已知错误的答案**验它有没有分辨力。

**全绿不证明测试有效。** 上线前把被测代码改坏一个具体方式，跑测试，**必须变红**：
判据改回旧错误形式 / 删掉一行关键分支 / 删一个 import / 判据退化成空操作。
不变红 = 那条测试没测到它声称测的东西。**每个变异单独恢复**（叠着变异时红屏说明不了是哪个测试起作用），
**跳过 ≠ 通过** —— 替换字符串没匹配上时脚本会打印「模式没匹配」然后跳过，看上去像通过了。

**最隐蔽的一种：mock 让所有分支走同一条路 ⇒ 测试零分辨力。**
写「切换后必须复验」的测试时把探针设成恒定失败，两条路径（验了/没验）表现完全一样——
**把复验那行整个删掉，测试照样通过**。正确做法是用**状态化 mock**（「第一次通、之后不通」），
让断言落在两条路径结果不同的那个变量上；并配一条反向的正向测试，
否则「永远返回 None」也能测成绿的。

**静默路径同样是个读数。** watchdog 的「无输出 / exit 0」有两种可能：真的干净，和它根本没在看。
上线前验三态：① 正常 → 静默 ②**注入一个已知坏态** → 必须报③ 撤掉 → 恢复干净。
**自动化一个哑巴检查器，危害大于不自动化** —— 它会一直显示绿灯，让人以为有闸门。

**接现成规则集前，先按条量命中数并逐条看过**，不要整批开或整批关。
实测某批安全规则在真实库上报 120 条，绝大多数是本库设计如此（脚本调 subprocess、绑 0.0.0.0 供手机访问、
参数化查询）。**误报用 `# noqa: <code> — 为什么这里安全` 逐处标注，不要删规则** ——
删规则等于放弃未来的信号；标注保留了「我看过、这里为什么安全」。
规则集本身也可能有覆盖洞：实测某条「硬编码密码」规则**不认 `API_KEY`**，而那才是最常泄露的一类；
这类洞只能拿真样本逐个试出来。

### 22b. 判据型自检的样本设计（全文见 ref）

写「给数据打标签/判过期/挑可疑项」这类带多条判据的自检时，样本集本身最容易骗人。
**完整 15 条**（样本设计、环外不变量、验证器可归因、独立审读）
→ `references/criteria-code-design.md`

速查最常用的 3 条：
1. **一条判据可能根本没被测到** —— 因为另一条判据顺手给了同一个结论。数「判据条数」与「样本条数」，一一对上。
2. **配一条反证样本**：同一条输入只改一个 token，结论必须翻转。
3. **样本不要硬编码阈值的结论，要断言「关系」**（`assert age(旧) > LIMIT > age(新)`）。

⚠️ 最危险的一条（原文）：**「状态缺失/损坏 → 不该报」的断言，绝大多数是 fail-open 在盖章。**
问「攻击者第一步删哪个文件最省事」——若答案正是这个状态，自检就在替全部静默绕过背书。
